# 00 · Flowable 历史表族 —— 宏观篇

> 这一篇不讲任何具体字段，只回答三个问题：**为什么会有历史表 / 它们和运行时表是什么关系 / 八张表各站什么位置**。
> 微观逐表见同目录 `01`~`05`。
>
> 全程用当前库（`flowable_db2`）里的两条真实实例当标本：
> - **test-0004** `175ffafb-84bc-11f1-b2ab-5eea1d7fcc1d` —— 已办结（employee 发起 → manager 办理 → endEvent）
> - **test-0005** `6a897d3d-84d2-11f1-b2ab-5eea1d7fcc1d` —— 在途，停在 `managerApprove`

## 一、诞生背景：为什么不能只有一套表

先设想一个**没有历史表**的引擎，只有 `ACT_RU_*`。会撞上两堵墙。

### 墙 1：完结的数据往哪放

流程实例天生有生命周期：发起 → 流转 → 完结。完结后这条实例还有没有用？

有，而且用处很大——「我的已审批」、「这单谁批的」、「平均审批耗时」、「三个月前那笔报销的审批链」。**审批系统的价值有一半在事后可追溯**，办完就消失的系统没人敢用。

那把完结的实例继续留在 `ACT_RU_*` 里行不行？撞第二堵墙。

### 墙 2：运行时表必须小

`ACT_RU_EXECUTION` 不是一张普通业务表，它是**引擎每走一步都要读写的热表**。你在 Day 13 的日志里亲眼看到了，办理一个任务，引擎对它 `select` 了 4 次、`update` 2 次、`delete` 2 次——而这还只是一个只有三个节点的最简流程。

如果完结的实例永远堆在里面，一个跑了三年的系统会有几百万行死数据压在这张最热的表上，每一次流转都要在这堆垃圾里翻找。索引会膨胀，锁竞争会加剧，而这些死数据**运行时一次也用不到**。

### 于是：冷热分离

两堵墙夹出唯一的解法——**分成两套表**：

| | 运行时表 `ACT_RU_*` | 历史表 `ACT_HI_*` |
|---|---|---|
| 装什么 | 只装**在途**的 | 装**全部**（含在途） |
| 读写特征 | 高频读写，引擎每步都碰 | 写入频繁但只追加/更新，读取由用户触发 |
| 数据量 | 恒定在"当前在途量"级别 | 只增不减，随时间线性增长 |
| 谁在用 | **引擎自己** | **业务查询**（你的 HistoryService 接口） |
| 完结后 | 行被**删除** | 行**保留**并补上结束信息 |

这是数据库设计里非常经典的一招：**把一张兼具"工作台"和"档案馆"两种职能的表拆开**。工作台要快要小，档案馆要全要久。两者的优化方向完全相反，硬塞在一张表里会互相拖累。

> 类比：银行的"当前挂单"和"历史流水"从来不是一张表。撮合引擎只关心挂单簿，对账系统只关心流水。

## 二、设计意图：HI 不是"归档区"，是"全量账本"

这是**最容易理解错的一点**，也是你 2026-07-21 那天亲手验出来的：

> 终止 test-0002 **之前**查 `ACT_HI_PROCINST`，那行**已经存在**了（`END_TIME_` / `DURATION_` / `DELETE_REASON_` 全空，`REV_=1`）。

所以数据流**不是**"完结时从 RU 搬到 HI"，而是：

```
发起时  ──►  同时写 RU 和 HI        （HI 行诞生，处于"未完结"状态）
流转中  ──►  同时更新 RU 和 HI       （日志里 updateActivityInstance 与
                                       updateHistoricActivityInstance 成对出现）
完结时  ──►  删除 RU，更新 HI 补结束信息（REV_ 1→2 就是这次更新的指纹）
```

**"双写"是理解整个历史表族的钥匙。** 由此推出三个重要结论：

**结论 1：HI 是 RU 的超集。** 任何时刻 `ACT_HI_PROCINST` 的行数 ≥ 在途实例数。在途实例在两边都有。

**结论 2：在途的东西也能从 HI 查到。** 这就是你 `HistoryController` 上那句注释「运行中的实例也可查」的底层依据，也是 test-0005 虽然没办完、`ACT_HI_ACTINST` 里却已经有 3 行的原因。

**结论 3：「未完结」的标志是 `END_TIME_` 为空。** HI 表里的行分两种状态：进行中（`END_TIME_` NULL）和已完结（`END_TIME_` 有值）。所有 HI 表都遵循这个约定。你的 `approved()` 里那句 `.finished()`，翻译成 SQL 就是 `END_TIME_ IS NOT NULL`——**没有它，正等着你办的任务会混进"我的已审批"**。

> ⚠️ 代价：双写意味着**每个引擎动作的写入量翻倍**。这是 Flowable 性能调优的首要战场，也是下面"历史级别"这个开关存在的原因。

## 三、八张表全景：核心四张 + 外围四张

Flowable 的历史表有 8 张。它们不是平级的，分两圈：

### 内圈（核心四张）—— 回答"流程走过什么"

| 表 | 一句话 | 粒度 | 你项目里谁在用 |
|---|---|---|---|
| `ACT_HI_PROCINST` | **一条实例一行** | 实例 | 将来的"我的申请"历史列表 |
| `ACT_HI_TASKINST` | **一个人工任务一行** | userTask | `GET /history/approved`「我的已审批」 |
| `ACT_HI_ACTINST` | **走过的每一步一行**（含连线） | 所有节点 | `GET /history/instance/{id}/activities` 轨迹 |
| `ACT_HI_VARINST` | **一个变量一行**（存最终值） | 变量 | 历史表单数据回显 |

它们的关系是**逐级细化**：一条实例（PROCINST）走过若干步（ACTINST），其中的人工步骤额外单独记一份（TASKINST），过程中携带的数据另记一份（VARINST）。

```
ACT_HI_PROCINST      1 行   test-0004 这一单
   └─ ACT_HI_ACTINST 5 行   startEvent / flow1 / managerApprove / flow2 / endEvent
        └─ ACT_HI_TASKINST 1 行   只有 managerApprove（唯一的人工节点）
   └─ ACT_HI_VARINST 5 行   days / reason / initiator / approved / comment
```

> 注意 `ACT_HI_ACTINST` 和 `ACT_HI_TASKINST` 在 `managerApprove` 这一步**重复记录**了。这不是冗余失误，是刻意为之——原因在 `01` 篇细讲。

### 外圈（外围四张）—— 回答"人对流程做了什么"

| 表 | 一句话 | 何时写入 | 默认是否有数据 |
|---|---|---|---|
| `ACT_HI_IDENTITYLINK` | 谁和实例/任务是什么关系（发起人、候选组、参与者） | 随实例/任务 | ✅ 有 |
| `ACT_HI_COMMENT` | 操作日志与审批意见 | 认领/改派时自动写；审批意见需代码显式调 | ✅ 你库里已有（claim 留痕） |
| `ACT_HI_ATTACHMENT` | 附件元信息（不存文件本体） | 代码显式调 `taskService.createAttachment` | ❌ 空（没写过） |
| `ACT_HI_DETAIL` | 变量的**每一次变更**（不是最终值） | 仅 `full` 历史级别 | ❌ 空（默认 `audit` 级别不写） |

**为什么这四张是"外围"**：核心四张记的是**引擎自己的行为**（引擎跑到哪、停在哪、带了什么数据），不写就等于引擎失忆；外围四张记的是**人的行为与附加信息**（谁评论了、谁传了附件、变量被改了几次），缺了不影响流程理解，属于"锦上添花的审计增强"。

**为什么值得知道它们存在**：你现在的需求（我的已审批 + 轨迹）核心四张就够了。但一旦产品提出——

- "审批意见要显示在轨迹上" → `ACT_HI_COMMENT`
- "要看到请假条附件" → `ACT_HI_ATTACHMENT`
- "这个金额字段被改过几次、谁改的" → `ACT_HI_DETAIL`（且必须提前调到 `full` 级别，**事后调没用，历史补不回来**）
- "抄送人、协办人也要能查到这单" → `ACT_HI_IDENTITYLINK`

——你才知道该往哪找，而不是去业务表里另造一套。

## 四、总开关：历史级别（history level）

双写有代价，所以 Flowable 给了一个全局开关，四档递增：

| 级别 | 写哪些 | 适用 |
|---|---|---|
| `none` | **什么都不写**，HI 表全空 | 极致性能、纯自动化流程（无人工审批） |
| `activity` | PROCINST + ACTINST + VARINST | 只要轨迹、不要任务级审计 |
| `audit` | 上面 + **TASKINST** + 表单属性 | **默认值**，绝大多数审批系统用这档 |
| `full` | 上面 + **DETAIL**（变量每次变更） | 强审计场景（金额、合规），写入量最大 |

配置项：`flowable.history-level`（Spring Boot starter）。

三个必须记住的点：

1. **默认是 `audit`**，所以你什么都没配，`ACT_HI_TASKINST` 就有数据——「我的已审批」能做得成，是这个默认值给的。
2. **`full` 必须提前开。** 历史是"当时记下来的"，事后调级别对已发生的流程无效。要审计就一开始就开。
3. **调级别是全局的**，不能只对某个流程开 `full`。要精细控制得用其他手段（如显式写 comment）。

> 另有 `async-history`（异步历史）：把历史写入丢进后台队列，主线程不等它落库。能明显提升吞吐，代价是历史数据有秒级延迟——**办完立刻查"我的已审批"可能查不到**。你这个 demo 用不上，知道有这么个东西即可。

## 五、"能不能删"的三个层次（重要，别混淆）

后面每篇都会回答"能不能删"，但**"删"有三种完全不同的含义**，先在这里分清，否则会得出自相矛盾的结论：

### 层次 1：DROP 掉这张表

**不行。** 引擎启动时会做 schema 校验（你的 `database-schema-update` 配置决定行为）：

- `true`：发现表缺失会**自动重建**，你白删
- `false` / `validate`：直接**启动失败**

而且即使侥幸跑起来，`HistoryService` 的任何查询都会因表不存在而抛异常。**表结构是引擎契约的一部分，不属于你能裁剪的范围。**

### 层次 2：不往里写（关掉历史级别）

**可以，这是官方支持的方式。** 调 `flowable.history-level` 即可。代价是对应功能直接消失——把级别调到 `activity`，`ACT_HI_TASKINST` 不再写入，你的「我的已审批」永远返回空列表，但**引擎照常运转**，流程该走还走。

这印证了一个关键事实：**引擎运行时不读历史表**。历史表是纯粹的"写出去给人看"的旁路，它对引擎自身是只写不读的。（唯一例外是历史数据的删除/查询 API 自己会读。）

### 层次 3：删掉表里的数据（保留表）

**可以，而且是生产必做的运维动作。** 三种做法：

- `historyService.deleteHistoricProcessInstance(id)`：按实例删，会连带清掉它在四张核心表里的所有行
- `repositoryService.deleteDeployment(id, true)`：**cascade 删部署时连历史一起删**——你 Day 12 步骤 5 亲眼见过，`ACT_HI_PROCINST` 归零
- 定时归档：把 N 年前的历史迁到冷库/数仓再删，这是大型系统的标准做法

> ⚠️ 这里有个业务陷阱，你已经踩过一次并记进文档了：**`terminate` 清 RU 保 HI（业务作废，可追溯）；`cascade=true` 删部署则 RU + HI 一并抹除（审计线索归零）**。前端删除流程模板的二次确认，拦的就是后者——用户以为在"删一个模板"，实际连所有历史审批记录一起没了。

## 六、四个常见误解（先破了，后面读起来顺）

| 误解 | 实情 |
|---|---|
| "HI 表是完结后才写的归档表" | 发起时就写了，全程双写。HI 是全集不是子集 |
| "查历史 = 查已完成的" | HI 里在途的也在。想只要完成的必须显式 `.finished()`（= `END_TIME_ IS NOT NULL`） |
| "引擎靠 HI 表恢复流程状态" | 引擎**从不读** HI 表跑流程。删空它引擎照跑，只是人看不到过去 |
| "ACT_HI_ACTINST 和 ACT_HI_TASKINST 重复了" | 粒度不同、生命周期不同、可查字段不同，刻意冗余。见 `01` 篇 |
