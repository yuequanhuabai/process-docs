# 03 · 字母约定与签名读法

> **触发点**：`00` 第三节 Q3 只给了一张「`T` = Type、`E` = Element」的对照表就结束了；`02` 又甩了一串
> `<T:Ljava/lang/Object;>(TT;)Lcom/ha/pr/flowwork/common/R<TT;>;` 出来没教怎么读。
> 本篇专治这两件事：**这些字母到底是什么东西**，以及**拿到一个陌生泛型签名，从哪儿下手拆**。
>
> 本篇是从「懂原理」转向「能动手」的第一块砖。`04` 开始要自己写泛型，写之前得先能读。

---

## 一、先纠两个误解

### 误解 1 · `T`、`E`、`K`、`V` 是 Java 的关键字

**完全不是。编译器根本不认识这些字母。**

它们和 `int i = 0` 里的 `i` 是同一个性质——**你自己起的名字**。改成 `Banana`、`元素`、`XyzZy` 一样能编译通过（本篇实验 1 会亲手改一遍）。

Java 语言规范里，类型参数的名字只要求是**合法标识符**，仅此而已。

### 误解 2 · `T` 是"某种类型"

这个误解更隐蔽，也更要命。很多人以为 `T` 是一个特殊的、万能的类型，像 `Object` 那样。

**不是。`T` 是一个「变量」，只不过它装的不是值，而是类型。**

| | 装什么 | 声明 | 传实参 |
|---|---|---|---|
| 普通形参 | **值** | `void f(String data)` | `f("abc")` |
| 类型参数 | **类型** | `<T> void f(T data)` | `f("abc")` → T 被推断为 `String` |

**这是本篇最重要的一句话。** 后面所有读法都从它推出来。

## 二、纵向剥层：类型参数是"类型的变量"

### 2.1 一行代码里其实传了两种实参

看你项目里最熟的那一行：

```java
return R.ok(vo);
```

这一行**同时传了两个实参**：

```
R.ok(vo)
  │   └── 值实参：vo 这个对象
  └────── 类型实参：SysUserVO 这个类型（你没写，编译器推的）
```

写全了长这样，**完全合法**，你可以在项目里试着改一行：

```java
return R.<SysUserVO>ok(vo);   // 显式传类型实参
//       ↑ 尖括号写在方法名前面、点号后面
```

平时不用写，是因为编译器能从 `vo` 的类型倒推出来。**但"没写"不等于"没有"**——它一直在那儿，只是被省略了。

> 💡 这个显式语法 `对象.<类型>方法()` 长得很怪，正因为它太丑、几乎没人写，所以大多数人从没意识到"类型实参"这回事的存在。

### 2.2 声明处 vs 使用处（读签名的第一步）

同样是尖括号，有两种完全不同的含义：

```java
public class R<T> { ... }            // ← 声明：定义一个新的类型变量 T
private T data;                      // ← 使用：用刚才那个 T

List<String> list;                   // ← 使用：给 List 已有的类型参数传实参 String
```

**判据（记这一条就够）：**

> **尖括号紧跟在 `class` / `interface` 名后面，或紧跟在方法的修饰符后面（返回类型之前）—— 是声明。**
> **出现在其它任何位置 —— 是使用，是在传类型实参。**

对照着看：

```java
public static <T> R<T> ok(T data)
//            ↑声明 ↑使用 ↑使用
//     这是唯一的声明点，后面两个 T 都是在引用它
```

```java
private <E> IPage<ProcessInstanceVO> toPage(Query<?, E> query, ...)
//       ↑声明                                        ↑使用
```

**看不出哪个是声明点，就永远读不懂签名。** 这一步比认字母重要得多。

### 2.3 读一个陌生签名的四步法

拿 Flowable 那个吓人的签名做例子：

```java
public interface Query<T extends Query<?, ?>, U> { ... }
```

**第一步 · 圈出声明点，认出哪些字母是变量**

紧跟 `interface Query` 后面的 `<...>` 是声明区，里面声明了两个变量：`T` 和 `U`。
**其余出现的 `Query`、`?` 都不是变量。**

**第二步 · 剩下的都是具体类型**

`Query` 是这个接口自己。所以 `T extends Query<?,?>` 的意思是「T 必须是 Query 的某个子类型」。

**第三步 · 看边界（`extends` 后面那截）**

- `T extends Query<?, ?>` —— T 有上界，必须是个 Query
- `U` —— 没写 `extends`，等价于 `U extends Object`，即无约束

**第四步 · 代入一个真实类型读一遍** ⭐ 最有效的一步

Flowable 里的 `ProcessInstanceQuery` 是这么继承的（大意）：

```java
interface ProcessInstanceQuery extends Query<ProcessInstanceQuery, ProcessInstance>
//                                           ↑ T = 自己         ↑ U = 查询结果类型
```

代入之后再读父接口的方法：

```java
T orderByStartTime();          // 代入 → ProcessInstanceQuery orderByStartTime();
List<U> list();                // 代入 → List<ProcessInstance> list();
```

**读到这儿这个签名就塌了**：`T` 是"我自己"，用来让 `.a().b().c()` 链式调用不掉链子；`U` 是"我查出来的东西"。

> ⚠️ 「让类型参数指向自己」这个套路叫**自限定泛型**（self-bounded generics），是 `06` 篇的正菜，这里只要知道**第四步"代入具体类型"能把绝大多数唬人的签名打回原形**就行。

## 三、横向讲史：这些字母是怎么定下来的

### 3.1 为什么是单个大写字母

Java 官方的命名约定明确写着：**类型参数用单个大写字母**。理由很实际——

类型参数会在一个签名里出现好几次。如果起长名字：

```java
// 假想的长名字版本
public static <ResponseDataType> R<ResponseDataType> ok(ResponseDataType data)
// vs 现实
public static <T> R<T> ok(T data)
```

上面那行的**结构**被名字淹没了。签名要一眼看出形状（几个参数、返回什么），单字母是为了让**结构**浮出来。

**对照组：C# 的约定不一样**——它用 `TKey`、`TValue`、`TResult`，带 `T` 前缀的驼峰名。两条路各有道理：Java 赌"短"，C# 赌"自解释"。**没有对错，是不同的取舍。**

### 3.2 每个字母的来路

| 字母 | 来源 | 最早/典型出处 | 备注 |
|---|---|---|---|
| `T` | **T**ype | `Comparable<T>`、你的 `R<T>` | 直接继承自 C++ 的 `template<class T>` 传统 |
| `E` | **E**lement | `List<E>`、`Collection<E>` | 来自集合框架。**在泛型出现之前**，1998 年的 Collections 文档就已经在用 "element" 这个词描述装的东西了 |
| `K` / `V` | **K**ey / **V**alue | `Map<K, V>` | 同上，沿用集合框架既有术语 |
| `R` | **R**esult / **R**eturn | `Function<T, R>` | **晚得多**——Java 8（2014）引入函数式接口时才成为惯例 |
| `U` / `S` | 没有语义，纯排队 | `Query<T, U>`、`Function.andThen` | **为什么是 U 不是 A？** 因为字母表里 `S T U V` 挨着，需要第二个、第三个变量时就顺着 T 往两边取 |
| `N` | **N**umber | 少见 | |

> 💡 `U/S` 这一条最能说明问题：**它们连缩写都不是，纯粹是"T 隔壁的字母"**。这就是"约定"二字最赤裸的证据——不是设计，是习惯。

### 3.3 代价：字母会撞车

单字母 + 无语义，代价就是**同一个字母在不同上下文里含义完全不同**。你项目里就有现成的例子：

```java
public class R<T> { ... }              // R 是你的响应包装「类」
Function<E, ProcessInstanceVO> mapper  // Function<T, R> 的第二个参数叫 R，是「类型变量」
```

**同一个字母 `R`，在你的代码库里有两个身份。** 所以 `toPage` 的签名里不能照抄 JDK 文档写成：

```java
Function<E, R> mapper   // ❌ 这里的 R 会被解析成你的 com.ha.pr.flowwork.common.R 类，
                        //    而那个类需要一个类型实参，编译报错 / 语义完全走样
```

只能写具体类型：

```java
Function<E, ProcessInstanceVO> mapper   // ✅ 09 文档里的实际写法
```

> 这不是巧合造成的小麻烦，**它就是"字母是普通标识符"这个事实的直接后果**——普通标识符当然会和类名撞。

## 四、纵向剥到底：JVM 签名怎么读

`02` 篇给你看了 `R.class` 里的这一行：

```
Signature: <T:Ljava/lang/Object;>(TT;)Lcom/ha/pr/flowwork/common/R<TT;>;
```

它不是乱码，是一门有语法的小语言。**认识五个记号就能读**：

### 4.1 五个记号

| 记号 | 含义 | 例 |
|---|---|---|
| `L包/类名;` | 一个**引用类型**（分号是结束符，不能省） | `Ljava/lang/String;` = `String` |
| `T名字;` | 一个**类型变量** | `TT;` = 变量 `T`；`TE;` = 变量 `E` |
| `<...>` 在最前面 | **声明区** | `<T:Ljava/lang/Object;>` |
| `名字:上界` | 声明一个变量及其上界 | `T:Ljava/lang/Object;` = `T extends Object` |
| `(...)返回值` | 方法的参数表和返回类型 | `(TT;)V` = 吃一个 T，返回 void |

基本类型有单字母缩写：`I`=int、`J`=**long**（不是 L，L 被引用类型占了）、`Z`=boolean、`V`=void、`D`=double、`[`=数组。

### 4.2 逐字符拆 `R.ok` 的签名

```
<T:Ljava/lang/Object;>(TT;)Lcom/ha/pr/flowwork/common/R<TT;>;
└────────┬───────────┘└─┬─┘└──────────────┬──────────────────┘
      声明区           参数表            返回类型
```

一段一段读：

| 片段 | 读作 |
|---|---|
| `<T:Ljava/lang/Object;>` | 声明一个类型变量 `T`，上界是 `java.lang.Object`（= 没有约束） |
| `(TT;)` | 参数表里只有一个参数，类型是**类型变量 T** |
| `Lcom/ha/pr/flowwork/common/R<TT;>;` | 返回 `com.ha.pr.flowwork.common.R`，并给它传了类型实参 `T` |

拼回来正好是：

```java
public static <T> R<T> ok(T data)
```

### 4.3 两个最容易卡住的地方

**① `TT;` 看起来像打字打重了**

不是。**第一个 `T` 是记号（"接下来是个类型变量"），第二个 `T` 是变量名。**

把变量改名就一目了然了 —— 如果 `ok` 的类型参数叫 `E`，签名里就是 `TE;`；叫 `Banana` 就是 `TBanana;`。（实验 2 会亲眼看到这个变化。）

**② 冒号有一个和两个的区别**

```
<T:Ljava/lang/Object;>          ← 一个冒号：上界是「类」
<T::Ljava/lang/Comparable;>     ← 两个冒号：上界是「接口」
<T:LFoo;:LBar;>                 ← 类上界 Foo，同时还要实现接口 Bar
```

JVM 需要区分类界和接口界（对应 `T extends Foo & Bar` 的写法），就靠冒号的个数。**看到连着两个冒号别以为是笔误。**

## 五、动手实验

### 实验 1 · 证明字母是你自己起的名字 ⭐ 最快见效

打开 `process-back/.../common/R.java`，把 `ok` 方法的 `T` 全部改成 `Banana`：

```java
public static <Banana> R<Banana> ok(Banana data) {
    R<Banana> r = new R<Banana>();
    r.setCode(200);
    r.setData(data);
    r.setMsg("success");
    return r;
}
```

```bash
cd process-back && ./mvnw -q compile
```

**编译通过。** 调用方（几十个 Controller）**一行都不用改**。

> **对照组**：再把 `Banana` 改成 `int`（Java 关键字）→ 编译报错。改成 `String`（已存在的类名）→ **也能编译通过**，但从此这个方法里的 `String` 指的是你的类型变量，不再是 `java.lang.String`——这就是遮蔽，见实验 3。
>
> **验完记得改回 `T`。**

### 实验 2 · 看字母的变化怎么反映到 class 文件

接着实验 1，在改成 `Banana` 的状态下：

```bash
javap -v -p target/classes/com/ha/pr/flowwork/common/R.class | grep -A1 "ok"
```

`Signature` 会从

```
<T:Ljava/lang/Object;>(TT;)Lcom/ha/pr/flowwork/common/R<TT;>;
```

变成

```
<Banana:Ljava/lang/Object;>(TBanana;)Lcom/ha/pr/flowwork/common/R<TBanana;>;
```

**`TT;` 的第二个 T 跟着变成了 `Banana`，第一个 T 没变。** 4.3 里说的那件事，眼见为实。

### 实验 3 · 静态方法里的 `T` 和类上的 `T` 是两个东西 ⭐⭐ 本篇最反直觉

再看一遍你的 `R.java`：

```java
public class R<T> {                        // ← 这里声明了一个 T
    private T data;

    public static <T> R<T> ok(T data) {    // ← 这里又声明了一个 T
        ...
    }
}
```

**问题：这两个 `T` 是同一个吗？**

直觉答案是"是"。**正确答案是：完全无关的两个变量，只是恰好同名。**

**动手证：** 把 `ok` 方法开头的 `<T>` 删掉，只留 `public static R<T> ok(T data)`：

```bash
./mvnw -q compile
```

报错：

```
non-static type variable T cannot be referenced from a static context
```

**为什么？** 类上的 `T` 是**实例**的类型参数——`new R<String>()` 时才被绑定成 `String`。而 `static` 方法不属于任何实例，调用 `R.ok(...)` 时压根没有实例，也就没有任何东西能告诉它 `T` 是什么。**所以静态方法必须自带一个类型参数。**

它自带的这个 `T`，**遮蔽（shadow）了类上的 `T`**，就像方法里的局部变量 `int data` 会遮蔽字段 `this.data` 一样。

> 💡 **实验 3 的推论**：`R.java` 里其实存在 **5 个互不相干的 `T`** —— 类上 1 个，`ok(T)` / `ok()` / `fail(String)` / `fail(int,String)` 各 1 个。它们同名纯属命名习惯，改成 `<A>`、`<B>`、`<C>`、`<D>` 编译一样过。
>
> 这也解释了为什么 `R.ok(null)` 能塞给任何返回类型——那个 `T` 是**每次调用**独立推断的，和 `R<T>` 的 T 没有绑定关系。

## 六、常见误解速查

| 误解 | 实际 |
|---|---|
| `T`、`E`、`K`、`V` 是关键字 | 普通标识符，改成任何合法名字都能编译（实验 1） |
| `T` 是某种"万能类型" | `T` 是**类型的变量**，不是类型本身 |
| 泛型方法只能传值实参 | 每次调用都同时传了**类型实参**，只是通常由编译器推断、你没写（`R.<SysUserVO>ok(vo)` 是合法的） |
| `class R<T>` 里的 T 到处通用 | `static` 方法**用不了**类上的 `T`，必须自己再声明一个（实验 3） |
| `Signature` 里的 `TT;` 是笔误 | 第一个 T 是"类型变量"记号，第二个才是名字。`TE;` = 变量 E |
| `L` 开头一定是引用类型 | 单独的 `J` 才是 long，`L` 后面必须跟类名和分号 |
| 一个冒号和两个冒号是随便写的 | 一个 = 类上界，两个 = 接口上界 |
| 看到复杂签名只能硬记 | 四步法：**圈声明点 → 认具体类型 → 看边界 → 代入真实类型读一遍**。第四步最管用 |

## 七、回到本项目

| 位置 | 字母 | 是声明还是使用 | 说明 |
|---|---|---|---|
| `R.java:6` `public class R<T>` | `T` | **声明** | 实例级，`new R<String>()` 时绑定 |
| `R.java:9` `private T data` | `T` | 使用 | 引用上面那个 |
| `R.java:11` `public static <T> R<T> ok(T data)` | `T` | **声明**（新的） | ⚠️ 和 `:6` 的 T **无关**，遮蔽了它 |
| `SystemUserMapper.java:7` `extends BaseMapper<SysUser>` | — | 使用 | 继承时把类型实参**钉死**成 `SysUser`，接口体是空的却白捡二十几个带类型的方法 |
| `SystemUserServiceImpl.java:32` `new Page<>(current, size)` | — | 使用 | `<>` 菱形推断：类型实参从左边的声明抄过来 |
| `09` 文档 `private <E> IPage<..> toPage(Query<?, E> query, ...)` | `E` | **声明** | 名字随便起，叫 `<E>` 是因为它代表"查出来的元素" |
| 同上 `Function<E, ProcessInstanceVO> mapper` | `E` | 使用 | 第二个位置**不能写 `R`**——`R` 是你的类名，会撞（见 3.3） |

### 一个可以现在就做的小练习

不看答案，读出这一行是什么意思：

```java
IPage<SysUserVO> voPage = entityPage.convert(SysUserVO::of);
```

<details>
<summary>答案</summary>

`IPage` 上的方法签名是 `<R> IPage<R> convert(Function<? super T, ? extends R> mapper)`。

四步法：
1. 声明点是 `<R>`，所以 `R` 是变量；`IPage`、`Function` 是具体类型
2. `T` 是 `IPage<T>` 类上的变量，此处已被 `entityPage` 绑定为 `SysUser`
3. 无显式边界
4. 代入：`R` 由 `SysUserVO::of` 的返回类型推断为 `SysUserVO` → 整个方法变成
   `IPage<SysUserVO> convert(Function<? super SysUser, ? extends SysUserVO> mapper)`

⚠️ 注意这里的 `R` 又是一个类型变量，和你的 `com.ha.pr.flowwork.common.R` 毫无关系——MyBatis-Plus 的作者当然不知道你有个类叫 R。**这正是 3.3 那个撞车问题的一般形态。**

（`? super` / `? extends` 留给 `06` 篇。）
</details>

## 八、一句话总结

那些字母**不是关键字，是你自己起名的「类型的变量」**；读任何泛型签名的第一步都是**分清哪里在声明变量、哪里在传实参**，然后**代入一个真实类型读一遍**——绝大多数唬人的签名到这一步就塌了。字母的语义（T/E/K/V/R/U）纯属历史习惯，代价是它们会和类名撞车，你项目里的 `R` 就是活例子。
