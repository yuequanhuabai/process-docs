# 01 · 没有泛型的世界

> **触发点**：`00` 篇 Q1、Q5——「泛型解决什么问题」「没有它行不行」。
>
> 本篇只走**横向轴**：旧写法 → 卡在哪 → 新方案为什么长这个形状 → 代价。
> 读完你应该能回答：**为什么 Java 泛型必须是「编译期擦掉」这个形状，而不能是别的形状。**
> 不涉及 `T`/`E` 怎么用（那是 `03`）、不涉及擦除的技术细节（那是 `02`）。

## 一、旧世界：Java 1.4 的集合长什么样

2004 年之前，Java 没有尖括号。所有集合装的都是 `Object`：

```java
// Java 1.4 —— 注意：没有任何 <> 
List list = new ArrayList();
list.add(new SysUser());
list.add("我是一个字符串");        // ← 编译器毫无意见

SysUser user = (SysUser) list.get(0);   // 取出来必须手工强转
```

三个特征，每一个都是后面痛点的来源：

1. **`List` 里存的是 `Object`**——什么都能放进去；
2. **取出来必须强转**——因为编译器只知道你拿到的是 `Object`；
3. **编译器无法阻止你放错东西**——第 3 行那个字符串，编译期一声不吭。

### 把你的代码退回 1.4 看看

`SystemUserServiceImpl.java:30-37` 现在长这样：

```java
// 今天（Java 17 + 泛型）
public IPage<SysUserVO> querySysUserPage(long current, long size) {
    Page<SysUser> page = new Page<>(current, size);
    LambdaQueryWrapper<SysUser> wrapper = new LambdaQueryWrapper<SysUser>()
            .orderByDesc(SysUser::getCreateTime);
    IPage<SysUser> entityPage = systemUserMapper.selectPage(page, wrapper);
    return entityPage.convert(SysUserVO::of);       // 一行搞定
}
```

退回 1.4，同样的事得这么写：

```java
// Java 1.4 —— 尖括号全部消失，强转和手工循环全部出现
public IPage querySysUserPage(long current, long size) {
    Page page = new Page(current, size);
    IPage entityPage = systemUserMapper.selectPage(page, wrapper);

    List records = entityPage.getRecords();         // 这个 List 里装的是什么？只有天知道
    List vos = new ArrayList();
    for (int i = 0; i < records.size(); i++) {
        SysUser user = (SysUser) records.get(i);    // ← 强转 #1
        vos.add(SysUserVO.of(user));
    }
    entityPage.setRecords(vos);
    return entityPage;
}
```

**注意消失的不只是尖括号**：`convert(SysUserVO::of)` 这种方法根本写不出来——它的存在依赖「我知道自己装的是 `SysUser`，转完变成 `SysUserVO`」，而 1.4 的类型系统表达不了这句话。

## 二、痛点：具体是什么让人写不下去

> 讲解规则要求：不说"不优雅"，要说清**卡在哪**。以下四条，一条比一条狠。

### 痛点 1 · 错误发现得太晚，而且指错凶手 ⭐ 最狠

```java
List list = new ArrayList();
list.add(new SysUser());        // A 处：某人在这里放了个 SysUser
// ……三个模块之外、三个月之后……
String s = (String) list.get(0); // B 处：💥 ClassCastException
```

`ClassCastException` 抛在 **B 处**，但 bug 在 **A 处**。堆栈指向的是**受害者，不是凶手**。

这才是真正的痛点——不是"要多写几个括号"，而是**排查成本**：一个集合可能被十几处代码填充，出错时你只知道"里面有个东西不是 String"，不知道是谁放的、什么时候放的。

> 💡 这个模式你今天还会撞上。上一轮我们发现的 `Collectors.toMap` 的 NPE 就是同一类：**报错的位置不是出错的位置**。区别在于泛型能治前者，null 治不了。

### 痛点 2 · 强转是噪音，而且是**不安全**的噪音

每次 `get` 都要写 `(SysUser)`。更糟的是：**编译器无法验证这个强转是否合理**。你写 `(String)` 它就信你，错了运行期再说。

也就是说，1.4 里的强转不是"告诉编译器"，是**"绕过编译器"**。

### 痛点 3 · API 无法自我描述

```java
public List getUsers();     // 返回的 List 里装什么？
```

只能靠方法名猜、靠 javadoc 写、靠口口相传。而且——**IDE 补全全废**：`records.get(i).` 后面弹出来的只有 `Object` 的那 11 个方法（`equals`/`hashCode`/`toString`…）。

**这条对日常效率的杀伤，其实比痛点 1 更持续。**

### 痛点 4 · 写不出「对任意类型都成立」的工具方法

想写一个通用的"取第一个元素"：

```java
// Java 1.4
public static Object first(List list) {
    return list.isEmpty() ? null : list.get(0);
}

// 调用方还得再转一次
SysUser u = (SysUser) first(userList);   // 强转又回来了
```

返回类型只能是 `Object`，类型信息在方法边界处**丢失**了。调用方明明知道自己传进去的是 `List<SysUser>`，但这个知识传不进去、也带不出来。

> ⚠️ **这一条直接通向泛型方法**（`04` 篇）。`toPage` 之所以需要 `<E>`，本质就是要解决"类型信息怎么从调用方带进方法、再带出来"。**先记住这个问题，`04` 篇会回来收。**

### 一个流传最广的历史例子：`compareTo`

1.4 的 `Comparable` 接口是这样的：

```java
public interface Comparable {
    int compareTo(Object o);      // 参数是 Object
}
```

于是**每一个**实现类都得在方法体第一行强转：

```java
public class SysUser implements Comparable {
    public int compareTo(Object o) {
        SysUser other = (SysUser) o;      // 每个 compareTo 都要来这么一遍
        return this.realName.compareTo(other.realName);
    }
}
```

泛型之后：

```java
public class SysUser implements Comparable<SysUser> {
    public int compareTo(SysUser other) {  // 强转消失了
        return this.realName.compareTo(other.realName);
    }
}
```

**这是"泛型消灭强转"最直观的一例**，也是当年推销泛型时最常用的例子。

## 三、新方案：为什么必须是「擦除」这个形状

泛型能做的事有很多种设计路线（`07` 篇会对比 C++ 和 C#）。Java 最终选了**擦除**，不是因为它最好，而是因为**三条硬约束把答案逼到了这里**。

### 约束 1 · 必须向后兼容（决定性的一条）

2004 年 Java 已经跑了 9 年，全世界有海量的 1.4 代码和**已经编译好的 class 文件**在生产环境上。

新特性不能让老代码编不过，更不能让老 class 跑不了。

### 约束 2 · 新旧必须能互相调用

不只是"老代码继续能跑"，还要**新代码能调老库、老库能吃新代码**：

- 你写的 `List<String>` 要能传给一个 1.4 老库里声明为 `void f(List)` 的方法；
- 老库返回的裸 `List`，你要能赋给 `List<String>`。

这条比约束 1 更狠——它要求新旧类型**在运行时是同一个东西**。

### 约束 3 · JVM 尽量别改

改字节码格式意味着所有 JVM 实现、所有字节码工具（调试器、profiler、AOP 框架）全部要跟着改。代价极高。

### 三条约束的交集 = 擦除

把三条摆在一起，答案几乎是唯一的：

> **让泛型只活在编译器里。编译时做检查、自动插入强转，编译完把尖括号擦掉。**

生成的 class 文件和 1.4 手写强转的版本**几乎一模一样**——于是：

- 老 JVM 认得（约束 3 ✅）
- 老库和新代码在运行时是同一个 `List`（约束 2 ✅）
- 老代码一个字不改继续编译（约束 1 ✅）

**"泛型是给编译器看的"这句话，就是从这里来的。** 它不是一句比喻，是设计事实。

> 📌 **技术细节留给 `02`**。这里只需要建立因果：**是兼容性逼出了擦除**，不是设计者偷懒。

### 历史线（谁做的）

| 年份 | 事件 |
|---|---|
| ~1997 | **Pizza** —— Martin Odersky 与 Philip Wadler 的研究项目，给 Java 加三样东西：泛型、高阶函数、模式匹配 |
| 1998 | 裁剪成 **GJ（Generic Java）**，只保留泛型，目标是**能编译成标准 JVM 字节码**。论文标题是 *"Making the future safe for the past"*——**「让未来对过去是安全的」，一句话就是整个设计的中心思想** |
| ~1999 | GJ 的编译器被 Sun 采纳，成了后来 `javac` 的基础 |
| 2004 | Java 5（JSR 14）正式引入泛型 |
| 2003→ | Odersky 转头做了 **Scala**——因为他想要的很多东西，在"必须兼容 Java 1.4"的约束下做不了 |

> 那篇论文的标题值得记住。你以后遇到 Java 里任何别扭的设计，先问一句「它在兼容什么」，八成能问出答案。

## 四、代价：换来了什么，丢了什么

擦除不是免费的。这些代价你今天全都还在承受：

| 代价 | 具体表现 | 展开于 |
|---|---|---|
| 运行时拿不到类型参数 | 不能 `new T[]`、不能 `x instanceof List<String>` | `05` |
| 基本类型不能泛型 | 没有 `List<int>`，只能 `List<Integer>`，白白装箱 | `05` |
| 某些重载会撞车 | `f(List<String>)` 和 `f(List<Integer>)` 不能共存——擦除后签名一样 | `05` |
| **裸类型至今合法** | `List list = new ArrayList();` 今天仍能编译，只给个 warning | 见下方实验 1 |

最后一条是**兼容性代价的活化石**：为了让 2004 年的老代码继续编译，"不写尖括号"这个口子必须永远留着。二十多年过去了，它还在。

## 五、动手实验

### 实验 1 · 证明"旧世界"至今还活着（有对照组，结果反直觉）

新建一个类粘进去跑：

```java
import java.util.*;

public class RawTypeDemo {
    public static void main(String[] args) {
        // 反例：裸类型 —— Java 1.4 的写法，今天仍然能编译（只有一个 warning）
        List raw = new ArrayList();
        raw.add("我是字符串");
        raw.add(123);                       // 不同类型混装，编译器一声不吭
        String s = (String) raw.get(1);     // 💥 运行期 ClassCastException
        System.out.println(s);
    }
}
```

```java
        // 正例：泛型
        List<String> typed = new ArrayList<>();
        typed.add("我是字符串");
        typed.add(123);                     // ❌ 编译期就红，根本跑不起来
```

**反直觉的点**：反例**能编译通过**。二十年前的写法在 Java 17 里依然合法——这就是"向后兼容"四个字的实物证据。

**对照要看的差异**：错误从「运行期第 6 行炸」提前到了「编译期第 3 行红」。这一句话就是泛型的全部价值。

### 实验 2 · 亲眼看见编译器替你插入的强转（接上 `02` 篇）

```java
import java.util.*;

public class ErasureDemo {
    public static void main(String[] args) {
        List<String> list = new ArrayList<>();
        String s = list.get(0);
    }
}
```

编译后反编译看字节码：

```bash
javac ErasureDemo.java
javap -c ErasureDemo
```

在 `main` 的字节码里找 `get` 那一行，你会看到紧跟着一条：

```
invokeinterface java/util/List.get:(I)Ljava/lang/Object;    ← 返回的是 Object！
checkcast       java/lang/String                            ← 编译器替你插的强转
```

**两个结论一次看清**：

1. `List.get` 在字节码层面**返回的仍然是 `Object`**——尖括号真的被擦掉了；
2. `(String)` 这个强转**没有消失，只是从你手里搬到了编译器手里**。

> 💡 **泛型没有"消灭"强转，只是把手写强转换成了编译器自动生成的、且保证正确的强转。** 这是 `01` 通向 `02` 的桥，记住这句话再进下一篇。

## 六、常见误解速查

| 误解 | 实际 |
|---|---|
| 泛型让代码跑得更快 | 无关。强转开销可忽略；字节码里 `checkcast` 一条不少 |
| 泛型消灭了强制转型 | 没有。只是从**你写**变成**编译器写**（实验 2 看得见） |
| Java 5 之前没法写通用容器 | 能写，装 `Object` 就行。问题是**不安全 + 不自描述**，不是写不出来 |
| 裸类型 `List list` 早就不能用了 | 今天仍然合法，只给 warning。这是兼容性的活化石 |
| Java 泛型抄的 C++ | 直接前身是 Odersky 等人的 GJ；与 C++ 模板同源但实现路线相反（`07` 篇） |
| 选擦除是设计者偷懒 | 是被"兼容 1.4 + 新旧互操作 + 别改 JVM"三条约束逼出来的唯一解 |

## 七、回到本项目

拿掉泛型，你今天写的这些全部要重写：

| 现在的代码 | 位置 | 1.4 里会变成什么 |
|---|---|---|
| `entityPage.convert(SysUserVO::of)` | `SystemUserServiceImpl.java:36` | **这个方法压根不存在**，要手写 for + 强转（本篇第一节） |
| `LambdaQueryWrapper<SysUser>` + `SysUser::getUsername` | `:33`、`:52-53` | 方法引用检查依赖类型参数，退化成手写字符串列名，拼错编译期发现不了 |
| `Map<String, String> nameMap` | `09` 文档的 `enrich()` | 每次 `get` 都要 `(String)`，且 key 放错类型编译器不管 |
| `R<T>` / `IPage<SysUserVO>` | `R.java:6`、`SystemUserService` | 只能是裸 `R` / 裸 `IPage`，Controller 拿到还得自己转一次 |

## 八、一句话总结

泛型不是让你**能做新的事**，是让**编译器替你挡住一类老错误**——把「运行期在受害者身上炸」提前到「编译期在凶手身上红」；而 Java 因为背着"必须兼容 1.4"的包袱，只能把这件事做在编译器层面，编译完就把类型擦掉。
