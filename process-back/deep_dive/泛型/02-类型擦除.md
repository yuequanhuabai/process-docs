# 02 · 类型擦除（本系列的分水岭）

> **触发点**：「泛型是针对编译器的设计吗？」+ `01` 篇实验 2 看到的那条 `checkcast`。
>
> 本篇是整个系列**最该花时间的一篇**。后面所有"怪现象"——不能 `new T[]`、不能 `instanceof List<String>`、两个重载会撞车——全都是从这一篇推出来的。
> 本篇全程用**你自己项目编译出来的 `R.class`** 当标本，输出是真的，不是我编的。

---

## 一、先纠一个误解（很重要）

> ❌ 「类型擦除 = 泛型信息在运行时全部丢失。」

**这是网上流传最广、也最误人的一句话。** 准确的说法是：

> ✅ **擦除擦掉的是「实例」身上的类型实参；「声明」处的泛型信息，大部分保留在 class 文件里。**

举例说明这个分界：

| 问题 | 答案 |
|---|---|
| 运行时能问出 `list` 这个**对象**里装的是 String 吗？ | ❌ **不能**。对象身上没有这个信息 |
| 运行时能问出 `R` 这个**类**声明了一个类型参数 `T` 吗？ | ✅ **能**。写在 class 文件的 `Signature` 属性里 |
| 运行时能问出 `R.data` 这个**字段**声明的类型是 `T` 吗？ | ✅ **能**。同上 |

**「声明」保留、「实例」不保留**——这一条是本篇的总钥匙，也是后面 Jackson、MyBatis、`TypeReference` 一切行为的解释。第四节会看到实证。

---

## 二、擦除具体做了什么（三件事）

编译器在生成字节码时做三件事：

### ① 把类型参数替换成它的上界

```java
class R<T>               { private T data; }        // 无界 → 擦成 Object
class Box<T extends Number> { private T value; }     // 有界 → 擦成 Number
```

擦除后大致等价于：

```java
class R   { private Object data; }
class Box { private Number value; }
```

> 💡 **"无界就是 Object"**——因为 `<T>` 其实是 `<T extends Object>` 的简写。你在 `javap` 里会**真的看见**这个补全（下一节）。

### ② 在必要的地方插入 `checkcast`

就是 `01` 篇实验 2 看到的那条。**手写强转没消失，只是搬给了编译器。**

### ③ 生成桥接方法（bridge method）

为了让继承+泛型的场景下多态还能正常工作，编译器会偷偷多生成一个方法。**这一条留给 `05` 篇**，现在只需要知道"有这么个东西"。

## 三、拿你自己的 `R.class` 看（真实输出）

`R.java` 源码是这样的：

```java
public class R<T> {
    private int code;
    private String msg;
    private T data;

    public static <T> R<T> ok(T data) { ... }
}
```

### 证据 1 · 字段和方法的**描述符**被擦成了 `Object`

```bash
javap -v -p target/classes/com/ha/pr/flowwork/common/R.class
```

常量池里的真实输出：

```
#11 = Methodref  #1.#12   // R.setData:(Ljava/lang/Object;)V
#40 = Fieldref   #1.#41   // R.data:Ljava/lang/Object;
```

**`setData` 的参数类型、`data` 字段的类型，在字节码层面都是 `Object`。** `T` 不见了——这就是"擦除"。

### 证据 2 · 但**声明**的泛型信息保留在 `Signature` 属性里

同一份输出里还有：

```
public class com.ha.pr.flowwork.common.R<T extends java.lang.Object>
                                          ↑ 注意：javap 把 <T> 补全成了 <T extends Object>

  private T data;
    Signature: #71     // TT;
                          ↑ "TT;" 是 JVM 签名语法，意思是"类型变量 T"

  public static <T> R<T> ok(T);
    Signature: #80     // <T:Ljava/lang/Object;>(TT;)Lcom/ha/pr/flowwork/common/R<TT;>;
```

**看最后那一行**——`ok` 方法的完整泛型签名**一个字都没丢**：有一个类型参数 `T`（上界 `Object`），吃一个 `T`，返回 `R<T>`。

### 结论

**同一份 class 文件里，同一个 `data` 字段有两套类型信息：**

| | 内容 | 谁用它 |
|---|---|---|
| **描述符**（Descriptor） | `Ljava/lang/Object;` | **JVM 执行时用**——它只认这个 |
| **签名**（Signature 属性） | `TT;` | **编译器和反射用**——JVM 执行时忽略 |

这就是"擦除"的真相：**不是删掉，是降级成 JVM 看得懂的形式，同时把原文另存一份给编译器**。

> 📌 这也解释了为什么泛型**不影响性能**：JVM 从头到尾只看描述符，`Signature` 属性对它就是一段注释。

---

## 四、正式回答：「它是针对编译器的设计吗？」

**是，但需要说得更准。** 三句话：

1. **类型检查 100% 在编译期**。运行时没有任何泛型检查——`checkcast` 检查的是擦除后的类型，不是 `List<String>`。
2. **类型信息在运行时保留「声明」、不保留「实例」**（第一节那张表）。
3. **JVM 完全不认识泛型**。字节码指令集里没有一条和泛型有关。`Signature` 属性对 JVM 而言是可以整段跳过的元数据。

所以更精确的表述是：

> **泛型是一层「编译期的类型协议」，编译完把协议原文存进 class 文件供工具查阅，但真正执行的字节码里，协议已经被降级成 `Object` + `checkcast`。**

---

## 五、为什么必须这么设计（接 `01` 的三条约束）

`01` 篇给了三条硬约束（兼容 1.4 / 新旧互操作 / 别改 JVM）。这里补上技术层面的决定性一条：

### 迁移兼容性：新旧必须是**同一个类**

设想不擦除的方案：`List<String>` 和 `List<Integer>` 在运行时是两个不同的类（C# 就是这么干的）。那么——

- 1.4 老代码里的裸 `List` 是**哪一个**？
- 老库的方法 `void f(List)`，新代码传 `List<String>` 进去，类型对得上吗？
- 整个 JDK 集合库要不要出两套？

**唯一能让老代码一个字不改继续跑的答案，就是让它们在运行时是同一个 `java.util.List`。** 而这必然意味着：类型实参在运行时不存在。

> 这就是 GJ 论文标题 *"Making the future safe for the past"* 的具体落地。**擦除是兼容性的代价，不是技术偏好。**

### 前瞻：Java 正在试图部分补救

**Project Valhalla** 是 OpenJDK 的长期项目，目标之一就是"特化泛型"（让 `List<int>` 成为可能，避免装箱）。它难产多年，难就难在**要在不破坏擦除语义的前提下**加特化。

**知道这件事的意义**：擦除的代价是真实的、被官方承认的，只是历史包袱太重、二十年也没还完。

## 六、动手实验

### 实验 1 · 两个不同泛型的对象，`getClass()` 相等（反直觉）

```java
import java.util.*;

public class ErasureDemo1 {
    public static void main(String[] args) {
        List<String>  a = new ArrayList<>();
        List<Integer> b = new ArrayList<>();

        System.out.println(a.getClass());              // class java.util.ArrayList
        System.out.println(b.getClass());              // class java.util.ArrayList
        System.out.println(a.getClass() == b.getClass());   // true ← 就是这个 true
    }
}
```

**记忆点就在那个 `true`。** 你在源码里写的两个不同类型，运行时是**同一个类**。

顺带：`List<String>.class` 这个写法**语法上就不合法**——因为根本没有这么一个类。

### 实验 2 · 看你自己的 `R.class`（不用写任何代码）

```bash
cd process-back
javap -p target/classes/com/ha/pr/flowwork/common/R.class
```

看到 `public class com.ha.pr.flowwork.common.R<T>`——泛型还在。再看完整版：

```bash
javap -v -p target/classes/com/ha/pr/flowwork/common/R.class | grep -E "Signature|Ljava/lang/Object"
```

**对照着找两样东西**：`setData:(Ljava/lang/Object;)V`（擦了）和 `Signature: TT;`（留了）。**一个字段，两套类型信息**——这就是第三节那张表的实物。

### 实验 3 · 证明「声明保留、实例不保留」⭐ 本篇最关键的实验

```java
import java.lang.reflect.*;
import java.util.*;

public class ErasureDemo3 {
    // 一个普通的字段声明
    static List<String> field;

    // 一个匿名子类：注意 extends ArrayList<String>
    static class StringList extends ArrayList<String> {}

    public static void main(String[] args) throws Exception {
        // ✅ 能读到:字段的【声明】
        Field f = ErasureDemo3.class.getDeclaredField("field");
        System.out.println(f.getGenericType());
        // → java.util.List<java.lang.String>       类型实参读出来了！

        // ✅ 能读到:父类的【声明】
        Type sup = StringList.class.getGenericSuperclass();
        System.out.println(((ParameterizedType) sup).getActualTypeArguments()[0]);
        // → class java.lang.String                 也读出来了！

        // ❌ 读不到:【实例】
        List<String> instance = new ArrayList<>();
        System.out.println(instance.getClass());
        // → class java.util.ArrayList              String 呢？没了
        // 没有任何 API 能从 instance 这个对象问出 "String"
    }
}
```

**三个输出并排看**，"声明保留、实例不保留"这句话就再也忘不掉了。

> 💡 第二个输出（匿名子类能读出 `String`）**不是花絮，是重要伏笔**——第七节会看到 Jackson 的 `TypeReference` 就是靠这个技巧工作的。

## 七、回到本项目

### 7.1 你的 `R<T>` 在运行时是什么样

```java
return R.ok(vo);          // 编译期:R<SysUserVO>
                          // 运行时:一个 R 对象,data 字段是 Object,里面碰巧放着 SysUserVO
```

**序列化没问题**——Jackson 序列化时看的是 `data` 里**实际那个对象**，不需要泛型信息。所以你的接口返回一直很正常。

### 7.2 但反序列化会撞墙（迟早遇到）

哪天你写客户端调自己的接口：

```java
// ❌ 拿回来的 data 是 LinkedHashMap,不是 SysUserVO
R r = objectMapper.readValue(json, R.class);

// ❌ 这样写编译不过 —— 没有 R<SysUserVO>.class 这个东西
R<SysUserVO> r = objectMapper.readValue(json, R<SysUserVO>.class);

// ✅ 正确姿势:TypeReference
R<SysUserVO> r = objectMapper.readValue(json, new TypeReference<R<SysUserVO>>() {});
//                                                                            ↑ 注意这个 {}
```

**那个 `{}` 是关键**——它创建了一个**匿名子类**，于是 `R<SysUserVO>` 变成了这个匿名类的**父类声明**，而"声明是保留的"（实验 3 第二个输出）。Jackson 通过 `getGenericSuperclass()` 就能把 `SysUserVO` 读出来。

> **这是整篇最有实用价值的一段**：`TypeReference` 那个空 `{}` 看着莫名其妙，其实是**绕过擦除的标准手法**——把类型信息从"实例"挪到"声明"里。Spring 的 `ParameterizedTypeReference`、Gson 的 `TypeToken` 全是同一个套路。

### 7.3 ⚠️ 一个必须分清的混淆

`toPage` 方法体里**不能**写 `list.stream().map(ProcessInstanceVO::of)`——

**这不是擦除造成的**，是**编译期重载决议**造成的（`E` 未知，编译器不知道选哪个重载）。两回事，别混。

擦除在 `toPage` 里造成的限制是另外两条：

```java
E[] arr = new E[10];              // ❌ 擦除:运行时不知道 E 是什么,没法创建数组
if (e instanceof ProcessInstance) // ⚠️ 能写,但这是在检查擦除后的类型,不是检查 E
```

**分清"编译期推断问题"和"运行期类型不存在问题"**，是读懂泛型报错信息的前提。

## 八、常见误解速查

| 误解 | 实际 |
|---|---|
| 擦除 = 泛型信息全丢 | 只丢**实例**的类型实参；**声明**保留在 `Signature` 属性里 |
| `List<String>` 和 `List<Integer>` 是两个类 | 运行时是同一个 `ArrayList`（实验 1 的 `true`） |
| 有 `List<String>.class` 这种写法 | 没有，语法就不合法 |
| 泛型有运行时开销 | 没有。JVM 只看描述符，`Signature` 属性它整段跳过 |
| 反射拿不到任何泛型信息 | 拿得到——`getGenericType()` / `getGenericSuperclass()`，只要它来自**声明** |
| `TypeReference<X>(){}` 的 `{}` 是可选的 | **必须有**。没有 `{}` 就没有匿名子类，就没有可读的父类声明 |
| 选擦除是设计者偷懒 | 是"新旧必须是同一个类"逼出来的唯一解 |
| `toPage` 里不能直接写 `::of` 是擦除导致的 | 不是。那是编译期重载决议问题（7.3） |

---

## 九、一句话总结

类型擦除 = **编译器把泛型降级成 `Object` + `checkcast` 交给 JVM 执行，同时把泛型原文另存进 `Signature` 属性供工具查阅**；所以「声明」处的泛型运行时读得到、「实例」身上的读不到——这一条分界，解释了从 `TypeReference` 的空 `{}` 到 `new T[]` 报错的全部现象。
