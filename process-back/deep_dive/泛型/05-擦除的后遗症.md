# 05 · 擦除的后遗症

> **触发点**：`04` 学会写泛型之后，写着写着就会撞墙——`new T()` 不行、`new T[]` 不行、`instanceof List<String>` 不行、两个长得不一样的重载居然报"名字冲突"。
> 本篇把这些坑一次收齐，**并且证明它们全是 `02` 那一条推出来的必然结果**，不是零散的规定。
>
> 另外收一个反向的东西：**桥接方法**——擦除唯一的"正面产物"，编译器偷偷替你打的补丁。

---

## 一、先纠一个误解

> **误解**：这些限制是 Java 设计得不好，只能一条条死记。

不是。**它们全部由 `02` 的一句话推出来**：

> **擦除擦掉的是「实例」身上的类型实参 —— 运行时，`T` 具体是什么已经不存在了。**

于是有一条**万能推导模板**：

> ### ⭐ 这个操作需要在**运行期**知道 `T` 到底是什么吗？
> ### 需要 → 一定不行。不需要 → 一定行。

本篇后面每一条，你都可以先自己用这个模板推一遍，再看答案。**推得出来就不用记了。**

---

## 二、纵向剥层：六条后遗症

> 下面的报错原文都是 **javac 17 实跑**出来的，不是我编的。
> 中文环境想看英文报错：`javac -J-Duser.language=en -J-Duser.country=US X.java`

### 后遗症 ① · 不能 `new T()`

```java
static <T> T create() { return new T(); }
```

```
error: unexpected type
  required: class
  found:    type parameter T
```

**为什么**：`new` 要在运行期找到具体的构造器。运行期 `T` 不存在，找谁的构造器？

**怎么绕**：把"怎么造"当参数传进来。

```java
static <T> T create(Supplier<T> factory) { return factory.get(); }
create(ArrayList::new);
```

> 💡 **这条就是 `toPage` 必须收 `mapper` 参数的根本原因**，见第七节。

### 后遗症 ② · 不能 `new T[n]`

```java
static <T> T[] make(int n) { return new T[n]; }
```

```
error: generic array creation
```

**为什么**：这条比 ① 更深，牵涉到**数组和泛型是两套哲学**——横向轴那节专讲（3.1）。

**怎么绕**：三条路，从好到差——

1. **改用 `List<T>`**（首选。你在业务代码里几乎永远该选这个）
2. 传一个 `T[]` 进来当模板：`toArray(T[] a)`（JDK 集合就是这么干的）
3. `(T[]) new Object[n]` + `@SuppressWarnings` —— 能过编译，**但只要把它 return 出去就可能在调用方炸 `ClassCastException`**。`ArrayList` 内部用的是这招，但它把数组藏得死死的从不外泄。

### 后遗症 ③ · 不能 `instanceof List<String>`

```java
boolean f(Object o) { return o instanceof List<String>; }
```

```
error: Object cannot be safely cast to List<String>
```

**为什么**：`instanceof` 是运行期检查。运行期只有一个 `List`，`List<String>` 和 `List<Integer>` 是**同一个类**（`02` 实验 1 已经验过 `getClass()` 相等）。

**能写什么**：

```java
o instanceof List           // ✅ raw，能过（有警告）
o instanceof List<?>        // ✅ 推荐。「是个 List，元素类型我不问」
o instanceof List<String>   // ❌
```

> ⚠️ **强转也一样没检查**：`(List<String>) o` 能编译（只给 unchecked 警告），运行期**只检查是不是 List**，元素类型完全不管。所以强转成功不代表里面真是 String——`01` 篇那个"堆栈指向受害者不指向凶手"的老毛病，在泛型时代仍然从这个口子漏出来。

### 后遗症 ④ · 重载撞车

```java
void m(List<String> a) {}
void m(List<Integer> a) {}
```

```
error: name clash: m(List<Integer>) and m(List<String>) have the same erasure
```

**为什么**：擦除之后两个都是 `m(List)`，字节码层面是同一个方法。**JVM 装不下两个同名同签名的方法。**

**注意报错的位置**：不在调用处，**在定义处**。编译器在你写下第二个方法时就拦住了。

**怎么绕**：改名。`m(List<String>)` → `mStrings`。就这么朴素。

> 💡 这条在你项目里是**活雷**，见第七节 7.2。

### 后遗症 ⑤ · 不能 catch 泛型异常

```java
try { ... }
catch (T e) { ... }              // ❌ 编译不过
class MyEx<T> extends Exception  // ❌ 泛型类不能继承 Throwable
```

**为什么**：`catch` 的匹配发生在**运行期**——JVM 拿抛出的异常对象逐个比对 catch 块的类型。运行期 `T` 不存在，没法比对。

**能做的**：`throws T`（声明可以，因为那只是编译期的检查）。抛和接都不行。

### 后遗症 ⑥ · 基本类型不能当类型实参

```java
List<int> a;      // ❌
List<Integer> a;  // ✅
```

**为什么**：擦除后 `T` 被替换成它的上界，通常是 `Object`。而 `int` **不是** `Object` 的子类——Java 的基本类型压根不在对象体系里。

**代价是真金白银的**：`List<Integer>` 里存的是**一堆 Integer 对象的引用**，不是一片连续的 int。一百万个数字，比 `int[]` 多出上百万次装箱、多占好几倍内存、缓存局部性也差。

> 这是 `02` 提到的 **Project Valhalla** 想解决的正题之一（"specialized generics"，让 `List<int>` 真的存 int）。**喊了十年还没进正式版**，可见改起来有多难。

### ⚠️ 不属于本篇的一条：static 用不了类上的 `T`

`04` 讲过 `public static <T> R<T> ok(T data)` 必须自带 `<T>`。

**这条不是擦除造成的。** 原因是"静态方法没有实例，而类上的 `T` 依附于实例"——**纯粹的作用域问题，跟运行期有没有类型信息无关**。

> 就算 Java 明天改成 C# 那样的 reified 泛型，这条限制**依然存在**。
>
> 和 `02` §7.3 是同一条纪律：**分清"编译期作用域问题"和"运行期类型不存在问题"**。归错因，以后遇到新报错就推不出来了。

## 三、横向讲史

### 3.1 数组 vs 泛型：两套哲学撞车（解释后遗症 ②）

数组是 **Java 1.0** 就有的，泛型是 **1.5** 加的。中间隔了九年，设计取向正好相反：

| | 数组（1.0） | 泛型（1.5） |
|---|---|---|
| 子类型关系 | **协变**：`String[]` **是** `Object[]` | **不变**：`List<String>` **不是** `List<Object>` |
| 类型检查在哪 | **运行期**（存错了抛 `ArrayStoreException`） | **编译期** |
| 运行时记得元素类型吗 | **记得** | **不记得**（擦了） |

**数组之所以敢协变，是因为它运行时记得自己装什么**，存错了能当场拦下。你可以亲眼看见（实验 2）：

```java
Object[] arr = new String[1];   // 协变，合法
arr[0] = 42;                    // 编译通过！运行期 ArrayStoreException
```

**现在把两者叠在一起**：`new T[n]` 要造一个"运行时记得自己装 T"的数组，可 `T` 在运行时不存在。**两个前提直接矛盾**——所以这不是"Java 懒得支持"，是**逻辑上办不到**。

> 💡 顺带解释了一个常见困惑：**为什么泛型是"不变"的？**
> 因为它没有数组那道运行期防线。如果允许 `List<Object> l = stringList`，那 `l.add(42)` 就无人可拦，`ClassCastException` 会在很远的地方爆——正是泛型要消灭的东西。**协变的门票是运行期检查，泛型付不起。**
> （想要有限的协变怎么办 → `? extends`，`06` 篇。）

### 3.2 桥接方法：擦除唯一的"正面产物"

前六条都是"不能做什么"。**桥接方法反过来——是编译器偷偷替你补的一块**。

**问题是这样冒出来的。** 你写：

```java
public class Money implements Comparable<Money> {
    public int compareTo(Money other) { ... }
}
```

擦除之后，接口那边变成了 `compareTo(Object)`（因为 `Comparable<T>` 的 `T` 擦成 Object），而你的实现是 `compareTo(Money)`。

**JVM 判断"重写"看的是方法名 + 描述符，两者必须完全一致。**

```
接口要求：  compareTo(Ljava/lang/Object;)I
你实现的：  compareTo(LMoney;)I          ← 签名不同！
```

**在 JVM 眼里这根本不是重写，是两个不相干的方法。** 于是多态断了：

```java
Comparable c = new Money();
c.compareTo(x);      // 调到接口的 compareTo(Object) —— 你的实现根本没被调到
```

**Java 5 的处理**：编译器**自动生成**一个签名对得上的方法，方法体只做一件事——转个类型，转发给真正的实现。这就是**桥接方法（bridge method）**。

它长这样（实验 3 会亲眼看到）：

```java
public int compareTo(Object o) {     // 编译器生成，源码里没有
    return compareTo((Money) o);     // checkcast 后转发
}
```

**代价**：

- 每个实现泛型接口的类都会多出一些看不见的方法。`javap` 一看就是"我没写过这个"
- **反射会看见它们**——`getDeclaredMethods()` 返回的方法数比你写的多，且有重名的。用反射扫方法时必须过滤 `Method.isBridge()`，这是踩过的人才知道的坑
- 那个 `checkcast` 就是 `01` 篇说的"编译器替你插的强转"，只不过这次插在了一个你没写过的方法里。**传错类型时 `ClassCastException` 的堆栈会指向一个源码里不存在的行**

## 四、动手实验

> 用 `04` 建的那个临时目录就行，验完删掉。

### 实验 1 · 一次验完四条报错

四个独立小文件，分别 `javac`（**用中文环境的话加 `-J-Duser.language=en` 看英文报错**）：

```java
// E1.java —— 后遗症 ②
public class E1 { static <T> T[] make(int n) { return new T[n]; } }

// E2.java —— 后遗症 ④
import java.util.*;
public class E2 { void m(List<String> a) {} void m(List<Integer> a) {} }

// E3.java —— 后遗症 ③
import java.util.*;
public class E3 { boolean f(Object o) { return o instanceof List<String>; } }

// E4.java —— 后遗症 ①
public class E4 { static <T> T create() { return new T(); } }
```

对应报错（实跑结果）：

| 文件 | 报错 |
|---|---|
| E1 | `generic array creation` |
| E2 | `name clash: m(List<Integer>) and m(List<String>) have the same erasure` |
| E3 | `Object cannot be safely cast to List<String>` |
| E4 | `unexpected type / required: class / found: type parameter T` |

**每条报错先自己用第一节的模板推一遍**："这个操作运行期需要知道 T 吗？"

> **对照组**：把 E3 改成 `o instanceof List<?>` → 编译通过。**一个 `?` 的差别**，因为它不再追问元素类型。

### 实验 2 · 数组协变的活证据 ⭐ 反直觉

```java
public class E5 {
    public static void main(String[] args) {
        Object[] arr = new String[1];   // ① 编译通过（数组协变）
        arr[0] = 42;                    // ② 编译也通过！
    }
}
```

```bash
javac E5.java && java E5
```

```
Exception in thread "main" java.lang.ArrayStoreException: java.lang.Integer
```

**编译期一路绿灯，运行期才炸。** —— 这就是 3.1 说的"数组把检查放在运行期"。

**对照组（泛型的做法）：**

```java
List<Object> l = new ArrayList<String>();   // ❌ 编译就报错
```

**一个运行期拦、一个编译期拦。两种哲学的差别，两行代码就看清了。**

### 实验 3 · 亲眼看桥接方法 ⭐⭐ 本篇最值钱

**a) 零成本版——看 `String`（不用写任何代码）**

```bash
javap -p java.lang.String | grep compareTo
```

```
public int compareTo(java.lang.String);
public int compareToIgnoreCase(java.lang.String);
public int compareTo(java.lang.Object);      ← 这个 String 源码里没有
```

`String` 实现的是 `Comparable<String>`，源码里只有 `compareTo(String)`。**那个 `compareTo(Object)` 是编译器生成的桥。**

> 这正好接上 `01` 篇讲的历史：1.4 时代 `Comparable.compareTo(Object)` 是**真的**要你手写强转；泛型时代它还在，只不过退居幕后，由编译器代劳了。**旧世界并没有消失，只是被藏起来了。**

**b) 自己造一个，看得更清楚**

```java
// Money.java
public class Money implements Comparable<Money> {
    int cents;
    public int compareTo(Money other) { return Integer.compare(cents, other.cents); }
}
```

```bash
javac Money.java && javap -p Money.class
```

```
public class Money implements java.lang.Comparable<Money> {
  int cents;
  public Money();
  public int compareTo(Money);
  public int compareTo(java.lang.Object);     ← 你没写过这个
}
```

**再看它的标记和内容：**

```bash
javap -v -p Money.class | grep -A3 "compareTo(java.lang.Object)"
```

```
public int compareTo(java.lang.Object);
  descriptor: (Ljava/lang/Object;)I
  flags: (0x1041) ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
```

- **`ACC_BRIDGE`** = 这是桥接方法（`Method.isBridge()` 读的就是它）
- **`ACC_SYNTHETIC`** = 源码里没有，编译器造的

**最后看它干了什么：**

```bash
javap -c -p Money.class | sed -n '/compareTo(java.lang.Object)/,/^$/p'
```

```
public int compareTo(java.lang.Object);
  Code:
     0: aload_0
     1: aload_1
     2: checkcast     #8    // class Money       ← 强转
     5: invokevirtual #19   // Method compareTo:(LMoney;)I   ← 转发给你写的那个
     8: ireturn
```

**五条指令，整篇文章的话它全说完了**：转个类型，调你写的那个，返回。

> **"咦"就在这儿**：你源码里只有一个 `compareTo`，class 文件里有两个；多出来的那个里面藏着一个你没写过的 `checkcast`。

## 五、常见误解速查

| 误解 | 实际 |
|---|---|
| 这些限制得一条条背 | 一条模板全推得出来：**运行期需要知道 T 吗？需要就不行** |
| `new T[]` 不行是 Java 偷懒 | 逻辑上办不到：数组要求运行期记得元素类型，擦除保证了记不得（3.1） |
| `(List<String>) o` 强转会检查元素类型 | **不会**，只检查是不是 `List`。里面装什么完全不管 |
| `instanceof List<?>` 也不行 | 行。`?` 表示"不追问元素类型"，正是能过的原因 |
| 重载撞车会在调用时报错 | **在定义处**就报，你写下第二个方法时编译器就拦了 |
| `List<Integer>` 和 `int[]` 性能差不多 | 差很多：装箱 + 引用间接 + 缓存不友好。Valhalla 想治的就是这个 |
| static 用不了类的 `T` 是擦除害的 | **不是**。是"没有实例"的作用域问题，reified 泛型也一样不行 |
| 源码里几个方法，class 里就几个 | 实现泛型接口时编译器会**偷加桥接方法**；反射扫方法要用 `isBridge()` 过滤 |
| 数组和 List 的子类型规则一样 | 相反：数组**协变**，泛型**不变**。实验 2 两行代码看清 |

## 六、回到本项目

### 6.1 后遗症 ① 就是 `toPage` 必须收 `mapper` 的原因 ⭐

再看一眼签名：

```java
private <E> IPage<ProcessInstanceVO> toPage(Query<?, E> query,
                                            Function<E, ProcessInstanceVO> mapper,
                                            long current, long size)
```

**为什么不能让 `toPage` 自己把 `E` 转成 VO？** 因为它做不到——

- 想 `new ProcessInstanceVO(e)`？那要求 `toPage` 知道 `e` 到底是 `ProcessInstance` 还是 `HistoricProcessInstance`，才能挑对构造逻辑。**运行期 `E` 不存在**（后遗症 ①/③）
- 想 `if (e instanceof ProcessInstance)`？这条能编译（不带类型实参），但那就等于把泛型白写了——又退回 `01` 篇的 if-else 手工分派

**所以只剩一条路：把"怎么转"当成一个函数传进来。** 谁调用谁知道 `E` 是什么，就由谁负责提供转换逻辑：

```java
return toPage(query, ProcessInstanceVO::of, current, size);
//                   ↑ 调用方知道 E 是 ProcessInstance，所以它选得出正确的 of 重载
```

> **这就是 `04` §6.2 第 3 问的答案背后的原理。** `mapper` 不是为了"灵活"，是**擦除逼出来的唯一解**。

### 6.2 后遗症 ④ 是你项目里的一颗活雷 ⚠️

`ProcessInstanceServiceImpl` 里现在是两个不同名的方法：`page()` 和 `myStarted()`。

**假如哪天觉得"都是分页查询，不如重载成同名的"：**

```java
IPage<ProcessInstanceVO> page(ProcessInstanceQuery q, long c, long s)          // 想这么写
IPage<ProcessInstanceVO> page(HistoricProcessInstanceQuery q, long c, long s)  // 这个能行
```

这两个**能编译**（`ProcessInstanceQuery` 和 `HistoricProcessInstanceQuery` 是两个不同的接口，擦除后签名不同）。

**但下面这对就不行了：**

```java
IPage<..> page(Query<?, ProcessInstance> q, long c, long s)
IPage<..> page(Query<?, HistoricProcessInstance> q, long c, long s)   // ❌ name clash
```

擦除后两个都是 `page(Query, long, long)`。**判据：看擦除后的签名，不是看你写的签名。**

### 6.3 其它散点

| 位置 | 关联 |
|---|---|
| `enrich()` 里的 `Map<String, String>` | 后遗症 ⑥：key 是 userId，本可以是 `long`，但泛型只收对象，只能 `String`/`Long` |
| `R<T>` 反序列化要 `new TypeReference<R<SysUserVO>>() {}` | `02` §7.2，同一个根因 |
| `SystemUserMapper extends BaseMapper<SysUser>` | MyBatis-Plus 靠动态代理拿类型，**绕开擦除**用的是"继承时钉死类型实参"这一招——和 `TypeReference` 的 `{}` 是同一个原理（声明保留） |

## 七、一句话总结

擦除的所有后遗症共享同一个根因——**运行期 `T` 不存在**，所以凡是需要在运行期知道 `T` 的操作（`new T()`、`new T[]`、`instanceof T`、`catch T`）一律不行，凡是编译期就能决定的（`throws T`、`instanceof List<?>`）一律可以。重载撞车是同一枚硬币的另一面：擦除后签名相同，JVM 装不下。而**桥接方法是擦除唯一的正面产物**——编译器偷生成一个签名对得上的转发方法，把被擦除切断的多态重新接上，代价是 class 文件里多出你没写过的方法。**`toPage` 之所以必须收一个 `mapper`，正是后遗症 ① 的直接结果，不是风格选择。**
