# 06 · 通配符与边界（`?` 到底在说什么）

> **触发点**：`04` §6.2 推 `toPage` 签名时，唯一没解释的就是 `Query<?, E>` 里那个 `?`。
> `05` §3.1 末尾还欠了一笔账：**"泛型是不变的，那想要协变怎么办？"** —— 就在本篇结。
>
> 本篇讲完，`toPage` 的签名**每一个字符**你都能解释。`08` 只剩合起来重写一遍。

---

## 一、先纠两个误解

### 误解 1 · `?` 是「任意类型」，和 `T` 差不多

不是。两者的区别一句话说清：

> **`T` 是「我给这个类型起了个名字，因为后面还要提到它」。**
> **`?` 是「我不给它起名字，因为我根本不打算提到它」。**

```java
<E> IPage<..> toPage(Query<?, E> query, Function<E, ProcessInstanceVO> mapper, ...)
//                         ↑ ↑
//                         │ └── E 起了名，因为下一个参数还要用（Function<E,..>）
//                         └──── ? 没起名，因为 toPage 从头到尾没提过 query 是哪种 Query
```

**判据和 `04` 的作用域判据是一脉相承的**：

| 问 | 用什么 |
|---|---|
| 这个类型，签名或方法体的**别处还要提到**吗？ | 要 → 起名 `T`／`E`；不要 → `?` |

`?` 就是**匿名的类型参数**，仅此而已。

### 误解 2 · `List<?>` 和 `List<Object>` 差不多

**差得远，而且方向和直觉相反。**

```java
List<Object> a = ...;
a.add("abc");     // ✅ 能加
a.add(42);        // ✅ 能加

List<?> b = ...;
b.add("abc");     // ❌ 编译不过
b.add(42);        // ❌ 编译不过
b.add(null);      // ✅ 只有 null 能加
```

**`List<?>` 比 `List<Object>` 更"受限"，不是更宽松。** 为什么，看下一节。

## 二、纵向剥层

### 2.1 为什么 `List<?>` 不能 add ⭐ 本篇的地基

`List<?>` 的准确含义是：

> **"这是某一种确定类型的 List，但我不知道是哪一种。"**

注意是**某一种确定的**，不是"什么都能装的"。它可能是 `List<String>`，也可能是 `List<Integer>`——**编译器不知道**。

于是：

```java
List<?> b = getSomeList();   // 可能是 List<String>，也可能是 List<Integer>
b.add("abc");                // 如果它其实是 List<Integer> 呢？
```

编译器没法保证安全，**只能一律禁止**。`null` 是唯一例外——因为 `null` 对任何类型都合法。

**反过来，读是安全的：**

```java
Object o = b.get(0);   // ✅ 不管里面装什么，一定是 Object 的子类
String s = b.get(0);   // ❌ 不保证是 String
```

> **总结成一句**：`?` 让你**读得出 Object，写不进任何东西**。
> 这条是后面 `? extends` / `? super` 的母版。

### 2.2 `? extends X` —— 上界，只读

```java
List<? extends Number> list;   // "某种 Number 的 List，具体哪种不知道"
```

**能接受的实参变多了**（这正是它存在的意义）：

```java
List<? extends Number> l;
l = new ArrayList<Integer>();   // ✅
l = new ArrayList<Double>();    // ✅
l = new ArrayList<Number>();    // ✅
```

**读：变好了。**

```java
Number n = l.get(0);   // ✅ 不管是 Integer 还是 Double，一定是 Number
```

**写：还是不行。**

```java
l.add(1);        // ❌ 万一 l 其实是 List<Double> 呢？
l.add(1.0);      // ❌ 万一 l 其实是 List<Integer> 呢？
l.add(null);     // ✅ 老规矩
```

> **`? extends` = 我只从里面**拿**东西。**

### 2.3 `? super X` —— 下界，只写

```java
List<? super Integer> list;   // "某种 Integer 的父类型的 List"
```

**能接受的实参：**

```java
List<? super Integer> l;
l = new ArrayList<Integer>();   // ✅
l = new ArrayList<Number>();    // ✅
l = new ArrayList<Object>();    // ✅
l = new ArrayList<Double>();    // ❌ Double 不是 Integer 的父类
```

**写：可以了！**

```java
l.add(1);           // ✅ 不管它是 List<Integer>/List<Number>/List<Object>，装个 Integer 都合法
l.add(1.0);         // ❌ Double 不一定装得下
```

**读：退化了。**

```java
Object o = l.get(0);    // ✅ 只能保证是 Object
Integer i = l.get(0);   // ❌ 万一它是 List<Object>，里面可能是任何东西
```

> **`? super` = 我只往里面**放**东西。**

### 2.4 PECS

Joshua Bloch 在《Effective Java》里的助记：

> ## **P**roducer → **E**xtends，**C**onsumer → **S**uper

**站在"这个参数对我这个方法而言是干什么的"的角度：**

| 这个集合对我来说是 | 用 | 我能做 |
|---|---|---|
| **生产者**（我从它那儿**取**数据） | `? extends X` | 读，读出来是 `X` |
| **消费者**（我往它那儿**塞**数据） | `? super X` | 写，能写进 `X` |
| **两样都要** | **不用通配符**，直接 `X` | 读写都行，但接受的实参窄了 |
| **都不要**（只关心它存在） | `?` | 读出 Object |

**JDK 里的教科书例子：**

```java
public static <T> void copy(List<? super T> dest, List<? extends T> src)
//                                ↑ 消费者，我往它写      ↑ 生产者，我从它读
```

一个方法里两种都出现，语义完全对称。**这个签名读得懂，PECS 就过关了。**

### 2.5 ⚠️ 两个 `extends` 长得一样，含义完全不同

这是本篇最大的坑：

```java
<T extends Number> void a(List<T> list)       // ① 边界（bound）
void b(List<? extends Number> list)           // ② 通配符（wildcard）
```

| | ① `<T extends Number>` | ② `<? extends Number>` |
|---|---|---|
| 这是在干什么 | **声明**一个类型变量，并限制它的上界 | **传实参**，只是不说具体是哪个 |
| `T` / `?` 后面还能用吗 | 能，`T` 是有名字的 | 不能，没名字 |
| 能往 list 里 add 吗 | **能**（`list.add(t)`，t 是 T） | **不能** |
| 什么时候用 | 需要在别处提到这个类型 | 只是想放宽入参 |

**记忆锚点（回到 `03` 的判据）**：

> **`<...>` 出现在方法/类的声明区里 → 那是①，在声明变量。**
> **`?` 出现在参数类型内部 → 那是②，在传实参。**

### 2.6 自限定泛型：`Query<T extends Query<?, ?>, U>`

终于到 Flowable 那个签名了。**这是 `javap` 实跑的真实声明（Flowable 7.1.0）：**

```java
public interface Query<T extends Query<?, ?>, U> {
    T asc();
    T desc();
    T orderBy(QueryProperty p);
    long count();
    U singleResult();
    List<U> list();
    List<U> listPage(int firstResult, int maxResults);
}
```

**先按 `03` 的四步法拆：**

1. **声明点**：`interface Query<...>` 后面，声明了 `T` 和 `U`
2. **具体类型**：`Query` 是它自己
3. **边界**：`T extends Query<?, ?>` —— T 必须是个 Query（里面两个 `?` 是"我不关心它的两个参数是什么"）
4. **代入真实类型** ⭐ —— javap 实跑：

```java
interface ProcessInstanceQuery
        extends Query<ProcessInstanceQuery, ProcessInstance>
//                    └─ T = 我自己 ─┘      └─ U = 我查出的东西 ─┘

interface HistoricProcessInstanceQuery
        extends Query<HistoricProcessInstanceQuery, HistoricProcessInstance>, ...
```

代入后，父接口的方法变成：

```java
// 对 ProcessInstanceQuery 而言
ProcessInstanceQuery asc();
List<ProcessInstance> listPage(int, int);

// 对 HistoricProcessInstanceQuery 而言
HistoricProcessInstanceQuery asc();
List<HistoricProcessInstance> listPage(int, int);
```

#### 为什么要让类型参数指向自己

**因为链式调用要跨过继承边界。** 假如父接口老老实实写 `Query asc()`：

```java
runtimeService.createProcessInstanceQuery()
        .processInstanceId("x")   // 子接口的方法，返回 ProcessInstanceQuery ✅
        .asc()                    // 父接口的方法，返回 Query ← 退化了
        .processInstanceId("y")   // ❌ 编译不过，Query 上没有这个方法
```

**链子在调到父接口方法的那一刻断掉。** 让 `T` 指向"实现者自己"，父接口的方法就能返回子类型：

```java
        .asc()                    // 返回 ProcessInstanceQuery ✅ 链子接上了
```

> 这个套路的学术名叫 **F-bounded polymorphism**，C++ 圈叫 **CRTP**。
> Java 标准库里的活例子：`enum E extends Enum<E>`、`class Builder<T extends Builder<T>>`。
> **凡是"父类的方法要返回子类类型"的场景，都是它。**

#### 那两个 `?` 是干嘛的

`T extends Query<?, ?>` 里的两个 `?`：**约束"T 必须是个 Query"就够了，至于那个 Query 自己的两个参数是什么，这里不关心。**

写成 `T extends Query<T, U>` 理论上更精确，但会把约束绷得太死（`HistoricProcessInstanceQuery` 还同时继承了 `DeleteQuery` 等好几个接口）。**这是设计上的松紧取舍——松一点，换来更多实现方式。**

## 三、横向讲史

### 3.1 旧世界：Java 5 刚有泛型，通配符还没来

泛型是**不变**的（`05` §3.1），于是第一天就撞墙：

```java
void printAll(List<Object> list) { for (Object o : list) System.out.println(o); }

printAll(new ArrayList<String>());   // ❌ 编译不过！
```

**痛点具体在哪**：`printAll` 只是**读**，读出来当 Object 用，逻辑上百分之百安全。但类型系统不让传。

**当时的绕法**（够难看的）：

- 用 raw type：`void printAll(List list)` —— 退回 `01` 篇的老路，全部警告
- 每个类型抄一份：`printAllStrings` / `printAllIntegers` —— 抄到死

**根子在**：不变是为了安全（`05` §3.1 讲过，允许 `List<Object> = stringList` 就拦不住 `add(42)`）。**但"只读"的场景其实不需要那道防线。**

### 3.2 新方案：把"我只读"这件事写进类型里

通配符的设计就是**让调用方声明自己的意图**：

```java
void printAll(List<?> list)                       // 我只读，不写
void sum(List<? extends Number> list)             // 我只读，且读出来当 Number 用
void fill(List<? super Integer> list)             // 我只写 Integer
```

**说了"我只读"，编译器就能放宽入参；作为交换，它禁止你写。** 这笔交易非常直白。

> 学名叫 **use-site variance**（使用点型变）——型变规则写在**用的地方**（每个方法签名里）。

### 3.3 对照组：Kotlin / Scala 走的是另一条路

它们用 **declaration-site variance**（声明点型变）——在**类声明**时一次说清：

```kotlin
interface List<out T>      // out = 只产出 T，天然协变
interface Consumer<in T>   // in  = 只消费 T，天然逆变
```

之后 `List<String>` **自动**就是 `List<Any>` 的子类型，**调用方一个符号都不用写**。

| | Java（use-site） | Kotlin（declaration-site） |
|---|---|---|
| 型变写在哪 | 每个用到的方法签名里 | 类型声明处，一次 |
| 调用方负担 | 要懂 `? extends`/`? super` | 无感 |
| 灵活度 | 高（同一个类可以这儿协变那儿逆变） | 低一些 |
| 签名可读性 | 差（`? extends` 满天飞） | 好 |

**Java 为什么不走 Kotlin 那条路？——又是兼容性。** `List<T>` 在 1.2 就存在了，泛型化时**不能改它的声明**（改了所有旧代码全废）。**只能在使用处补救。**

> `01` → `02` → 本篇，同一条线索第三次出现：**Java 泛型所有别扭的地方，追到底都是"不能破坏 1.4 的旧代码"。**

### 3.4 代价

- **签名变丑**：`copy(List<? super T> dest, List<? extends T> src)` 这种东西劝退了整整一代人
- **理解成本转嫁给调用方**：Kotlin 用户不需要知道型变，Java 用户必须知道
- **捕获转换（capture）报错极其难懂**：`capture of ? extends Number` 这类报错，不懂原理根本读不下去

## 四、动手实验

### 实验 1 · `List<?>` 写不进去 ⭐ 必做

```java
import java.util.*;
public class W1 {
    public static void main(String[] args) {
        List<String> src = new ArrayList<>(List.of("a"));

        List<?> a = src;
        Object o = a.get(0);   // ① ✅ 读得出 Object
        a.add("b");            // ② ❌ 注释掉才能编译

        List<Object> b = src;  // ③ ❌ 这行也过不了！
    }
}
```

**三个观察点：**

- ① 通过——`?` 读得出 Object
- ② 报错 `no suitable method found for add(String)` —— **明明装的就是 String 也不让加**，因为编译器不知道
- ③ 报错 `incompatible types` —— **这就是"泛型不变"**。想传进只读方法，必须用 `?`

> **对照组**：把 `List<?> a` 改成 `List<Object> a` → ② 通过但 ③ 依然报错；把 `List<String> src` 改成 `List<Object> src` → ③ 通过。**三种组合各试一次，"不变"就刻进去了。**

### 实验 2 · PECS 两边各撞一次

```java
import java.util.*;
public class W2 {
    static double sum(List<? extends Number> src) {      // 生产者
        double t = 0;
        for (Number n : src) t += n.doubleValue();       // ① ✅ 读
        // src.add(1);                                   // ② ❌ 打开试试
        return t;
    }
    static void fill(List<? super Integer> dest) {       // 消费者
        dest.add(1);                                     // ③ ✅ 写
        // Integer x = dest.get(0);                      // ④ ❌ 打开试试
        Object x = dest.get(0);                          // ⑤ ✅ 只能读出 Object
    }
    public static void main(String[] args) {
        System.out.println(sum(List.of(1, 2.5)));        // Integer/Double 混着传都行
        fill(new ArrayList<Number>());                   // 传 Number 的 List 也行
    }
}
```

把 ② 和 ④ 依次打开，看两个方向的报错。**`extends` 挡写、`super` 挡读——完全对称。**

### 实验 3 · 自限定泛型断链现场 ⭐⭐ 最能说明问题

**a) 先看正常的（用你项目里的 Flowable）**

在 `ProcessInstanceServiceImpl` 里随便找个地方写一行，看它编译过不过：

```java
runtimeService.createProcessInstanceQuery()
        .processInstanceId("x")     // 子接口方法
        .desc()                     // ← 父接口 Query 的方法
        .processInstanceId("y");    // ← 还能接着调子接口方法？
```

**能编译。** 因为 `desc()` 声明的返回类型是 `T`，而 `ProcessInstanceQuery extends Query<ProcessInstanceQuery, ...>` 把 `T` 钉成了它自己。

**b) 手写一个"没有自限定"的版本，看链子怎么断**

```java
public class W3 {
    // 没有自限定：父类方法返回父类型
    static class BaseBuilder {
        BaseBuilder common() { return this; }
    }
    static class MyBuilder extends BaseBuilder {
        MyBuilder special() { return this; }
    }
    public static void main(String[] args) {
        new MyBuilder().special().common().special();   // ❌ 编译不过
        //                        ↑ 返回 BaseBuilder，上面没有 special()
    }
}
```

报错：`cannot find symbol: method special()`。**这就是断链现场。**

**c) 加上自限定，链子接上**

```java
static class BaseBuilder<T extends BaseBuilder<T>> {
    @SuppressWarnings("unchecked")
    T common() { return (T) this; }
}
static class MyBuilder extends BaseBuilder<MyBuilder> {   // ← T = 自己
    MyBuilder special() { return this; }
}
// 现在这行能编译了：
new MyBuilder().special().common().special();
```

> 💡 注意 `common()` 里那个 `(T) this` 强转和 `@SuppressWarnings` —— **自限定泛型有个洗不掉的污点**：编译器没法证明 `this` 真的是 `T`（理论上有人能写 `class Evil extends BaseBuilder<MyBuilder>`）。**Flowable 的实现类内部也是这么强转的。**
>
> 这是"设计自己的泛型"时会遇到的真实取舍：**为了 API 好用，内部吞一个 unchecked 警告。**

## 五、常见误解速查

| 误解 | 实际 |
|---|---|
| `?` 和 `T` 差不多 | `T` 有名字（后面还要用），`?` 没名字（用完就扔）。判据同 `04` |
| `List<?>` ≈ `List<Object>` | `List<Object>` 能 add，`List<?>` 只能 add(null)。`?` 更**受限** |
| `List<?>` 是"能装任意类型的 List" | 是"**某一种确定类型**的 List，但不知道是哪种"。差别就在这儿 |
| `? extends` 让集合更灵活所以能随便写 | 恰恰相反，**它禁止写**。放宽的是"能传什么进来" |
| `? super` 能读出原类型 | 只能读出 `Object` |
| `<T extends X>` 和 `<? extends X>` 是一回事 | 完全不同：前者**声明变量**（能写入），后者**传实参**（不能写入）。见 2.5 |
| PECS 里的"生产/消费"是站在集合角度 | 站在**你这个方法**角度：方法从它取 = 生产者 |
| `T extends Query<?,?>` 里的 `?` 很神秘 | 就是"我不关心那两个参数"。约束到"是个 Query"就够了 |
| 自限定泛型是炫技 | 是**唯一**能让父类方法返回子类型的办法，否则链式调用必断（实验 3） |

## 六、回到本项目

### 6.1 `toPage` 签名逐字符读完

```java
private <E> IPage<ProcessInstanceVO> toPage(Query<?, E> query,
                                            Function<E, ProcessInstanceVO> mapper,
                                            long current, long size)
```

| 片段 | 读作 | 出处 |
|---|---|---|
| `<E>` | 声明一个方法级类型变量 E | `03` 声明点 / `04` 四问判据第 4 条 |
| `Query<?, E>` 的 `?` | "第一个参数是什么我不关心" —— `toPage` 只调 `count()`/`listPage()`，从不需要返回自身类型 | 本篇 2.1 |
| `Query<?, E>` 的 `E` | "查出来的元素类型"，起了名因为下一行还要用 | 本篇 2.6（U 的位置） |
| `Function<E, ProcessInstanceVO>` | 怎么把 E 变成 VO —— **必须传进来，因为 `toPage` 不能 `new E()`** | `05` §6.1 |
| 第二个位置写死 `ProcessInstanceVO` 而不是 `R` | `R` 是你的响应类，会撞名 | `03` §3.3 |
| 整个 `<E>` 在方法上不在类上 | 没字段用、非 static、单方法独占 | `04` §2.2 |

**每一个字符都有出处了。** 这就是 `00` 说的"三样拆开，每一样都不难"。

### 6.2 那个 `?` 换成 `T` 行不行？

```java
private <T extends Query<?,?>, E> IPage<..> toPage(Query<T, E> query, ...)
```

**能编译，但没有任何好处**——`toPage` 方法体里从头到尾没提过 `T`，白多一个类型参数，调用方还得多推一个类型。

> **这正好是 `08` 篇那条纪律的预演**：**能用 `?` 就别起名字。** 起名字是有成本的（读的人要跟踪它），只在真要用时才起。

### 6.3 项目里其它通配符

| 位置 | 通配符 | 说明 |
|---|---|---|
| `IPage.convert` 的 `Function<? super T, ? extends R>` | 两个都有 | 标准 PECS：入参位置 `? super T`（消费 T），出参位置 `? extends R`（生产 R）。`SystemUserServiceImpl.java:36` 调的就是它 |
| `Comparator.comparing(...)` | `Function<? super T, ? extends U>` | `FlowableHistoryServiceImpl.java:53` 排序时用到，同一个模式 |
| Flowable `Query<T extends Query<?,?>, U>` | 自限定 + `?` | 本篇 2.6 |

> 💡 **看出规律了吗**：`Function` 作为参数出现时，几乎总是写成 `Function<? super T, ? extends R>`。因为**函数的入参位置是消费者、出参位置是生产者**——PECS 在函数式接口上的固定形态。你自己写 `Function` 参数时照抄这个形状就对了。

## 七、一句话总结

`?` 是**匿名的类型参数**——不起名，因为不打算再提它；代价是**读得出 Object，写不进任何东西**。`? extends` 放宽入参、只准读（生产者），`? super` 放宽入参、只准写（消费者），合起来就是 PECS。它们存在的唯一理由是**泛型不变**（`05` §3.1）挡住了那些逻辑上安全的调用，而 Java 因为不能改 `List<T>` 的既有声明，只能走"使用点型变"这条更丑的路。自限定泛型 `T extends Query<?,?>` 则是另一回事——**让父接口的方法返回子类型，否则链式调用一碰到父接口方法就断。** 至此 `toPage` 签名的每个字符都有出处了。
