# 00 · Java 泛型全景（宏观篇）

> **触发点**（2026-07-31）：读 `toPage(Query<?, E> query, Function<E, ProcessInstanceVO> mapper, ...)` 时卡住，确认根因不是这个方法，而是**泛型基础一直没打牢**——此前的用法只有 `List<User> list = new ArrayList<>()` 这一种。
>
> 本篇是**宏观层**：只给地图、结论和分篇计划，**不展开原理**。每个问题的完整剥层在后续分篇里。
> 读法：本篇读完你应该知道「泛型一共有几块、我在哪、还差什么」，而不是「我全懂了」。

---

## 一、先给一句话定位

> **泛型是给编译器看的类型标注。它把「运行期才会炸的 `ClassCastException`」提前到「编译期就报红」，代价是这些标注在编译完成后基本被擦掉了。**

这句话里有三个词后面每一篇都会回来：**编译器**、**提前**、**擦掉**。

---

## 二、你现在在哪（三档地图）

泛型的使用者分三档，难度台阶很陡：

| 档 | 干什么 | 长什么样 | 你的状态 |
|---|---|---|---|
| **① 被动使用者** | 用别人写好的泛型类，填一个具体类型进去 | `List<User>`、`Page<SysUser>` | ✅ 熟练 |
| **② 泛型方法作者** | 自己写带类型参数的方法 | `static <T> R<T> ok(T data)`、`<E> IPage<..> toPage(...)` | 🔄 **能读懂一点，但写不出来**——本系列的靶心 |
| **③ 泛型类/接口作者** | 设计带类型参数的类型，还要考虑边界、通配符、自引用 | `class R<T>`、`interface Query<T extends Query<?,?>, U>` | ⬜ **本系列的终点**（2026-07-31 上调） |

### 目标定在 ③（2026-07-31 修订）

原本写的是「② 走稳即可，③ 只需读懂别人写的」。**这个定位站不住，两个理由**：

1. **本篇自己就矛盾**——第七节的验收标准是「合上文档能写出 `R<T>`」，而 `R<T>` 是泛型**类**，写它就是 ③。
2. **更本质的**：读 `List<User>` 不需要懂设计，但读 `Query<T extends Query<?,?>, U>` 这种，**不知道「为什么有人要让类型参数指向自己」，就只是认字，不是读懂**。而本系列要读的恰好是后一种。**设计意图是读懂的前提，不是读懂之后的进阶。**

> ⚠️ **附带一条纪律**：**会设计 ≠ 到处用**。刚学会泛型最典型的翻车，是拿它去套本来两个普通方法就能解决的事（`toHiPage` 复制版就是个正当选项）。
> **验收标准 = 设计得出来，且知道什么时候不该设计。** 后半句同等重要，`08` 篇会专门收这一条。

## 三、五个宏观问题的一句话答案

细节全部留给分篇，这里只给结论，先建立方位感。

### Q1 · 泛型解决什么问题？

**把类型错误从运行期提前到编译期。** 没有泛型时，集合里装什么都行，取出来必须手工强转，转错了要等到那一行真正执行才抛 `ClassCastException`——可能是上线三个月后的凌晨。

→ 展开见 `01-没有泛型的世界.md`

### Q2 · 它是针对编译器的设计吗？

**是。这是你问得最准的一个问题，也是整个泛型的总钥匙。**

Java 的泛型采用**类型擦除**（type erasure）：编译后 `List<String>` 和 `List<Integer>` 变成同一个 `List`，类型参数信息基本不进 class 文件。所以泛型**几乎是纯编译期的**——编译器拿它做检查、自动插强转，运行时基本看不见它。

后面所有"怪现象"（不能 `new T[]`、不能 `instanceof List<String>`、两个重载会撞车）都是这一条推出来的。

→ 展开见 `02-类型擦除.md`（**本系列的分水岭，最该花时间的一篇**）

### Q3 · `T` / `E` / `R` / `U` / `K` / `V` 是什么？

**纯命名约定，编译器完全不认识这些字母。** 你把它们改成 `A`、`Foo`、`张三` 都能编译通过。

约定俗成的含义：

| 字母 | 来源 | 典型出处 |
|---|---|---|
| `T` | **T**ype | `R<T>`、`Comparable<T>` |
| `E` | **E**lement | `List<E>`、`Collection<E>` |
| `K` / `V` | **K**ey / **V**alue | `Map<K, V>` |
| `R` | **R**esult / **R**eturn | `Function<T, R>` |
| `U` / `S` | 第二、第三个类型（没有语义，纯排队） | `Query<T, U>` |

→ 展开见 `03-字母约定与签名读法.md`

### Q4 · 是从 C++ 借来的吗？

**概念同源，实现路线完全不同。**

- **同源**：泛型的学术名字叫「参数化多态」（parametric polymorphism），源头在 ML / Haskell 一脉，C++ 模板和 Java 泛型都是它的分支。
- **不同**：C++ 模板是**编译期代码生成**——`vector<int>` 和 `vector<string>` 会生成两份**独立的机器码**；Java 是**擦除**——只有一份代码。
- **Java 的直接前身**不是 C++，是 Martin Odersky 等人的 **Pizza / GJ（Generic Java）**，1998 年前后的研究项目，2004 年随 Java 5 进入正式语言。（顺带一提：Odersky 后来做了 Scala。）
- **对照组**：C# 2.0 的泛型是 **reified**（运行时保留类型），能做 Java 做不到的事——它敢这么设计，是因为当时 .NET 生态小、破坏兼容的代价扛得住。**Java 选擦除是历史包袱的产物，不是技术上更优。**

→ 展开见 `07-横向对比-C++-C#-Kotlin.md`

### Q5 · 没有它行不行？

**行。Java 1.4 及之前就没有泛型，照样写了十年企业应用。**

代价是：满地强制转型、类型错误全在运行期爆、API 文档只能靠注释说明"这个 List 里装的是 User"。**泛型不是让你能做新的事，是让编译器帮你挡住一类老错误。**

→ 展开见 `01-没有泛型的世界.md`

## 四、你其实一直在用泛型（本项目清单）

这一节是本篇最该看的。**你不是"只会 `List<User>`"，你是已经在用一堆泛型、只是一直没意识到。**

按难度排：

| 难度 | 你项目里的代码 | 位置 | 用到的泛型知识 |
|---|---|---|---|
| ⭐ | `List<ProcessInstanceVO>`、`Map<String, String>`、`Set<Long>` | 遍地 | 填一个具体类型（你熟的那档） |
| ⭐ | `Page<SysUser> page = new Page<>(current, size)` | `SystemUserServiceImpl.java:32` | 同上；`<>` 菱形推断 |
| ⭐⭐ | `LambdaQueryWrapper<SysUser>` | `SystemUserServiceImpl.java:33` | 类型参数决定 `SysUser::getUsername` 这种方法引用能不能通过检查 |
| ⭐⭐ | `interface SystemUserMapper extends BaseMapper<SysUser>` | `SystemUserMapper.java:7` | **继承时把类型参数钉死**——空接口白捡二十几个方法，全部自动带上 `SysUser` |
| ⭐⭐ | `IPage<SysUserVO>` ← `entityPage.convert(SysUserVO::of)` | `SystemUserServiceImpl.java:36` | 泛型方法 + 方法引用；`convert` 把 `IPage<SysUser>` 变 `IPage<SysUserVO>` |
| ⭐⭐⭐ | **`public class R<T>`** | `R.java:6` | 泛型类。**能读懂大概，写不出来**（← 台阶在这） |
| ⭐⭐⭐ | **`public static <T> R<T> ok(T data)`** | `R.java:11` | 泛型方法。同上 |
| ⭐⭐⭐⭐ | `Function<E, ProcessInstanceVO> mapper` | `09` 文档的 `toPage` | 把"函数"当参数传，类型参数描述它的入参出参 |
| ⭐⭐⭐⭐⭐ | `Query<T extends Query<?,?>, U>` | Flowable jar | 自限定泛型 + 通配符 |

### 💡 最重要的一条

⚠️ **先澄清**：`R<T>` 和 `R.ok()` 是**答疑文档生成的代码，不是自己写的**。当前状态是"读得懂个大概，但让我从零写绝对写不出来"。本系列的目标就是把这句话里的"写不出来"去掉。

不过它依然是最好的起点，因为——看 `R.java:11`：

```java
public static <T> R<T> ok(T data) {
```

**返回类型前面那个 `<T>`，和 `toPage` 的 `<E>` 是完全同一个东西。**

```java
private <E> IPage<ProcessInstanceVO> toPage(Query<?, E> query, ...)
//      ↑ 同一个语法位置
```

两者的差距，**不在 `<E>` 这个尖括号**，而在 `toPage` 同时叠了另外两样东西——`Query<?, E>` 的通配符，和 `Function<E, R>` 这个函数类型。**三样拆开，每一样都不难。**

这就是本系列的基本策略：**从项目里已有、且你已经读得懂个大概的 `R<T>` 出发，一样一样加，最后自然长成 `toPage`。** 目标不是"看懂"，是**合上文档能自己写出来**。

## 六、常见误解速查（宏观级）

| 误解 | 实际 |
|---|---|
| `T`、`E` 是 Java 关键字 | 纯约定，改成任何合法标识符都能编译 |
| 泛型是运行时特性 | 几乎纯编译期，运行时基本被擦掉 |
| `List<String>` 和 `List<Integer>` 是两个类 | 运行时是**同一个类**（`02` 篇有实验证明） |
| 泛型让程序更快 | 无关。它省掉的强转开销可忽略；C++ 模板才有性能含义 |
| 泛型是从 C++ 抄的 | 概念同源，实现路线相反（生成多份 vs 擦成一份） |
| 「读得懂」等于「会写」 | 两回事。`R<T>` 能读个大概但写不出来，缺的正是这一级台阶——本系列以**能自己写出来**为验收标准 |

---

## 七、一句话总结

泛型是**编译期的类型标注**，为了把强制转型的错误提前暴露；Java 因为要兼容 1.4 的旧代码而选了**擦除**实现，这个历史选择解释了后面所有别扭的地方。而缺的不是入门，是**从「用现成的」到「自己写」之间那一级台阶**——`R.java:11` 就摆在项目里，读得懂个大概，但合上文档写不出来。本系列的验收标准就是把它写出来。
