# 04 · 泛型类与泛型方法（`<T>` 到底写在哪）

> **触发点**：`03` 的实验 3 发现 `R.java` 里有 5 个互不相干的 `T`，静态方法用不了类上的 `T`。
> 那反过来问：**什么时候该写类上、什么时候该写方法上？** 这是自己动手写泛型时的第一个决策，也是唯一一个绕不过去的决策。
>
> **本篇是本系列第一篇要你自己写代码的**。前三篇都在读，这篇开始写。

## 一、先纠两个误解

### 误解 1 · 「泛型类里的方法都是泛型方法」

看 `R.java`（Lombok 生成的那些也算上）：

```java
public class R<T> {
    private T data;
    public T getData() { ... }          // ← 这是泛型方法吗？
    public void setData(T data) { ... } // ← 这个呢？
}
```

**都不是。** 它们只是**用**了类上的 `T`，没有自己声明类型参数。

> **泛型方法的定义只有一条：它自己的签名里声明了类型参数**（返回类型前面有 `<...>`）。

```java
public T getData()                  // ❌ 不是泛型方法，借用类的 T
public static <T> R<T> ok(T data)   // ✅ 是泛型方法，自己声明了 T
```

这个区分不是抠字眼——**它决定了 `T` 是什么时候被绑定的**：

| | `T` 何时确定 | 一个对象上能变吗 |
|---|---|---|
| 借用类的 `T`（`getData`） | `new R<String>()` 那一刻 | **不能**，整个对象生命周期都是 String |
| 方法自己的 `T`（`ok`） | **每次调用**那一刻 | 能，这次 String 下次 Integer |

### 误解 2 · 「泛型方法必须写在泛型类里」

不用。`toPage` 就是反例——它写在 `ProcessInstanceServiceImpl` 里，那是个**普通类**，一个类型参数都没有：

```java
public class ProcessInstanceServiceImpl implements ProcessInstanceService {   // 普通类
    private <E> IPage<ProcessInstanceVO> toPage(Query<?, E> query, ...)       // 泛型方法
}
```

**两者完全正交**：泛型类里可以有非泛型方法，普通类里也可以有泛型方法。

## 二、纵向剥层：判据是「这个类型要活多久」

### 2.1 唯一的本质区别是作用域

把类型参数当成变量看（`03` 第二节那句话），问题就变成了**变量的作用域该定在哪一级**——和你决定「这个值该做字段还是做局部变量」是同一类问题。

```java
public class R<T> {              // T 的作用域 = 整个类体
    private T data;              //   ↳ 字段能看见它
    public T getData() {...}     //   ↳ 所有实例方法能看见它
}
//     生命周期：从 new R<String>() 到对象被回收，T 恒等于 String
```

```java
private <E> IPage<..> toPage(Query<?, E> query, ...) {   // E 的作用域 = 这个方法体
    ...                                                  // 出了大括号 E 就不存在了
}
//     生命周期：从进入方法到离开方法。下一次调用 E 可以是完全不同的类型
```

**`page()` 调 `toPage` 时 E 是 `ProcessInstance`，`myStarted()` 调时 E 是 `HistoricProcessInstance`——同一个对象上，两次调用两个类型。** 这件事只有把 `E` 放在方法上才做得到。

### 2.2 四条判据（按顺序问，问到第一个"是"就停）

> **问 1 · 有字段要用它吗？**
> 是 → **类上**。没得选。字段属于实例，只能依赖实例级的类型参数。
> `R.java` 的 `private T data` 就是这一条，`R<T>` 的 `T` 想挪也挪不走。

> **问 2 · 是 `static` 方法吗？**
> 是 → **方法上**。也没得选。静态方法在任何实例存在之前就能被调用（`R.ok(...)` 前面根本没有对象），没有任何东西能告诉它类上的 `T` 是什么。
> —— 这就是 `03` 实验 3 那个报错的全部原因。

> **问 3 · 有多个方法要共享同一个类型吗？**
> 是 → **类上**。否则每个方法各自声明的 `T` 互不相干，编译器不会认为它们是同一个类型。

> **问 4 · 剩下的情况**
> → **方法上**。默认选它。

### 2.3 拿两个真实例子过一遍

**`R<T>`：**

| 问 | 答 | 结论 |
|---|---|---|
| 1 · 有字段用吗？ | 有，`private T data` | → **类上**，到此为止 |

**`toPage`：**

| 问 | 答 | 结论 |
|---|---|---|
| 1 · 有字段用吗？ | 没有，`E` 只出现在参数里 | 继续问 |
| 2 · static 吗？ | 不是（`private` 实例方法） | 继续问 |
| 3 · 多个方法共享吗？ | 不，只有 `toPage` 自己用 | 继续问 |
| 4 · 剩下 | | → **方法上** |

**结论一句话：`E` 只在一次调用里有意义，出了 `toPage` 就没人关心它了——所以它属于方法，不属于类。**

### 2.4 一个反例：什么时候两个都要

```java
public class Box<T> {                          // 类上的 T：盒子里装什么
    private T item;                            //   ↳ 字段用了，判据 1

    public <U> Pair<T, U> pairWith(U other) {  // 方法上的 U：这一次要配什么
        return new Pair<>(item, other);        //   ↳ 只这一次调用有意义，判据 4
    }
}
```

`box.pairWith("abc")` 和 `box.pairWith(42)` 可以在同一个 `box` 上先后调用，`T` 不变、`U` 变。**两个判据同时生效，各管各的。**

## 三、横向讲史：为什么要有「方法级」这一套

### 3.1 旧世界：只有类级泛型行不行

假设 Java 5 当年只加了泛型**类**，没加泛型**方法**。看看什么写不出来——

```java
// java.util.Collections 里的真实方法
public static <T> void sort(List<T> list, Comparator<? super T> c)
```

`Collections` 是个**工具类**，全是静态方法，它自己不装任何东西。**你没法把 `T` 放到 `Collections` 上**——那意味着要 `new Collections<String>()` 才能排序，荒谬。

同理，你项目里的：

```java
R.ok(vo)   // 如果 ok 不能是泛型方法，就得写成 new R<SysUserVO>().ok(vo)
```

**痛点具体是**：静态工具方法先于任何实例存在，而类级类型参数依附于实例。**两者的生命周期对不上。**

### 3.2 那时候实际是怎么绕的

Java 1.4 的 `Collections.sort` 长这样：

```java
public static void sort(List list, Comparator c)   // 全是 raw
```

调用方自己保证类型对，错了运行期 `ClassCastException`——就是 `01` 篇那套老毛病。**另一条路是复制粘贴**：给每个类型手写一份 `sortStrings` / `sortIntegers`，代码翻倍。

> 💡 **这条历史线你现在正踩在上面**：Day 16 的 `toHiPage` 复制版，就是 3.2 里"复制粘贴"那条路的现代版本。它不是错的写法，只是你已经决定走另一条。

### 3.3 新方案的形状：为什么 `<T>` 写在返回类型前面

方法级泛型的学术祖宗是 ML 一脉的 **let-polymorphism**（1978，Milner），Java 只是把它塞进 C 风格的语法里。塞的时候有个约束：

```java
public static <T> R<T> ok(T data)
//            ↑ 为什么必须在这儿？
```

因为**返回类型里就要用 `T` 了**（`R<T>`）。变量必须先声明后使用，所以声明区只能放在返回类型**之前**、修饰符**之后——那个位置是唯一没被占用的空档。

> 这和 `03` 里说的「找声明点」是同一件事的两面：**声明点的位置不是随便定的，是被"先声明后使用"逼出来的。**

### 3.4 代价

**两套语法位置，初学者永远搞不清写哪。** 你现在卡的就是这个代价——它是真实存在的设计债，不是你的问题。

判据（2.2 那四问）能还掉这笔债，但**判据本身是要背的**，语言没能让它自然而然。

## 四、动手实验

> ⚠️ **本篇的实验是要你写代码的，别只看。** 建议直接在项目里建个临时类，验完删掉：
> `process-back/src/main/java/com/ha/pr/flowwork/Scratch.java`

### 实验 1 · 第一次自己写一个泛型方法 ⭐ 必做

**先看对照组（没有泛型的写法）：**

```java
public class Scratch {
    // 1.4 风格：装 Object，调用方自己强转
    static Object firstOrNull(java.util.List list) {
        return list.isEmpty() ? null : list.get(0);
    }

    public static void main(String[] args) {
        java.util.List<String> names = java.util.List.of("a", "b");
        String s = (String) firstOrNull(names);   // ← 必须强转
        System.out.println(s);
    }
}
```

```bash
cd process-back && ./mvnw -q compile
```

能编译（会有 raw type 警告）。**痛点就是那个 `(String)`——它是你在替编译器打包票。**

**现在你来写泛型版。** 只给骨架，`____` 处自己填：

```java
static ____ ____ firstOrNull(java.util.List<____> list) {
    return list.isEmpty() ? null : list.get(0);
}
```

三个空分别是：**声明区**、**返回类型**、**参数里的元素类型**。

填之前先过一遍 2.2 的四问：有字段用吗（没有）→ static 吗（是）→ **方法上**。

<details>
<summary>写完了再展开对答案</summary>

```java
static <T> T firstOrNull(java.util.List<T> list) {
    return list.isEmpty() ? null : list.get(0);
}
```

调用方不用强转了：

```java
String s = firstOrNull(names);        // ✅ 编译器从 names 推出 T = String
Integer i = firstOrNull(numbers);     // ✅ 同一个方法，这次 T = Integer
```

**再验一次它真的在检查**：写 `Integer i = firstOrNull(names);` → 编译报错
`incompatible types: String cannot be converted to Integer`。

**这就是泛型的全部价值**——`01` 篇里那个"运行期才炸"的错误，现在在编译期就红了。
</details>

### 实验 2 · 把 `<T>` 挪到类上，看后果 ⭐⭐ 判据的实证

把实验 1 的方法改成"类级泛型"：

```java
public class Scratch<T> {                     // ← T 挪到类上
    T firstOrNull(java.util.List<T> list) {   // ← 去掉 static 和 <T>
        return list.isEmpty() ? null : list.get(0);
    }
}
```

**能编译。但用起来变了：**

```java
Scratch<String> s = new Scratch<>();     // ① 必须先造对象
String a = s.firstOrNull(names);         // ② OK
Integer b = s.firstOrNull(numbers);      // ③ ❌ 编译报错！
```

第 ③ 行报错，因为 `s` 这个对象的 `T` **在第 ① 行就被永久钉死成 `String` 了**。想处理 Integer 得另造一个 `Scratch<Integer>`。

> **这就是"作用域"的实际后果，也是 2.1 那段话的实证**：
> 类上的 `T` 一个对象只能有一个值；方法上的 `T` 每次调用都能不同。
> 而 `firstOrNull` 显然属于后者——**没有字段用它，把它锁在实例上是白白付出代价**。

### 实验 3 · 类型实参从哪来（三个来源）

你项目里 `R.java` 有个无参的 `ok()`：

```java
public static <T> R<T> ok() { return ok(null); }
```

**它没有参数，编译器怎么知道 `T` 是什么？** 试这三行：

```java
R<String> a = R.ok();          // ① 从「目标类型」推 → T = String
var b = R.ok();                // ② 没有目标类型 → T 只能推成 Object
R<String> c = R.<String>ok();  // ③ 显式指定
System.out.println(b.getClass());   // 打印看看
```

**三个来源，优先级从常用到罕见：**

| # | 来源 | 例 | 备注 |
|---|---|---|---|
| 1 | **实参的类型** | `R.ok(vo)` → `T = SysUserVO` | 最常见，你项目里几乎全是这种 |
| 2 | **目标类型**（赋值左边 / 方法返回位置） | `R<String> a = R.ok();` | Java 8 起大幅加强。**你的 Controller 里 `return R.ok();` 就是靠这个**——从方法声明的返回类型倒推 |
| 3 | **显式指定** | `R.<String>ok()` | 前两个都推不出来时才写 |

> **反直觉点在 ②**：`var b = R.ok()` 推成 `R<Object>`。**`var` 会让目标类型推断失效**——因为 `var` 本身就是等着被推的，没有"目标"可言。
>
> 这解释了一类真实报错：明明 `R<String> a = R.ok();` 好好的，换成 `var` 就崩了。

## 五、常见误解速查

| 误解 | 实际 |
|---|---|
| 泛型类里的方法都是泛型方法 | 只有**自己声明了类型参数**的才是。`getData()` 只是借用类的 `T` |
| 泛型方法要写在泛型类里 | 无关。`toPage` 就在普通类里 |
| `<T>` 写类上还是方法上凭感觉 | 有判据：**字段用吗 → static 吗 → 多方法共享吗 → 都不是就放方法上** |
| 类上的 `T` 静态方法也能用 | 用不了。静态方法先于实例存在（`03` 实验 3） |
| 放类上更"通用" | 反了。类上的 `T` 一个对象**只能有一个值**，比方法级**更受限**（实验 2） |
| 泛型方法必须能从参数推出类型 | 还能从**目标类型**推（`R<String> a = R.ok()`），或显式写 `R.<String>ok()` |
| `var` 和显式类型效果一样 | 用了 `var` 就没有目标类型了，`var b = R.ok()` 会推成 `R<Object>` |
| `<>`（菱形）和 `<T>` 是一回事 | 完全不同。`<T>` 是**声明**变量，`<>` 是**省略**已能推出的类型实参 |

## 七、一句话总结

`<T>` 写在哪，取决于**这个类型要活多久**：字段要用、多个方法要共享 → **类上**（跟着对象走）；只在一次调用里有意义、或者是 `static` → **方法上**（跟着调用走）。四问顺着走一遍就能定，`R<T>` 卡在第一问、`toPage` 落到第四问。**放类上不是"更通用"，反而更受限**——实验 2 那个 `Scratch<String>` 再也处理不了 Integer，就是代价。
