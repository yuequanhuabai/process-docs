## 1. Flowable 命令模式：一个门面背后的多表操作与命令事务　⬜

**登记日期**：2026-07-13（Day 11 写 `ProcessDefinitionServiceImpl.deploy()` 期间）

**来源**：`repositoryService.createDeployment()...deploy()` 一个调用就写了三张表（`ACT_RE_DEPLOYMENT` / `ACT_GE_BYTEARRAY` / `ACT_RE_PROCDEF`），感觉 `RepositoryService` 封装得太多——它到底是怎么把"多张表的写入"包进"一个方法调用 = 一个事务"里的？

**当前理解**（已澄清的部分，避免重复弄一遍）：
- 那段代码里只有 `deploy()` 一次创建；后面的 `createProcessDefinitionQuery()` 是查询器（Flowable 版 `LambdaQueryWrapper`），执行的是 SELECT 回读，不是第二次创建。
- 流程定义是 `deploy()` 内部解析 XML 时顺带产出的：存部署回执 → 存文件字节 → 解析每个 `isExecutable` 的 process 插入定义，三步同一个引擎命令事务，非法 XML 整体回滚。
- 部署 : 定义 = 1 : N（一次部署多个文件、一个文件多个 process），所以 `deploy()` 只返回回执 `Deployment`，想知道解析出了什么要按 `deploymentId` 查。
- Flowable 服务按**领域**切门面（Repository / Runtime / Task / History / Management），不是一实体一 Service；MyBatis-Plus 是一表一 Mapper 粒度细，Flowable 一域一门面粒度粗——引擎表结构是内部实现，不让外界按表操作。

**深入路径**（剥层顺序）：
1. **门面入口**：读 Flowable 源码 `RepositoryServiceImpl#deploy` —— 会看到它只有一行：`commandExecutor.execute(new DeployCmd<>(deploymentBuilder))`，门面方法全是"包一个 Cmd 扔给执行器"。
2. **命令拦截器链**：`CommandExecutor` 是一条责任链（日志 → 事务拦截器 → CommandContext 拦截器 → 最终调 `Cmd.execute()`），事务边界就在链条中间——这就是"一个 Cmd 一个事务"的由来。
3. **CommandContext / DbSqlSession**：`Cmd.execute()` 里对多张表的插入并不是立刻发 SQL，而是先攒进会话缓存，命令收尾统一 flush 成批量 SQL——理解"三张表整体回滚"的真正实现位置。
4. **对照已熟的那套**：MyBatis-Plus（一表一 Mapper + Spring 声明式 `@Transactional`）vs Flowable（一域一门面 + 命令自带事务），两种设计各自的取舍；顺带回答 02 手册坑清单第 4 条"为什么不要给 deploy 套 `@Transactional`"。
5. **动手实验**：`application.yml` 开 `logging.level.org.flowable.engine.impl.persistence: debug`（或看 Druid SQL 日志），部署一次流程，数一数实际发出的 SQL 序列和顺序，验证第 3 步的"攒缓存再 flush"。

## 2. LambdaQueryChainWrapper：把日常查询改成链式自执行风格　⬜

**登记日期**：2026-07-13（Day 11 解析 `ProcessDefinitionQuery` 链式 DSL 之后）

**来源**：看懂 Flowable 查询器"攒条件不发 SQL、终结方法才执行"的模式后，发现 MyBatis-Plus 的 `LambdaQueryChainWrapper` 就是同款融合版（构造时喂 mapper，链尾直接 `.list()/.one()/.count()/.exists()/.page()`），想把现有代码改造过去。

**当前理解**（已剥过的层）：
- 链式 DSL 四零件：`return this`（链的地基）、接口收窄（修剪词汇表）、orderBy 两步状态机、终结方法持有执行通道。
- 普通 `LambdaQueryWrapper` 只有前两个零件，不认识 mapper，链尾必须断开塞给 `mapper.selectXxx(wrapper)`；ChainWrapper 补上了零件 4。
- MP 用方法引用当列名的原理：运行期把 lambda 反序列化出 `SerializedLambda`，从 `getUsername` 反推列名——代价是一次反射解析，收益是列名拼错编译不过（比 Flowable 手写字符串方法更安全）。
- 词汇表取舍：Flowable 每个可查字段手写一个方法（封闭词汇表，隐藏表结构，适合引擎/SDK）；业务 CRUD 用 MP 泛型化的开放词汇表即可，不值得每表手写 Query 类。

**改造点**（`SystemUserServiceImpl`，自己动手改）：
1. `createUser` 的重名检查（原 `selectCount(new LambdaQueryWrapper<>()...) > 0`）→ 链式 + `.exists()`（发 `SELECT 1 ... LIMIT 1`，比 COUNT 便宜且语义准）。
2. `querySysUserPage`（原 `new Page` + wrapper + `selectPage` 三段式）→ `.orderByDesc(SysUser::getCreateTime).page(new Page<>(current, size))` 一条链到底。
3. 改完 `mvnw compile` + swagger 冒烟（分页 total 正常、重名报错正常），确认行为不变。

**深入路径**（改造之外想再剥的层）：
1. 读 `LambdaQueryChainWrapper` 源码：它怎么同时"是个 wrapper"又"持有 baseMapper"（`ChainQuery` 接口的默认方法把终结操作转发给 mapper）。
2. 断点看一次 `SysUser::getUsername` → `SerializedLambda` → 列名的完整解析链（`LambdaUtils` / 缓存）。
3. 对比 `.exists()` 与 `selectCount` 实际发出的 SQL（Druid 日志），验证"便宜在哪"。

## 4. 泛型化的 `toPage()` 与 Flowable 的自限定泛型　✅ 已吃透

**登记日期**：2026-07-31（读 `../process_instance/09-Day16-完整代码.md` 的改造版 `toPage()` 时）

**来源**：`private <E> IPage<ProcessInstanceVO> toPage(Query<?, E> query, Function<E, ProcessInstanceVO> mapper, ...)` 这串泛型看不懂——`Query<?, E>` 的 `?` 是什么、为什么要多传一个 `Function` 而不在里面直接写 `ProcessInstanceVO::of`。

**笔记位置**：[`泛型toPage与自限定泛型.md`](./泛型toPage与自限定泛型.md)　✅ 2026-07-31

**结论提要**（免得重读全篇）：
- 分页 body **一行没变**，变的只是"谁来决定元素类型"；泛型不是为了优雅，是绕开两个**编译期硬障碍**。
- 障碍①：`ProcessInstanceQuery` 与 `HistoricProcessInstanceQuery` **无继承关系**（javap 确认，共同祖先只有 `Query`），写死参数的旧版塞不进去。
- 障碍②：泛型方法体内 `E` 未知 → **重载决议无法进行**，所以必须由知情的调用点选好 `of` 的重载、打包成 `Function` 传进来。
- `Query<T extends Query<?,?>, U>` 的 `T` 是**自限定泛型**（同 `Enum<E extends Enum<E>>`）：没它，`.desc()` 之后就调不到子接口专属方法，链断在中间。我们不关心 T，故写 `?`。
- 代价：方法体内只剩 `Query` 的 8 个公共方法，碰不到具体查询条件——**抽到公共层就只剩公共能力**。
- 附带四个坑：`Stream.toList()` 不可变、`count()`/`listPage()` 两条 SQL 不同事务、`(int)` 强转括号位置、javap 找不到方法要往父接口翻（`count`/`listPage` 在 `Query`、`processInstanceIdIn` 在 `TaskInfoQuery`）。

**发现的文档缺陷（已修）**：`09` 里 `page()` 的 return 写成 `return  (query, ...)` **漏了方法名 `toPage`**；`08`/`09` 两处散文写「`page()` 零改动」与实际矛盾（`toPage` 变 4 参后调用行必须补 mapper）。根因：**标「完整代码」的文档从没进过编译器**。已确立流程——参考代码先落进真实项目 `mvn compile` 过一遍再复制进文档。

## 6. `Stream.toList()`：为什么 Java 16 才加、为什么不可变　⬜

**登记日期**：2026-07-31（读第 4 条笔记的坑 1 时冒出来）

**来源**：Stream 是 Java 8 引入的，但 `Stream.toList()` 是 Java 16 才有，且返回**不可变** List，与老写法 `collect(Collectors.toList())` 行为不同。疑问：中间这八年发生了什么？为什么新方法要选不可变？"不可变"和 `final` 字段是一回事吗？有哪些应用场景？

**深入路径**：① `Collectors.toList()` 的契约本来就没承诺可变性（只是实现恰好返回 `ArrayList`），大量代码依赖了未承诺的行为；② Java 9 的 `List.of()` 起，JDK 开始系统性推不可变集合；③ 不可变 vs `final`：`final` 管的是**引用不能换**，不可变管的是**内容不能改**，两者正交；④ 为什么不直接改 `Collectors.toList()`——向后兼容，同 `02` 篇擦除的那套逻辑；⑤ 动手实验：`set(0, ...)` 在两种写法下的对照。

**优先级**：排在第 5 条（泛型）之后。

## 7. `<router-view/>` 与 slot：「父组件留坑、子组件填内容」的两种实现　⬜

**登记日期**：2026-08-05（Day 16 讲 `views/instance` 布局第 1 步时冒出来）

**来源**：讲「你的页面为什么不用写侧栏」时，机制答案是 `router/index.ts` 里 `/instance` 是 layout 的 **children**，而 `layout/index.vue:60` 的 `<router-view/>` 是留给子路由的**出口**——URL 变化决定往那个坑里填哪个组件。用户当场提出：这跟 slot 是什么关系？两者都是「父组件留位置、子组件填内容」，那区别在哪？

**当前理解（讲到的深度）**：只说到「`<router-view/>` 是**由 URL 决定填什么**的坑」这一句类比，**没有展开**。

**深入路径**：① slot 的填充者是**父模板里的书写者**（编译期就定了），`router-view` 的填充者是**路由表 + 当前 URL**（运行期才定）；② 两者在 Vue 内部是不是同一套机制（`router-view` 的实现里到底有没有用 slot）；③ 嵌套路由多层 `router-view` 的匹配规则；④ 命名视图 `<router-view name="xxx">` 与具名插槽的对照；⑤ 动手实验：把 `layout/index.vue:60` 的 `router-view` 删掉，看 `/instance` 变成什么样（预期：侧栏顶栏都在，主区空白）——这个实验能一次性验证「侧栏不是自动出现的」。

**优先级**：⏳ **用户明确要求推迟**——非主线，**整个项目完工后**再展开。别在 P4~P8 期间主动插进来。
