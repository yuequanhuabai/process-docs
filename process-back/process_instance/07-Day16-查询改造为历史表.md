## 一、为什么要改（问题是什么）

Day 12 写的 `myStarted()` 查的是 `RuntimeService`：

```java
runtimeService.createProcessInstanceQuery().startedBy(userId)
```

`RuntimeService` 只翻 `ACT_RU_EXECUTION` —— **只装在途的实例**。实例一办结/终止，行就被删了。

**后果**：员工发起 4 条申请，经理批完 1 条、终止 1 条之后，「我的发起」页只剩 2 条。**另外 2 条像人间蒸发** —— 用户会以为丢单。

这个问题 2026-07-21 写 [`../deep_dive/hi_tables/03-ACT_HI_PROCINST.md`](../deep_dive/hi_tables/03-ACT_HI_PROCINST.md) 时发现并登记，2026-07-30 定方案：**改查历史表**。

---

## 二、关键认知：HI 表不是归档表

改之前必须先破一个直觉误解，否则会写出「查两次再合并」的错代码。

直觉上以为 `ACT_HI_*` 是归档表 —— 流程走完才搬进去。**不是。**

你 Day 12 亲手验过（记在 [`../deep_dive/hi_tables/00-历史表族-宏观.md`](../deep_dive/hi_tables/00-历史表族-宏观.md)）：终止实例**之前**去查 `ACT_HI_PROCINST`，那一行**早就在了**，只是 `END_TIME_` 为空、`REV_=1`；完结时引擎只是回来把 `END_TIME_` **UPDATE** 上去。

| 表 | 装什么 |
|---|---|
| `ACT_RU_*` | **只装在途的**，结束就删行 |
| `ACT_HI_*` | **装全部**（含在途），在途的 `END_TIME_` 为空 |

所以两者是「**在途子集 / 全集**」，不是「运行时 / 归档」。

> ✅ **一次查询就够** —— 查 HI 拿到全集，靠 `endTime` 区分在途与已结束。
> ❌ 不要查 RU 再查 HI 然后合并去重。

---

## 三、结局判据（本次改造的核心）

Flowable **不存**一个叫 `status` 的字段，没有哪一列写着「已办结」。结局要靠两个字段推断：

| `endTime` | `deleteReason` | 结局 | 前端 tag |
|---|---|---|---|
| `null` | — | `RUNNING` 进行中 | `primary` 蓝 |
| 有值 | `null` | `COMPLETED` 已办结 | `success` 绿 |
| 有值 | 有值 | `TERMINATED` 已终止 | `danger` 红 |

数据库层面的完整判据表（含 `END_ACT_ID_`、`ACT_HI_ACTINST` 有无 `endEvent` 行）见 [`../deep_dive/hi_tables/03-ACT_HI_PROCINST.md`](../deep_dive/hi_tables/03-ACT_HI_PROCINST.md) 第五节，是 Day 12 + Day 13 交叉验出来的。

> 💡 **判据放后端算**，VO 直接给前端一个 `status` 字符串。
> 理由：这套规则只写一遍。前端不该知道 `deleteReason` 是什么东西，更不该写 `if (endTime && !deleteReason)` —— 规则写两遍迟早不一致。

## 四、改动清单（2 个文件）

### 1. `dto/response/ProcessInstanceVO.java`

现有 8 个字段（`id` / `processDefinitionId` / `processDefinitionKey` / `processDefinitionName` / `businessKey` / `startUserId` / `startTime` / `suspended`）**装不下**新需求，补 5 个：

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `endTime` | `Date` | `HistoricProcessInstance.getEndTime()` | `@JsonFormat` 与 `startTime` 保持一致；RU 来源恒为 null |
| `status` | `String` | **按第三节判据算** | `RUNNING` / `COMPLETED` / `TERMINATED` |
| `deleteReason` | `String` | `getDeleteReason()` | 终止原因，给前端显示"为什么被终止" |
| `startUserName` | `String` | **查 `sys_user` 换姓名** | 否则页面上「发起人」显示的是 `"3"` 而不是「李員工」 |
| `currentActivityName` | `String` | **查当前任务拿节点名** | 已结束的实例为 null |

**还要加一个工厂方法**。现有的只吃 `ProcessInstance`：

```java
public static ProcessInstanceVO of(ProcessInstance instance) { ... }   // 已有，RU 来源
```

新增一个吃 `HistoricProcessInstance` 的重载 —— 这两个是**不同的接口**，传错了编译就不过。判据那三行写在这个新方法里。

### 2. `service/impl/ProcessInstanceServiceImpl.java` + `ProcessInstanceController.java`

- `myStarted()` 改查 `historyService.createHistoricProcessInstanceQuery().startedBy(userId)`
- **接口加一个可选的 `status` 过滤参数**（见下）
- 新增私有方法 `enrich(List<ProcessInstanceVO>)`，填 `startUserName` 和 `currentActivityName`

> ⚠️ **`page()` 不要跟着改**。「运行中实例」页本来就只该看在途的，继续查 RU 是**故意的**，不是漏改。但它**要复用 `enrich()`** —— 那两个字段两个页面都要显示。

#### `status` 过滤参数（前端「状态筛选」下拉要用）

前端页面顶部有个「全部 / 进行中 / 已办结 / 已终止」的下拉。**筛选必须放后端做** —— 放前端只能过滤当前这一页，分页立刻就错（总数还是全量、翻页会出现空页）。

`GET /process-instance/my-started` 增加：

```
@RequestParam(required = false) String status   // RUNNING / COMPLETED / TERMINATED，不传=全部
```

`HistoricProcessInstanceQuery` 上有现成的过滤方法可以组合（写的时候在 IDE 里补全确认一下方法名）：

| status | 大致对应 |
|---|---|
| `RUNNING` | `.unfinished()` |
| `COMPLETED` | `.finished()` + 未被删除 |
| `TERMINATED` | `.finished()` + 被删除（`DELETE_REASON_` 有值）|

> 判据和第三节那张表是**同一套规则**，只是一个用在「查的时候过滤」、一个用在「查回来后判定 status」。**别写成两份**——把判定逻辑收在一个私有方法里，过滤分支和 VO 赋值都调它。

## 五、⚠️ 两个批量查询：别写成 N+1

`startUserName` 和 `currentActivityName` 都需要额外查一次。**天真写法是在循环里逐条查 —— 一页 10 条就是 20 次查询。**

正确做法是**每页各查一次批量**：

**① 发起人姓名**
```
收集这页所有 startUserId → Set
一次 LambdaQueryWrapper .in(SysUser::getId, ids) 查出来
转成 Map<String, String>（userId → realName）
遍历 VO 回填
```

**② 当前节点名**
```
收集这页 status == RUNNING 的实例 id
用 TaskQuery 一次查出这些实例的当前任务
按 processInstanceId 分组成 Map
遍历 VO 回填；已结束的实例没有当前任务，留 null
```

> `TaskQuery` 有没有批量按实例 id 过滤的方法，写的时候在 IDE 里补全确认一下。若确实没有，退而求其次也要**一次查完再分组**，绝不能放进循环。

> 💡 **为什么「当前节点」这次才变得重要**：Day 15 时库里只有 `leaveProcess` 一个单级流程，卡在哪儿无所谓。07-30 新增了报销/采购/出差三个**三级流程**（经理审批 → 财务/总监审批），不显示节点名就看不出卡在第一级还是第二级。

## 六、验收（先后端后前端）

**这一步必须先做完再动前端。** 否则前端「状态」列是空的，你会以为自己前端写错了，其实是后端还没给。

knife4j 走一遍：

1. 用 employee 账号发起 3–4 条不同流程（现在有 4 个模板可选）
2. 用 manager + admin 把其中一条**两级都批完**（三级流程要批两次才结束）
3. 终止另一条
4. 调 `GET /process-instance/my-started`（employee token，先**不传** `status`）—— **重点看**：
   - [ ] 办结的那条**还在列表里**（改造前会消失）
   - [ ] 终止的那条也在
   - [ ] 三条的 `status` 分别是 `COMPLETED` / `TERMINATED` / `RUNNING`
   - [ ] 办结与终止的有 `endTime`，在途的为 `null`
   - [ ] 终止的那条 `deleteReason` 有值
   - [ ] `startUserName` 是「李員工」不是 `"3"`
   - [ ] 在途那条 `currentActivityName` 有值（能看出停在「经理审批」还是「总监审批」）
5. 再带上 `status` 各调一次：`RUNNING` 只回在途那条、`COMPLETED` 只回办结那条、`TERMINATED` 只回终止那条，**且三次的 `total` 相加 = 不传时的 `total`**（这条能验出过滤分支有没有漏/重）
6. 调 `GET /process-instance/page` —— 确认它**仍然只返回在途的**（没被顺手改坏），且同样有 `startUserName` / `currentActivityName`
