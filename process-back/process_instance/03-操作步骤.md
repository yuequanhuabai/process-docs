# 03 · 操作步骤

> 前提：02 的代码已进项目且 `mvnw compile` 通过。全程在 knife4j（`http://localhost:9090/workflow/doc.html`）操作，配合 SQL 客户端看表。

## 步骤 0 · 准备

1. 启动后端，确认「流程实例」分组出现在文档页；
2. 用 **employee 账号**登录（`/auth/login`），token 粘进 Authorize；
3. SQL 客户端连库备用，先记一下基线（此刻应全为 0 行或仅有此前测试残留）：

```sql
SELECT COUNT(*) FROM ACT_RU_EXECUTION;
```

## 步骤 1 · 发起一条实例（主路径）

`POST /process-instance/start`，body：

```json
{
  "processDefinitionKey": "leaveProcess",
  "businessKey": "test-0001",
  "variables": { "days": 3, "reason": "年假" }
}
```

**预期响应**：`R.data` 里有 `id`（实例 id）、`processDefinitionId`（形如 `leaveProcess:N:xxx`，N 是当前最新版本）、`startUserId`（= employee 的 userId）、`startTime`、`suspended=false`。

**随即看表**（把 `{instanceId}` 换成响应里的 id）：

```sql
-- 实例 + 游标：预期 2 行，ID_ = PROC_INST_ID_ 的是实例本身，START_USER_ID_ 有值
SELECT ID_, PROC_INST_ID_, PARENT_ID_, PROC_DEF_ID_, BUSINESS_KEY_, START_USER_ID_, ACT_ID_
FROM ACT_RU_EXECUTION WHERE PROC_INST_ID_ = '{instanceId}';

-- 当前任务：预期 1 行，manager 审批节点
SELECT ID_, NAME_, TASK_DEF_KEY_, ASSIGNEE_ FROM ACT_RU_TASK WHERE PROC_INST_ID_ = '{instanceId}';

-- 变量：预期 3 行 —— days(integer)、reason(string)、initiator(string, = employee userId)
SELECT NAME_, TYPE_, TEXT_, LONG_ FROM ACT_RU_VARIABLE WHERE PROC_INST_ID_ = '{instanceId}';

-- 候选组：预期有一行 GROUP_ID_ = 'manager' 的 candidate
SELECT TYPE_, GROUP_ID_, USER_ID_, TASK_ID_ FROM ACT_RU_IDENTITYLINK WHERE PROC_INST_ID_ = '{instanceId}';
```

## 步骤 2 · 异常路径

依次验证三种失败都返回统一 `R` 错误结构：

1. **key 不存在**：body 里 `processDefinitionKey` 写 `"noSuchProcess"` → 「流程定义不存在」；
2. **key 缺失**：body 里去掉 `processDefinitionKey` → 400 参数校验错误（`@NotBlank` 生效）;
3. **定义挂起**：先 `PUT /process-definition/{最新版definitionId}/suspend`，再发起 → 「流程定义已挂起，无法发起」，**测完记得 activate 回来**。

## 步骤 3 · 查询两连

1. 再用步骤 1 发起 1–2 条实例（businessKey 换一下便于区分）；
2. `GET /process-instance/page` → 全部运行实例，按发起时间倒序，total 正确；试一次 `definitionKey=leaveProcess` 过滤和 `definitionKey=xxx`（应 0 条）；
3. `GET /process-instance/my-started` → 与 page 相同条数（目前只有 employee 发起过）；
4. **换 token 验证隔离**：Authorize 里换 **admin** 的 token，再调 `my-started` → 应为 **0 条**（admin 没发起过），而 `page` 仍能看到全部——这就是 `startedBy` 过滤生效的证据。

## 步骤 4 · 终止

1. （仍用任一 token）挑一条实例 `DELETE /process-instance/{instanceId}?reason=测试终止`；
2. 复查：`page` 少一条；`ACT_RU_EXECUTION`/`ACT_RU_TASK` 里该实例的行消失；
3. 历史留痕预览（Day 14 的正主，先瞄一眼）：

```sql
SELECT ID_, END_TIME_, DELETE_REASON_ FROM ACT_HI_PROCINST WHERE ID_ = '{instanceId}';
-- 预期：行还在，END_TIME_ 有值，DELETE_REASON_ = '测试终止'
```

4. 对不存在的 id 再 DELETE 一次 → 「运行中的流程实例不存在」。

## 步骤 5 · 清 Day 11 的 cascade 欠账

前提：库里还有至少一条**运行中**实例（没有就再发一条），且知道它用的定义属于哪次部署（`processDefinitionId` 里的 key:version 对得上哪条 deployment，忘了就用 Day 11 那条 JOIN SQL 查）。

1. **cascade=false 分支**：`DELETE /process-definition/deployment/{那个deploymentId}?cascade=false`
   → 预期失败，报「删除失败：该部署下可能存在流程实例…」（你 Impl 里 catch 后转 BizException 的那个分支，第一次真正被走到）；
2. **cascade=true 分支**：同一 deploymentId，`cascade=true`
   → 预期成功；复查三处：`ACT_RE_PROCDEF` 该版本消失、`ACT_RU_EXECUTION` 里跑在该版本上的实例消失、`ACT_HI_PROCINST` 里它们的**历史也一并消失**（cascade 的"连历史一起删"不是虚言——这也是界面上必须二次确认的原因）；
3. 测完检查现场：若把唯一的 leave 部署删没了，重新 `POST /process-definition/deploy` 传一次 `leave.bpmn20.xml`，恢复到"有定义可发起"的状态，别给 Day 13 留坑。
