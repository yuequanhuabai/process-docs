# 01 · 流程实例发起原理

> 对应排期 Day 12「流程实例接口」。读完本文再进 `02-前置任务与完整代码`。
> 上一块（Day 11）你操作的是**图纸**（`ACT_RE_*`，静态）；这一块开始操作**生产**（`ACT_RU_*`，动态）。

---

## ① 换门面：RuntimeService

Day 11 的主角是 `RepositoryService`（仓库域）；本块主角是 `RuntimeService`（运行域），管辖 `ACT_RU_*` 系列表：

| 表 | 存什么 | 直觉类比 |
|---|---|---|
| `ACT_RU_EXECUTION` | 流程实例 + 执行分支（游标） | 生产工单 + 进度指针 |
| `ACT_RU_TASK` | 当前停留的人工任务 | 当前工位上的活 |
| `ACT_RU_VARIABLE` | 流程变量 | 随工单流转的物料清单 |
| `ACT_RU_IDENTITYLINK` | 任务/实例与人的关系（候选组、发起人等） | 派工单 |

依旧是"一域一门面"：这四张表你都不直接碰，全部经 `RuntimeService`（任务的办理归 `TaskService`，那是 Day 13 的门面）。

## ② 发起一条实例，引擎干了什么

`runtimeService.startProcessInstanceByKey(key, businessKey, variables)` 是一个命令（`StartProcessInstanceCmd`），一个命令事务内完成：

1. **找图纸**：按 key 取**最新版本**的流程定义（先查缓存，未命中才回 `ACT_RE_PROCDEF` + 重新解析字节）；
2. **开工单**：在 `ACT_RU_EXECUTION` 插入实例记录（可能不止一行，见 ④），`PROC_DEF_ID_` 记下**具体版本**的定义 id；
3. **落变量**：`variables` 逐个写 `ACT_RU_VARIABLE`（带类型列 `TYPE_`：string/long/boolean…）；`flowable:initiator` 声明的发起人变量也在这一步写入；
4. **推游标**：从 StartEvent 出发沿顺序流推进，直到撞上第一个**等待态**——我们的 leave 流程即 manager 审批的 UserTask；
5. **建任务**：在 `ACT_RU_TASK` 插入该 UserTask 的任务行，`candidateGroups="manager"` 展开成 `ACT_RU_IDENTITYLINK` 的候选组行；
6. **抄送历史**：以上动作同步镜像到 `ACT_HI_*` 历史表（history-level 默认 full）——Day 14 的历史接口就吃这些数据。

XML 里流程"跑"起来的真相：**引擎不是常驻线程在跑流程,而是"戳一下动一下"**——发起是一次戳（推到第一个等待态就存库返回），Day 13 的 complete 是下一次戳（从当前等待态推到下一个）。两次戳之间，流程的全部状态就躺在 `ACT_RU_*` 表里。

## ③ 发起人是怎么记上的：Authentication

`leave.bpmn20.xml` 的 StartEvent 写了 `flowable:initiator="initiator"`，意思是"发起时，把当前认证用户存进名为 initiator 的流程变量"。但引擎不认识你的 JWT/UserContext——它有自己的 ThreadLocal：

```
Authentication.setAuthenticatedUserId(userId)   // 告诉引擎"现在操作的人是谁"
→ 引擎发起时顺手做两件事：
   1. ACT_RU_EXECUTION.START_USER_ID_ = userId   （实例的发起人列）
   2. 流程变量 initiator = userId                 （XML 里声明的那个变量）
→ 用完必须还原（finally 里 set 回 null）
```

这和你写 `UserContext` 是同一个模式：ThreadLocal 传递"当前用户"，请求结束必须清，防线程池脏读。区别只是这是**引擎自己的**那份 ThreadLocal，两者需要在 Service 里手动"接线"一次。"我的发起"查询（`startedBy(userId)`）过滤的就是 `START_USER_ID_` 这一列。

## ④ 一条实例 ≠ 一行 EXECUTION

`ACT_RU_EXECUTION` 里，一条实例通常是**一行父执行（实例本身）+ 一行子执行（游标）**，并行网关还会分裂出更多游标行。所以：

- 数实例用 `createProcessInstanceQuery()`（只算实例行），别用 `createExecutionQuery()`（连游标一起算）；
- 发起一条 leave 实例后看表别惊讶行数是 2——`ID_ == PROC_INST_ID_` 的那行才是实例本身。

## ⑤ 版本钉死：key 选版本，id 锁版本

- **发起时**按 key 自动选**当时的最新版本**——所以接口入参用 key，不用 definitionId；
- **发起后**实例的 `PROC_DEF_ID_` 锁死那个具体版本——之后再部署 v3，**在途实例照旧按老版本走完**，只有新发起的用 v3。这是工作流引擎版本机制的核心承诺（流程改版不影响在途单据）。

## ⑥ 终止的语义

`runtimeService.deleteProcessInstance(instanceId, reason)`：

- 只对**运行中**实例有效（`ACT_RU_*` 里的行整套删掉）；
- 不是抹掉痕迹——历史表里该实例仍在，`DELETE_REASON_` 记下 reason（Day 14 能看到"谁因为什么终止了它"）；
- 已正常走完的实例不在 RU 表里，终止接口对它报"不存在"是正确行为。

## ⑦ 与 Day 11 的一处呼应

`deleteDeployment(cascade=false)` 之所以会在"有在途实例"时失败，就是因为 `ACT_RU_EXECUTION.PROC_DEF_ID_` 外键指着 `ACT_RE_PROCDEF`。本块做完你就有在途实例了，正好回头把那两个分支补测掉（已排进 03 操作步骤）。
