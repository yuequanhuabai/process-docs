## Step 1 · `ProcessInstanceVO.java`：补字段 + 判据方法 + HI 工厂重载

**做什么**：让 VO 能装下历史实例，并把「结局判据」封装成它自己的事。

**先看清现场（和 07 文档有一处出入）**：07 说"现有 8 个字段要补 5 个"，但实查 `ProcessInstanceVO.java:38-49`——`endTime` / `status` / `startUserName` / `currentActivityName` 四个**早已预留**（声明了但没人赋值）。所以本步真正要做的是：

1. **补 1 个新字段** `deleteReason`（`String`，加 `@Schema` 说明"终止原因，仅 TERMINATED 有值"）。
2. **定义三个状态常量** `STATUS_RUNNING` / `STATUS_COMPLETED` / `STATUS_TERMINATED`（`public static final String`）。为什么用常量不用裸字符串：这三个值 Service 的过滤分支、enrich 的筛选、前端契约都要引用，散着写迟早拼错一个字母还不报错。
3. **写私有静态方法 `statusOf(Date endTime, String deleteReason)`**——07 第三节那张判据表的代码化，三行搞定：`endTime` 为 null → RUNNING；`deleteReason` 为 null → COMPLETED；否则 TERMINATED。
4. **新增工厂重载 `of(HistoricProcessInstance hi)`**。字段对拷（`getId` / `getBusinessKey` / `getStartUserId` / `getStartTime` / `getEndTime` / `getDeleteReason`…），`status` 调 `statusOf()` 算。
5. **给现有的 `of(ProcessInstance)` 补一行** `vo.setStatus(STATUS_RUNNING)`——RU 表里的实例必然在途，这行不是装饰：Step 4 的 `enrich()` 要靠 `status` 判断"哪些实例该查当前任务"，`page()`（RU 来源）也要走 enrich，status 空着它就被跳过了。

**坑**：

- `ProcessInstance` 在 `org.flowable.engine.runtime`，`HistoricProcessInstance` 在 `org.flowable.engine.history`——**两个不同接口，没有继承关系**，import 别选错（IDE 弹的候选里还有个 `org.flowable.engine.repository.ProcessDefinition` 长得像，Day 12 就踩过一次选错 import）。
- `HistoricProcessInstance` 上**没有 `isSuspended()`**——挂起是纯运行时概念，`ACT_HI_PROCINST` 没这列。HI 来源的 VO `suspended` 恒为 false，在工厂方法里注释一句即可，别试图去查。
- `endTime` 的 `@JsonFormat` 要和 `startTime` 一致（预留字段上已经带了，确认没被删就行）。

**自测**：编译通过即可。此时没人调用新重载，正常。

## Step 2 · `ProcessInstanceService.java`：接口签名先动

**做什么**：`myStarted(long current, long size)` → `myStarted(long current, long size, String status)`，javadoc 同步改成"全部实例：在途 + 办结 + 终止；status 可选过滤"。

**为什么这步单独拎出来、且放在改实现之前**：改完接口，`ProcessInstanceServiceImpl` 和 `ProcessInstanceController` **立刻双双编译报错**——这两个红叉就是你剩余工作的待办清单，改完一个灭一个，不会漏。这是"面向编译器导航"的基本功，比记在脑子里可靠。

**自测**：此时项目**应该**编译不过（两处报错）。红叉位置对了就是成功。

## Step 3 · `ProcessInstanceServiceImpl.java`：换门面 + 状态过滤

**做什么**：`myStarted()` 从 RuntimeService 换到 HistoryService，并支持 status 过滤。

**怎么写（引导）**：

1. **注入三个新依赖**（和现有 `runtimeService` / `repositoryService` 并排，各配一行注释说明是哪个域的门面）：
   - `HistoryService`（`org.flowable.engine`）—— myStarted 的新数据源
   - `TaskService` —— Step 4 查"当前节点"用
   - `SystemUserMapper` —— Step 4 换发起人姓名用
2. **重写 `myStarted()`**：
   - `historyService.createHistoricProcessInstanceQuery().startedBy(UserContext.userId()).orderByProcessInstanceStartTime().desc()`
   - 调下面第 3 点的私有过滤方法
   - 分页收尾交给 Step 4 改造后的 `toPage()`
3. **新增私有方法 `applyStatusFilter(HistoricProcessInstanceQuery query, String status)`**：null/空白直接 return（不传=全部）；然后一个 switch：

   | status 常量 | 拼上的过滤 | 落到 SQL |
   |---|---|---|
   | `STATUS_RUNNING` | `.unfinished()` | `END_TIME_ IS NULL` |
   | `STATUS_COMPLETED` | `.finished().notDeleted()` | `END_TIME_` 有值且 `DELETE_REASON_ IS NULL` |
   | `STATUS_TERMINATED` | `.deleted()` | `DELETE_REASON_ IS NOT NULL`（终止必已结束，不必再拼 finished） |
   | 其他值 | 抛 `BizException("未知的状态过滤值：" + status)` | —— |

   default 分支**必须抛异常**而不是当"全部"处理：前端传错参数时安静地返回全量，是那种要 debug 半天的软故障。
   > 这张表和 Step 1 的 `statusOf()` 是**同一套判据的两面**——一面是"查之前拼 WHERE"，一面是"查回来后打标签"。语义上无法合成一个方法（方向相反），所以用注释互相指认，改其中一面时必须看另一面。

**坑**：

- **排序方法名不同**：RU 的 `ProcessInstanceQuery` 叫 `.orderByStartTime()`（现 `page()` 里就是），HI 的却叫 **`.orderByProcessInstanceStartTime()`**——直接照抄 RU 版会发现方法不存在。三个过滤方法名（`unfinished` / `finished` / `notDeleted` / `deleted`）已在 flowable-engine 7.1.0 jar 里 javap 核实过，放心用。
- `page()` 的**查询逻辑**一个字都不要动（它继续查 RU 是故意的，07 有说明）；`terminate()` 整个不动。
  ⚠️ 唯一例外是 `page()` 最后那行 `return toPage(...)`——Step 4 把 `toPage()` 改成 4 参后要跟着补 mapper，详见 Step 4 第 2 点。

**自测**：ServiceImpl 的红叉灭了（Controller 还红着，正常）。

## Step 4 · 还是 `ProcessInstanceServiceImpl.java`：`enrich()` 批量回填 + `toPage()` 改造

**做什么**：补 `startUserName` 和 `currentActivityName` 两个字段的值，且**整页只查 2 次库**，不是每行查 2 次。

**怎么写（引导）**：

1. **新增私有方法 `enrich(List<ProcessInstanceVO> vos)`**，两段：
   - **① 发起人姓名**：流收集所有 `startUserId` → `Set<Long>`（注意 `Long.valueOf` 转型，见坑）→ 一次 `systemUserMapper.selectList(new LambdaQueryWrapper<SysUser>().in(SysUser::getId, ids))` → 转 `Map<String, String>`（key 用 `String.valueOf(u.getId())` 转回字符串）→ 遍历 VO 回填。
   - **② 当前节点名**：筛出 `status == STATUS_RUNNING` 的实例 id → 一次 `taskService.createTaskQuery().processInstanceIdIn(runningIds).list()`（这个方法在父接口 `TaskInfoQuery` 上，已核实存在，吃 `Collection<String>`）→ 按 `getProcessInstanceId()` 转 Map，value 取 `getName()` → 回填；已结束的实例天然不在 Map 里，留 null。
2. **把现有 `toPage()` 泛型化**，让 RU 和 HI 两种 Query 走同一条分页收尾，并把 `enrich()` 收进去（这样 `page()` 的**查询逻辑**零改动就自动获得两个新字段，正是 07 要求的"page() 复用 enrich"）：
   - ⚠️ **但 `page()` 的 `return` 那一行必须改**：`toPage()` 签名从 3 参变 4 参，调用点要补上 `ProcessInstanceVO::of`，写成 `return toPage(query, ProcessInstanceVO::of, current, size);`。这是 Step 3 那句"`page()` 一个字都不要动"的**唯一例外**——那句说的是查询逻辑，不含分页收尾的调用行。漏了这行就是编译错误。
   - 关键认知：`ProcessInstanceQuery` 和 `HistoricProcessInstanceQuery` 都继承自 `org.flowable.common.engine.api.query.Query<T, U>`，`count()` / `listPage()` 就定义在这个公共接口上（已 javap 核实）。所以签名可以写成 `private <E> IPage<ProcessInstanceVO> toPage(Query<?, E> query, Function<E, ProcessInstanceVO> mapper, long current, long size)`，调用时传 `ProcessInstanceVO::of`——编译器会按 E 的实际类型自动选中正确的重载。
   - **如果泛型看着晕**：复制一份 `toPage` 改叫 `toHiPage`、参数类型写死，也完全能跑。泛型版是可选优化，先跑通再回头收编不丢人。两个版本 `09` 里都有说明。

**坑**：

- **N+1 是本步的头号敌人**：任何出现在 `for` / `stream().map()` **里面**的 `selectById` / `singleResult()` 都是错的——一页 10 条 = 20 次查询。两段都必须"先收集、一次批量、转 Map、再回填"。
- **类型转换链**：`START_USER_ID_` 存的是 `sys_user.id`（Long 雪花）的**字符串形态**（发起时 `Authentication.setAuthenticatedUserId(UserContext.userId())` 塞进去的就是 String）。所以：查库前 `Long.valueOf` 转过去，转 Map 时 `String.valueOf` 转回来。两头都不转、或只转一头，Map 就永远 get 不到。
- **MyBatis-Plus 的 `in()` 遇空集合会拼出非法 SQL**（`WHERE id IN ()`）。虽然本方法开头 `vos.isEmpty()` 已挡掉主要情况，两段各自的 id 集合仍要判空短路（比如整页全是已结束实例时 `runningIds` 为空）。
- **`Collectors.toMap` 撞 key 直接抛 `IllegalStateException`**：并行网关下一个实例可能同时有多个活动任务。当前四个模板都是单路径不会撞，但要给 `toMap` 带上第三个 merge 参数 `(a, b) -> a` 兜底——这是"今天不出错、明天画个并行网关就炸"的定时雷。
- **`Collectors.toMap` 的 value 为 null 会抛 NPE**（同一个方法的另一张脸）：它内部走 `HashMap.merge`，null 不是"存个空进去"而是直接炸。所以①段**不能**直接写成 `SysUser::getRealName`——`sys_user.real_name` 列可空、`CreateUserRequest.realName` 也没加 `@NotBlank`，用户管理页建一个不填姓名的用户，这一页就整页 500。写成 `u -> u.getRealName() == null ? u.getUsername() : u.getRealName()` 兜底。种子数据三条都有姓名，**这个坑自测时踩不出来**。

**自测**：全项目编译过（Controller 的红叉在下一步灭）。可以先跑一遍已有单测确认没把 `page()` 改坏。

## Step 5 · `ProcessInstanceController.java`：收口

**做什么**：`my-started` 接口加可选参数，文档注解同步更新。

**怎么写（引导）**：照 `page()` 里 `definitionKey` 的样子，给 `myStarted()` 加：

```
@RequestParam(required = false) String status
```

`@Parameter` 的 description 写清取值（`RUNNING / COMPLETED / TERMINATED，不传=全部`）——knife4j 页面上这行字就是前端同学（也是你）的接口文档。`@Operation` 的 summary 也要改：原来写"运行中实例"，现在语义变了，不改的话 swagger 说谎。

**坑**：`@RequestParam(required = false)` 别忘了，漏了的话不传 status 会直接 400，你会误以为后端逻辑写错。

**自测**：编译全绿，启动后端，knife4j 上 `GET /process-instance/my-started` 能看到新参数。
