# 05 · 疑问与解答

> 预置了操作前后最容易冒出来的问题；你自己的新疑问追加到文末「待解疑问」区，问过我、弄懂了就把答案补上来——这份文档就是你的部署知识底账。

---

### Q1 · 部署（Deployment）和流程定义（ProcessDefinition）到底什么关系？为什么要两张表？

**一次动作 vs 动作的产物**。Deployment 是「我在某时刻上传了一包资源」这个动作的收据；ProcessDefinition 是从这包资源里解析出来的「可执行流程」。一次部署可以带多个 BPMN 文件、每个文件可以含多个 process，所以是一对多，必须两张表。日常单文件单流程时它们看起来一一对应，容易误以为是一个东西。

### Q2 · 为什么文件名后缀必须是 `.bpmn20.xml` 或 `.bpmn`？

部署可以携带**任意**资源（将来表单 json、说明文档都可能塞进同一次部署），引擎需要一个规则决定「哪些资源要当 BPMN 解析」，它选了最简单的判据：文件名后缀。后缀不对的资源照存不解析、**不报错**——这是静默坑，所以接口层第一行就校验后缀。

### Q3 · 重复部署同一份 XML 会覆盖旧的吗？

不会，**永远是新增**：同 key 版本号 +1，老版本原封不动。「覆盖/更新」在流程引擎里不存在——因为可能有实例正跑在老版本上（见 Q7）。自动部署之所以重启不会堆版本，是因为它开了 `enableDuplicateFiltering`（同名部署 + 资源字节完全一致 → 跳过）；我们的手动接口没开，所以你重复上传就会看到 version 2、3、4……这也是清理测试数据要删部署的原因。

### Q4 · 部署后的 XML 存在哪？我直接改库里的 XML 能生效吗？

存在 `ACT_GE_BYTEARRAY.BYTES_`（BLOB，原始字节）。**直接改库不生效也绝不要改**：① 引擎解析后把流程模型放了内存缓存，运行时根本不回头读库里的 XML；② 流程定义的设计原则就是**不可变**（immutable），修改的唯一正道是部署新版本。前端设计器的「编辑」功能，本质是把 XML 捞出来改完再发一次部署。

### Q5 · `ACT_GE_BYTEARRAY` 里怎么多了一行 png？我没上传过图片。

引擎干的：配置项 `isCreateDiagramOnDeploy` 默认开启，只要 XML 带 DI 坐标，部署时就按坐标渲染一张流程图 png 存进去（`GENERATED_=1` 就是「引擎生成」标记）。画图用 AWT + 默认字体 Arial，**中文会变方框**——Day 10 挂起的 `FlowableConfig` 中文字体问题就是给这个画图器换字体。前端用 bpmn-js 自己渲染 XML、不用这张 png，所以它是不是方框暂时无所谓。

### Q6 · 部署到一半失败（比如 XML 语法错误），库里会留半截数据吗？

不会。`deploy()` 是一个引擎命令 = 一个数据库事务（01 文档第②步），解析抛异常时 `ACT_RE_DEPLOYMENT` / `ACT_GE_BYTEARRAY` 里已写的行一起回滚。**唯一的例外**是 `isExecutable="false"`：这不算"失败"，事务正常提交，只是没产生定义——所以 02 的代码要手动清掉这种空部署。

### Q7 · 部署了 version 2，正跑在 version 1 上的实例怎么办？

继续按 version 1 走完，不迁移、不中断。实例在**发起那一刻**绑定具体的 definitionId（三段式那个，含版本），终身不变。这正是「定义不可变 + 版本递增」这套设计换来的能力：升级流程不影响在途审批。新发起的实例默认用最新版本（按 key 发起时引擎自动选 latest）。

### Q8 · 挂起（suspend）到底挡住了什么？

我们用的简单重载 `suspendProcessDefinitionById(id)` 只挡**新实例的发起**（发起时抛异常），在途实例照常流转、任务照常办理。另有一个三参数重载可以连在途实例一起挂起、甚至定时生效——那是「紧急冻结某流程」的运维场景，管理页用不上就先不做。落库表现就一个字段：`ACT_RE_PROCDEF.SUSPENSION_STATE_`，1=激活 2=挂起。

### Q9 · 删除时 cascade 是 true 还是 false，怎么选？

- `false`（默认，安全）：只删「定义层」——部署 + 资源 + 流程定义。有实例引用时直接失败，**这是保护不是故障**。
- `true`（危险）：连这个部署下的所有流程实例、任务、**历史记录**一锅端。
原则：日常清理测试版本用 false，删不掉就该去看看是谁的实例还挂着；`true` 只在「确认连历史都不要了」时用，将来做管理页要配二次确认弹窗。

### Q10 · 流程定义的 id 为什么长成 `leaveProcess:1:2504` 这样？

`key : version : 引擎发号器序号` 三段拼接。前两段让人一眼看出「哪个流程的第几版」，第三段保证全局唯一（就是 `ACT_GE_PROPERTY.next.dbid` 那套发号器发的号）。推论：definitionId 是**字符串**且天然携带版本信息；而 key 是跨版本的稳定标识——「发起一个请假流程」传 key，「操作某个具体版本」传 definitionId，两者不能混用（挂起接口传成 key 会报"流程定义不存在"）。

### Q11 · `latestVersion()` 是什么？什么时候用？

查询修饰符：每个 key 只返回版本号最大的那条。管理页默认视图用它（用户关心"现在生效的是哪版"），版本历史视图不用它（要看全部版本）。接口里的 `latestOnly` 参数就是这个开关的透出。

### Q12 · 手动部署和之前的自动部署，代码路径一样吗？

一样，都是 `createDeployment().add资源().deploy()`。区别只有三点：① 触发者（引擎启动钩子 vs 你的 Controller）；② 资源来源（classpath 扫描 vs HTTP 上传）；③ 自动部署开了重复过滤（Q3）。所以你在 03 里看到的三张表变化，和 Day 10 启动日志里看到的完全同源。
