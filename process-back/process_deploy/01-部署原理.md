# 01 · 部署原理：`createDeployment().deploy()` 内部发生了什么

> 一句话：**部署 = 把一份 BPMN XML「原文存档 + 解析登记」**。原文进 `ACT_GE_BYTEARRAY`，这次部署动作本身记一行 `ACT_RE_DEPLOYMENT`，解析出的每个可执行流程登记一行 `ACT_RE_PROCDEF`。三张表一个事务内写完。

---

## 一、调用链总览

```
repositoryService.createDeployment()          ① 拿到 DeploymentBuilder（纯内存收集器）
    .name("请假流程手动部署")                  ② 设置部署名（只是元数据）
    .addBytes("leave.bpmn20.xml", bytes)      ③ 把资源攒进内存，还没碰数据库
    .deploy();                                ④ 真正干活：包装成 DeployCmd 提交给引擎
        │
        ▼
   命令拦截器链（开事务 → 建 CommandContext → 执行命令）
        │
        ▼
   DeployCmd.execute()
        ├─ a. DeploymentEntity 落库 ──────────► ACT_RE_DEPLOYMENT（1 行）
        ├─ b. 每个资源 ResourceEntity 落库 ───► ACT_GE_BYTEARRAY（原文 BLOB，1 行/资源）
        ├─ c. BpmnDeployer 挑出 BPMN 资源并解析
        │      （只认文件名以 .bpmn20.xml / .bpmn 结尾的资源！）
        │      BpmnParse：XML ──SAX──► BpmnModel（Java 对象模型）──► 校验
        ├─ d. 每个 isExecutable="true" 的 <process>
        │      → ProcessDefinitionEntity 落库 ► ACT_RE_PROCDEF（1 行/流程）
        ├─ e. （可选）按 DI 坐标画流程图 png ──► ACT_GE_BYTEARRAY（又 1 行）
        └─ f. 解析结果放进内存缓存（后续发起实例不再解析 XML）
        │
        ▼
   提交事务（任何一步失败 → 整体回滚，三张表都不会留下脏数据）
```

## 二、逐步剥层

### ① `createDeployment()` —— 拿到一个「购物车」

`DeploymentBuilder` 是纯内存对象，`name()` / `addBytes()` / `addInputStream()` / `addClasspathResource()` 都只是往里面攒东西。**这一步数据库零交互**——所以攒一半程序崩了什么都不会留下。一个 builder 可以 add 多个资源（一次部署多个流程文件），这就是「部署」和「流程定义」是两个概念、两张表的原因。

### ② `deploy()` —— 命令模式入口

Flowable 所有写操作都走**命令模式**：`deploy()` 把整个动作包装成 `DeployCmd`，丢进命令拦截器链。链上依次做：开启事务、创建 `CommandContext`（本次命令的工作台，攒着待刷库的实体）、执行命令、统一刷库、提交事务。**一个命令 = 一个事务**，这就是部署原子性的来源——你不需要也不应该在自己的 Service 上加 `@Transactional`。

### ③ 第一落库：存档

- `DeploymentEntity` → **`ACT_RE_DEPLOYMENT`**：这次「部署动作」的登记——id（引擎发号器发的数字，就是你之前看到的 `next.dbid` 那套）、你起的名字、部署时间。
- 每个资源一条 `ResourceEntity` → **`ACT_GE_BYTEARRAY`**：`NAME_` 存资源名（`leave.bpmn20.xml`），`BYTES_` 存**原始字节**（BLOB），`DEPLOYMENT_ID_` 外键挂到部署上。注意存的是原文，一个字符都不改——以后前端设计器要「编辑已部署流程」，就是从这里把 XML 原文捞回去。

### ④ 谁会被解析：文件名后缀是唯一判据

`BpmnDeployer` 遍历本次部署的所有资源，**只解析文件名以 `.bpmn20.xml` 或 `.bpmn` 结尾的**。后缀不对的资源会**静默跳过**——照样存进 `ACT_GE_BYTEARRAY`，但不产生任何流程定义，不报错。这是手动部署第一大坑：上传接口必须校验文件名后缀（02 文档的代码里做了这个校验）。

### ⑤ 解析与校验

`BpmnParse` 用 SAX 把 XML 读成 `BpmnModel`（一套纯 Java 对象：Process、UserTask、SequenceFlow……前端 bpmn-js 里也有一套等价的对象模型，两边通过 XML 互通）。同时做两层校验：XML 结构对不对（XSD）、语义对不对（比如 sequenceFlow 的 sourceRef 指向的节点存在吗）。**校验失败抛异常 → 事务回滚 → 三张表全部不留痕**。

### ⑥ 登记流程定义：版本号在这里诞生

每个 `isExecutable="true"` 的 `<process>` 生成一条 `ProcessDefinitionEntity`：

- **`KEY_`** = XML 里 `<process id="leaveProcess">` 的 id——这是流程的「身份证号」，跨版本不变；
- **`VERSION_`** = 查同 KEY_ 的当前最大版本 + 1（第一次部署 = 1）。版本号**按 key 独立计数**，不是全局的；
- **`ID_`** = `key:version:发号器序号` 三段拼接，如 `leaveProcess:1:2504`——所以流程定义 id 是**字符串**，不是雪花 Long；
- `isExecutable="false"` 的 process 会被解析但**不登记**——XML 合法、部署成功，`ACT_RE_PROCDEF` 却是空的（第二大坑，02 的代码对此做了兜底检查）。

### ⑦ 流程图 png（和 Day 10 的中文字体挂起项直接相关）

引擎配置 `isCreateDiagramOnDeploy` 默认开启：如果 XML 带 DI 坐标（我们的 `leave.bpmn20.xml` 带了），部署时会按坐标**画一张 png** 也存进 `ACT_GE_BYTEARRAY`（`GENERATED_=1` 标记是引擎生成的，名字类似 `leave.leaveProcess.png`）。画图用的字体默认是 Arial——**中文会画成方框**，这就是 Day 10 挂起的 `FlowableConfig` 中文字体问题的确切来源。所以查库时 `ACT_GE_BYTEARRAY` 大概率是 **2 行**：1 行 XML 原文 + 1 行生成的 png。

### ⑧ 缓存

解析出的流程模型放进引擎内存缓存（process definition cache）。之后发起流程实例时直接用缓存对象，**不会再读库解析 XML**。推论：库里的 XML 原文改了也不会影响运行——流程定义是**不可变**的，想改就部署新版本。

## 三、三张表的分工速查

| 表 | 角色 | 关键列 | 本次部署预期行数 |
|---|---|---|---|
| `ACT_RE_DEPLOYMENT` | 部署动作登记簿 | `ID_`、`NAME_`（你起的部署名）、`DEPLOY_TIME_` | 1 |
| `ACT_GE_BYTEARRAY` | 资源原文仓库（BLOB） | `NAME_`（资源名）、`BYTES_`（原文）、`DEPLOYMENT_ID_`（挂哪次部署）、`GENERATED_`（1=引擎生成） | 2（xml + png） |
| `ACT_RE_PROCDEF` | 可执行流程登记簿 | `KEY_`、`VERSION_`、`ID_`（key:version:序号）、`RESOURCE_NAME_`（从哪个资源解析来）、`DGRM_RESOURCE_NAME_`（对应 png）、`SUSPENSION_STATE_`（1=激活 2=挂起） | 1 |

> 表前缀含义：`RE` = repository（仓库域，静态定义），`GE` = general（通用域），后面会遇到 `RU` = runtime（运行域）、`HI` = history（历史域）。

## 四、和自动部署的关系

`check-process-definitions: true` 时的启动自动部署，走的是**同一条代码路径**——引擎启动时扫 `classpath:/processes/`，把扫到的文件 add 进同一个 `DeploymentBuilder` 然后 `deploy()`，只是额外开了「重复过滤」（`enableDuplicateFiltering`：同名部署且资源字节没变就跳过，防止每次重启版本 +1）。你现在做的手动部署，就是把「谁来调 deploy()」从引擎启动钩子换成了你自己的 Controller。
