## ① 第三个（也是最后一个）门面：HistoryService

四个 Day 收齐了 Flowable 的四大门面，一域一门面的规律到此闭环：

| Day | 门面 | 管辖 | 干的事 |
|---|---|---|---|
| 11 | `RepositoryService` | `ACT_RE_*` | 图纸：部署/版本/挂起 |
| 12 | `RuntimeService` | `ACT_RU_EXECUTION` / `VARIABLE` | 生产：发起/查实例/终止 |
| 13 | `TaskService` | `ACT_RU_TASK` / `IDENTITYLINK` | 工位：查待办/认领/办理 |
| **14** | **`HistoryService`** | **`ACT_HI_*`** | **档案：已办/轨迹** |

前三个门面查的都是"**活的**"（`ACT_RU_*`，Runtime）——实例办完就从这些表里消失（Day 13 你亲眼见过办完 `complete` 后运行时表全空）。`HistoryService` 查的是"**归档的**"（`ACT_HI_*`，History）——只要发生过就永久留痕，办完、终止的都在。

## ② RU 和 HI 的关系：一份数据的两次人生

这是本块最该建立的一张心智图。同一个流程实例，在库里同时有两套表：

```
        运行时（活着才有）          历史（发生过就有）
        ACT_RU_EXECUTION     ←→    ACT_HI_PROCINST     实例
        ACT_RU_TASK          ←→    ACT_HI_TASKINST     任务
        ACT_RU_VARIABLE      ←→    ACT_HI_VARINST      变量
        （无对应）             →     ACT_HI_ACTINST      活动轨迹（每经过一个节点一行）
```

关键的三点认知：

1. **HI 不是"完结后才写"的**。引擎是**边跑边往 HI 写**的——发起的一瞬间 `ACT_HI_PROCINST` 就有行了（`END_TIME_` 暂时为 null），经过一个节点就往 `ACT_HI_ACTINST` 补一行。所以**实例还活着时，历史接口就能查到它的轨迹**（未结束的节点 `END_TIME_` 为 null，表示"正停在这儿"）。
2. **RU 会被删，HI 不会**。办完 `complete` 撞 endEvent，`ACT_RU_*` 整条清空（Day 13 的"数据不见了"），但 `ACT_HI_*` 原封不动、补上 `END_TIME_`。**Day 13 你以为办丢的数据，全在这里等着。**
3. **这层"边跑边记"由历史级别（history level）决定**。本项目用引擎默认级别（`audit`/`full` 级别下任务、变量、活动都记全），所以不用额外配置就有完整轨迹。（若某天为了性能把级别调到 `none`，这些接口会集体查空——那是配置问题不是代码问题，知道有这么个开关即可。）

> 一句话记牢：**RU 是"正在发生"，HI 是"曾经发生"；RU 是 HI 的一个临时前台，办完就撤台，档案永远在后台。**

## ③ 命名坑复现：为什么又叫 `FlowableHistoryService`

和 Day 13 的 `FlowableTaskService` 一模一样的理由——你自己的接口若直接叫 `HistoryService`，Impl 里要注入引擎的门面就撞名了：

```java
import org.flowable.engine.HistoryService;      // 引擎的门面

public class FlowableHistoryServiceImpl implements FlowableHistoryService {
    @Resource
    private HistoryService historyService;        // 注入的是引擎那个
}
```

Day 13 的 ② 已经预告过这一处。至此两个带 `Flowable` 前缀的接口（Task / History）都是同一个理由，不是随手起名。

## ④ 我的已审批：靠 `taskAssignee` + `finished` 两个条件

「我的已审批」= 我办过、且已经办完的任务。落到查询就是两个条件叠加：

```java
historyService.createHistoricTaskInstanceQuery()
    .taskAssignee(me.getUserId())   // ASSIGNEE_ = 我
    .finished()                     // END_TIME_ 有值（已办结，排除正在办的）
    .orderByHistoricTaskInstanceEndTime().desc()
```

- **`.taskAssignee(userId)` 查的是 `ACT_HI_TASKINST.ASSIGNEE_`**。这一列的值，正是 Day 13 那个「未认领就自动认领」的决策写进去的。**Day 13 埋的坑，这一块开花**：如果当初 `complete` 前不 `claim`，`ASSIGNEE_` 全是 null，这里 `taskAssignee(userId)` 一条都查不到——这就是 Day 13 ⑥ 反复强调"自动认领是 Day 14 的前提"的兑现时刻。
- **`.finished()` 不能省**：HI 是边跑边写的，一个任务刚创建、还没办时，`ACT_HI_TASKINST` 里已经有它的行了（`END_TIME_` 为 null）。不加 `finished()`，"正在等我办的"也会混进"我已审批"里。已审批要的是**办结的**，所以过滤 `END_TIME_` 有值。

## ⑤ 历史轨迹：`ACT_HI_ACTINST` 是流程走过的脚印

一条实例每**经过一个节点**（startEvent、userTask、endEvent、gateway…），`ACT_HI_ACTINST` 就记一行：

```
ACT_HI_ACTINST（leave 流程办完后，3 行）
  ACT_ID_    ACT_NAME_   ACT_TYPE_     ASSIGNEE_   START_TIME_   END_TIME_
  startEvent  员工发起    startEvent    (null)      10:00:00      10:00:00
  managerApprove 经理审批 userTask      2           10:00:00      10:05:00
  endEvent    结束        endEvent      (null)      10:05:00      10:05:00
```

- 按 `START_TIME_` 升序取出来，就是**这条流程真实的流转顺序**——这就是排期里说的"实例历史轨迹"。
- **它是前端画"高亮流程图"的数据源**：拿到走过的 `activityId` 列表（`startEvent`/`managerApprove`/`endEvent`），去 BPMN 图上把对应节点染色，就能画出"这单走到哪了"。P5 的 BpmnViewer 会复用它。
- **对活着的实例也能查**：发一条不办，它的轨迹会有 `startEvent`（已完成）+ `managerApprove`（`END_TIME_` 为 null，正停在这儿）。前端据此高亮"当前所在节点"。
- **注意里面没有连线（sequenceFlow）**：`ACT_HI_ACTINST` 只记**节点**，不记 `flow1`/`flow2` 那些箭头。前端画图时连线是 BPMN 里静态就有的，节点才需要按轨迹动态高亮。

## ⑥ 状态判定：完成 vs 终止，还是靠 `DELETE_REASON_`

回收 Day 13 ⑨ 的伏笔。两条路都让实例进 `ACT_HI_PROCINST`，区别仍在一列：

| | `END_TIME_` | `DELETE_REASON_` |
|---|---|---|
| **正常办完**（Day 13 complete 走到 endEvent） | 有值 | **NULL** |
| **中途终止**（Day 12 terminate） | 有值 | 你传的 reason（如 `测试终止`） |

历史实例列表要显示"已完成 / 已终止"标签，判据就是读这一列：`DELETE_REASON_` 为 null 是正常办结，有值是被终止。VO 里把它带出来，前端做个三元判断即可。

## ⑦ 历史查询是"纯读"：三个"不需要"

和前几块对照，本块的接口性质最单纯——**只读、不改任何状态**：

- **不需要 `Authentication`**：那是"写"的时候（Day 12 发起要记发起人）才接的线，读历史不写引擎 ThreadLocal。
- **不需要 `try/finally` 清理**：没往任何 ThreadLocal 里塞东西，自然不用清。
- **不需要越权校验那套 `assertCanOperate`**：Day 13 的 `complete` 是"替别人做决定"，越权=篡改；本块是读，越权顶多是"看到别人的历史"，危害等级完全不同。所以：
  - **我的已审批**：天然带 `taskAssignee(me)` 过滤，只会查到自己的，不存在越权面。
  - **实例轨迹**：按 `instanceId` 查，当前 Demo **不校验调用者**——谁都能查任意实例的轨迹。这在演示阶段可接受（轨迹不含敏感字段，且前端本来就要给"我的发起/已审批"里的实例画图）。真实系统若要收紧，可加"该实例的发起人或参与人才能看"的校验，接缝就在 Service 那一个方法里，随时能补。别在 Demo 阶段提前加。

## ⑧ 与 P4 前端的交接（P3 到此收口）

本块产出的两个 VO，正是 P4 两个页面的数据源：

| 本块 VO | 喂给 | 页面 |
|---|---|---|
| `ApprovedTaskVO` | Day 18「已审批」页 | 我办过的审批记录列表 |
| `ActivityTraceVO`（列表） | Day 16/18 的"轨迹"抽屉 + P5 BpmnViewer 高亮 | 一条实例走过的节点 |

至此 **P3「引擎后端一条龙」全部闭环**：定义（11）→ 发起（12）→ 办理（13）→ 归档（14）。`03-操作步骤` 的最后会用**双 token 走一遍完整生命周期**（employee 发起 → manager 办理 → 两人各查自己的历史），亲眼看数据从 `ACT_RU_*` 搬进 `ACT_HI_*`，这趟冒烟通过就关掉 P3，进 P4 批量做前端页面。
