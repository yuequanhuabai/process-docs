## 三、改码阶段：测之前先落地两个决策点

排期 Day 14 挂着两个"实测前该定"的决策点。**先改再测**，否则测的是旧逻辑。

### 3.1 决策1（必改）：轨迹二次排序

**问题**：`ACT_HI_ACTINST` 的 `START_TIME_` 只到毫秒，同一事务里 <1ms 走完的多个节点（如 `startEvent`/`flow1`/`managerApprove`）时间戳会**撞车**。只按 `startTime` 排序，撞车时顺序不保证，且不报错——轨迹可能悄悄错乱。

**引擎的解法与限制**：引擎有 `TRANSACTION_ORDER_` 列记录同事务内先后，但 `HistoricActivityInstanceQuery` **没有**对应的 orderBy 方法（结果对象有 `getTransactionOrder()`，查询 API 没有）。所以只能在 Java 侧二次排序兜底。

**改动**（`FlowableHistoryServiceImpl.activities()`）：

```java
// 改前：
return list.stream().map(ActivityTraceVO::of).toList();

// 改后：startTime 相同时用 transactionOrder 兜底，null 置末
return list.stream()
        .sorted(Comparator.comparing(HistoricActivityInstance::getStartTime)
                .thenComparing(HistoricActivityInstance::getTransactionOrder,
                        Comparator.nullsLast(Comparator.naturalOrder())))
        .map(ActivityTraceVO::of)
        .toList();
```

配套加 `import java.util.Comparator;`。

### 3.2 决策2（待定）：轨迹接口是否过滤 sequenceFlow

**背景**：办结一条流程后，`ACT_HI_ACTINST` 有 5 行，含两条连线（`flow1`/`flow2`），它们的 `activityName` 为空——前端轨迹列表会出现空白行。

**三个选项**：① 后端过滤只返节点；② 后端全返、前端 `filter`；③ 加参数默认过滤。

**定为 ②（后端不改）**。理由：`ActivityTraceVO` 已有 `activityType` 字段，前端一行 `filter` 就能去连线；而 P5 的 BPMN 图路径高亮**需要**连线 id。后端如实返回"引擎走过的每一步"，一份数据两用。所以决策2 **没有代码改动**，只是把方向定下来写进文档。

### 3.3 编译验证

```bash
./mvnw compile
# → [INFO] BUILD SUCCESS
```

编译通过顺带确认了 `getTransactionOrder()` 这个方法真的存在于 `HistoricActivityInstance`（不然编译不过）——**用编译当"API 存在性"的验证器**。

## 四、起环境阶段：三个坑的排查实录（方法论重点）

这一段最能体现"实测"的价值——**代码没问题不代表能跑起来测**。三个坑一个套一个。

### 坑 1：curl 打 9090 全返 503

**现象**：
```bash
curl -s -o /dev/null -w "%{http_code}" http://localhost:9090/doc.html
# → 503
```
不管打哪个路径都是 503。503 是"服务不可用"，看起来像后端起了但没就绪。

**排查第一步——先证伪"后端在跑"这个假设**：查端口到底有没有进程在听。
```powershell
Get-NetTCPConnection -LocalPort 9090 -ErrorAction SilentlyContinue
# → nothing on 9090
```
**矛盾出现了**：端口上没有任何进程，curl 却能拿到 503。那 503 是谁发的？

**排查第二步——顺藤摸瓜查代理**：本机 9090 没人听还能有响应，只可能是中间有代理拦截。
```bash
echo "HTTP_PROXY=$HTTP_PROXY"
# → HTTP_PROXY=http://127.0.0.1:10808   （一个本地代理，多半是 VPN/clash）

curl -s --noproxy '*' -o /dev/null -w "%{http_code}" http://localhost:9090/doc.html
# → 000
```
**真相**：curl 默认走了 `HTTP_PROXY` 指向的本地代理 10808，代理连不上 9090 上游就替它回了 503。加 `--noproxy '*'` 绕过代理直连，得到 `000`（连接失败）——**这才是真相：9090 上根本没有后端在跑**。

> 💡 方法论：**遇到反直觉的响应码，先怀疑"是不是我以为的那个东西在应答"**。503 不是后端发的，是代理发的。用 `Get-NetTCPConnection` 证伪"进程存在"、用 `--noproxy` 剥离代理变量，两步就把假象戳穿。此后所有 curl 都带 `--noproxy '*'`。

### 坑 2（顺带发现）：context-path 前缀

读 `application.yml` 时发现 `context-path: /workflow`。所以真实接口路径是 `http://localhost:9090/workflow/...`，之前我漏了 `/workflow` 前缀。**这个坑没单独暴露**，因为坑1 先让所有请求都失败了；读配置时顺手就把它一起解决了。

> 💡 方法论：**起环境前先读一遍配置文件**，`port` / `context-path` / 数据源三个参数决定了你怎么连。省这一步就会用错 URL 反复撞墙。

### 坑 3：怎么"等后端起来"而不是 sleep 盲等

后端启动要 ~12s。启动脚本：
```bash
nohup ./mvnw spring-boot:run > /tmp/backend-day14.log 2>&1 &
```
然后不能盲目 `sleep 15`（可能不够、也可能浪费）。用 curl 的重试当"等就绪"探针——**连接被拒就重试，一旦端口开了返回 200 就停**：
```bash
curl --noproxy '*' --retry 40 --retry-delay 2 --retry-connrefused \
     -s -o /dev/null -w "up: HTTP %{http_code}\n" \
     http://localhost:9090/workflow/doc.html
# → up: HTTP 200
```
`--retry-connrefused` 是关键：启动中端口还没开 → 连接被拒 → 自动重试；端口一开 → 200 → 立即返回。**等待时间自适应，不多不少**。

起来后立刻看日志确认干净启动：
```bash
grep -iE "Started .*Application|ERROR|Exception|Deployment" /tmp/backend-day14.log | tail -20
# → Started ProcessBackApplication in 12.326 seconds  （无 ERROR）
```

### 拿三个账号的 token

登录三个账号，把 token 存成文件（bash 每次调用的 shell 状态不保留，存文件才能跨命令复用）：
```bash
SP=".../scratchpad"
base=http://localhost:9090/workflow
for u in manager employee admin; do
  resp=$(curl --noproxy '*' -s -X POST $base/auth/login \
    -H "Content-Type: application/json" \
    -d "{\"username\":\"$u\",\"password\":\"123456\"}")
  tok=$(echo "$resp" | grep -o '"token":"[^"]*"' | sed 's/"token":"//;s/"//')
  echo "$tok" > "$SP/tok_$u.txt"
done
```
三个都返回 200 + 完整用户信息，userId 对上 2/3/1。

> 💡 方法论：**token 存文件 = 跨命令复用**。Bash 工具每次调用是独立 shell，变量不跨调用；写文件是最省事的"会话状态"。

## 五、测试阶段：测试矩阵与脚本

### 5.1 测试设计思路（为什么这么测）

历史接口的本质是"查已发生的事"，所以测试分两类：

- **对存量数据查**（现成的 test-0004 办结 / test-0005 在途）→ 验证查询正确性，快、不改数据
- **走一条新流程再查**（整体冒烟）→ 验证 `RU→HI` 的搬运，覆盖完整生命周期

用例排序遵循**"从只读到写、从简单到复杂"**：先 Test A/B/C 只读存量（不改库、风险低），最后 Test D 冒烟（要发起/办理，改库）。这样前面出问题时数据还是干净的，好定位。

⚠️ 全程一条红线：**test-0005 不能碰**（它是唯一在途样本），所以冒烟必须用新实例，且办理时按实例 id 精确锁定、绝不误办 test-0005 的任务。

### 5.2 Test A：approved 三账号隔离

**目的**：证明 `taskAssignee(me)` 真按人分——manager 有办结记录、employee/admin 没有。

```bash
for u in manager employee admin; do
  tok=$(cat "$SP/tok_$u.txt")
  echo "===== approved as $u ====="
  curl --noproxy '*' -s "$base/history/approved?current=1&size=10" \
       -H "Authorization: Bearer $tok" | python -m json.tool
done
```

**结果**：manager 1 条（`assignee='2'`、`endTime` 有值、`durationInMillis=8629374` 毫秒、`deleteReason=null`），employee 0、admin 0。✅

**顺带发现的疑点**：manager 那条的 `name` 字段是乱码（`缁忕...`，应为「经理审批」）。先记下，不打断主流程，留到冒烟用新数据交叉验证。

### 5.3 Test B/C：activities 轨迹（办结 + 在途）

**目的**：验证轨迹顺序、时间格式、以及二次排序是否化解撞车。

```bash
tok=$(cat "$SP/tok_manager.txt")
show() {   # 用 python 把每行压成一眼能看懂的格式（中文不转义）
python -c "import sys,json
d=json.load(sys.stdin)['data']
print('rows:',len(d))
for a in d:
    print(f\"  {a['startTime']} -> {str(a['endTime']):<19} [{a['activityType']:<13}] id={a['activityId']:<15} name={a['activityName']} assignee={a['assignee']}\")

}
echo "===== test-0004 (办结) ====="
curl --noproxy '*' -s "$base/history/instance/175ffafb-84bc-11f1-b2ab-5eea1d7fcc1d/activities" \
     -H "Authorization: Bearer $tok" | show
echo "===== test-0005 (在途) ====="
curl --noproxy '*' -s "$base/history/instance/6a897d3d-84d2-11f1-b2ab-5eea1d7fcc1d/activities" \
     -H "Authorization: Bearer $tok" | show
```

**结果**：
- test-0004（办结）5 行：`startEvent→flow1→managerApprove→flow2→endEvent`，全部 `endTime` 有值，含两条连线（决策②如实返回）。✅
- test-0005（在途）3 行：`managerApprove` 的 `endTime=None`（当前停留节点）。✅

### 5.4 Test D 第一次：失败（中文请求体编码坑）⚠️

**目的**：employee 发起新实例 → manager 办理 → 查历史，验证 `RU→HI` 搬运。

第一版脚本请求体里带了中文（`"reason":"年假"`、`"applicant":"李員工"`）：
```bash
resp=$(curl --noproxy '*' -s -X POST "$base/process-instance/start" \
  -H "Authorization: Bearer $EMP" -H "Content-Type: application/json" \
  -d '{"processDefinitionKey":"leaveProcess","businessKey":"test-0006","variables":{"days":3,"reason":"年假","applicant":"李員工"}}')
```

**现象**：
```
{"code":500,"msg":"系统繁忙，请稍后再试","data":null}
```
发起直接 500，兜底文案，看不出根因。后续 taskId 拿空、办理也跟着报错（错误信息还是一串乱码 `绯荤...`）。

**定位——去日志找真异常**（500 兜底把真相藏了，日志里才有）：
```bash
grep -nE "Exception|ERROR|Caused by" /tmp/backend-day14.log | tail -40
```
挖到根因：
```
com.fasterxml.jackson.core.JsonParseException: Invalid UTF-8 middle byte 0xea
  (through reference chain: StartProcessInstanceRequest["variables"])
```

**根因分析**：
- 报错是 Jackson 解析请求体时 `Invalid UTF-8 middle byte 0xea`，出错字段是 `variables`。
- `0xea` 是 GBK 编码里中文的字节。**Git Bash 在 Windows 上把我命令里的中文按 GBK 编码发出**，而后端按 UTF-8 解析 → 字节非法 → 解析失败 → 落到 500 兜底。
- **关键判断：这不是接口 bug，是我测试工具（Git Bash）的编码问题**。后端拒绝非法 UTF-8 是正确行为。而且 Test A 那个乱码也是同源现象——终端/编码在中文上不可靠。

**为什么能快速判定不是接口 bug**：报错发生在 **Jackson 反序列化阶段**（请求还没进 Service），且字节 `0xea` 明显是编码问题特征。接口逻辑根本没被执行到。

### 5.5 Test D 第二次：成功（改用 ASCII 绕过）

**绕过策略**：中文对 Day 14 的验证毫无必要（我要验的是流程流转，不是变量内容），直接把变量值全换成 ASCII，从源头消除编码变量：

```bash
# start：变量值全 ASCII
resp=$(curl --noproxy '*' -s -X POST "$base/process-instance/start" \
  -H "Authorization: Bearer $EMP" -H "Content-Type: application/json" \
  --data-binary '{"processDefinitionKey":"leaveProcess","businessKey":"test-0006","variables":{"days":3,"reason":"annual","applicant":"employee"}}')
INST=$(echo "$resp" | python -c "import sys,json;print(json.load(sys.stdin)['data']['id'])")

# todo：manager 待办（此刻含 test-0006 + test-0005 两条），只挑 test-0006 那条
todo=$(curl --noproxy '*' -s "$base/task/todo?current=1&size=10" -H "Authorization: Bearer $MGR")
TASK=$(echo "$todo" | python -c "
import sys,json
inst='$INST'
for t in json.load(sys.stdin)['data']['records']:
    if t['processInstanceId']==inst: print(t['id']); break
")

# complete：只办 test-0006 的任务（绝不碰 test-0005）
curl --noproxy '*' -s -X POST "$base/task/complete" -H "Authorization: Bearer $MGR" \
  -H "Content-Type: application/json" \
  --data-binary "{\"taskId\":\"$TASK\",\"variables\":{\"approved\":true,\"comment\":\"agree\"}}"

# 办理后各查：RU page / approved / activities
```

**结果全通过**：
| 步骤 | 结果 |
|---|---|
| 发起 | employee(userId=3) 发起 test-0006，`startUserId=3` ✅ |
| 待办 | 2 条并存，用 `processInstanceId==INST` 精确锁定 test-0006 的 task，**test-0005 安全** ✅ |
| 办理 | 200 success ✅ |
| RU 迁移 | 办理后 `process-instance/page` 只剩 test-0005，test-0006 已搬出 RU ✅ |
| approved | 从 1 → 2 条，**新条 `name='经理审批'` 中文正常** ✅ |
| 轨迹 | test-0006 五行全有 `endTime` ✅ |

> 🎯 **乱码疑点结案**：新发的 test-0006 在 approved 里中文正常，而 test-0004 乱码——坐实了 test-0004 那条是**遗留脏数据**（早期会话在某种编码条件下写入的），**接口逻辑零问题**。用"新数据对照旧数据"一举结案。

## 六、失败场景总结（专题）

| # | 现象 | 定位手段 | 根因 | 是接口 bug 吗 | 处理 |
|---|---|---|---|---|---|
| 1 | curl 打 9090 全返 **503** | `Get-NetTCPConnection` 证伪进程存在 + `--noproxy` 剥离代理 | 本机代理 `127.0.0.1:10808` 代 curl 应答；后端根本没起 | 否（环境）| 加 `--noproxy '*'`，并启动后端 |
| 2 | 请求路径 404 隐患 | 读 `application.yml` | `context-path=/workflow` 前缀漏了 | 否（用法）| URL 统一加 `/workflow` |
| 3 | 发起流程 **500 系统繁忙** | 去 `backend-day14.log` grep 真异常 | Git Bash 把中文按 **GBK** 发出，后端 UTF-8 解析失败（`Invalid UTF-8 0xea`）| **否（测试工具编码）** | 变量值改纯 ASCII 绕过 |
| 4 | approved 里 name 乱码 | 与 activities/新数据交叉对照 | test-0004 那条 `ACT_HI_TASKINST.NAME_` 是遗留脏数据 | 否（存量脏数据）| 记录，不阻断；前端渲染可忽略 |

**四个"失败"没有一个是 Day 14 接口逻辑的 bug**。它们分别属于：环境（代理）、用法（路径）、测试工具（编码）、存量数据。这正是实测的意义——把这些"接口之外的噪音"逐个排除，才能对"接口本身对不对"下结论。

## 七、方法论提炼（我是怎么想的）

1. **反直觉响应先怀疑"谁在应答"**。503 不是后端发的而是代理发的——用证伪（查进程）+ 剥离变量（`--noproxy`）拆穿假象。

2. **500 兜底文案没有信息量，真相在日志**。`系统繁忙` 是给用户看的，`grep Exception 日志` 才拿到 `Invalid UTF-8 0xea` 这种能定位的线索。

3. **看报错发生在哪一层，判断是不是自己代码的锅**。编码错误发生在 Jackson 反序列化（进 Service 之前），说明接口逻辑没被执行，锅在请求方。

4. **隔离变量**。中文变量对测试目标无关紧要，就换 ASCII 把编码这个干扰变量彻底拿掉——不纠缠"怎么让 Git Bash 发 UTF-8"，而是绕开它。

5. **新旧数据交叉对照定性**。同一字段旧数据乱码、新数据正常 → 判定是脏数据而非逻辑 bug。一次冒烟顺带结了乱码的案。

6. **等待用自适应探针而非盲等**。`curl --retry-connrefused` 让"等后端起来"精确到端口一开就走，不 sleep 盲赌时间。

7. **只读优先、写操作垫后、写操作精确制导**。先测不改库的查询，冒烟放最后；办理时按实例 id 锁定目标任务，守住"别碰 test-0005"的红线。
