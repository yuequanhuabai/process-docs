# 03 · 操作步骤

> 前提：02 的代码已进项目且 `mvnw compile` 通过。全程在 knife4j（`http://localhost:9090/workflow/doc.html`）操作，配合 SQL 客户端看表。
> 账号：`admin`(id=1) / `manager`(id=2) / `employee`(id=3)，密码均 `123456`。
> **本块是 P3 的收尾冒烟**：不只验历史两个接口，而是用双 token 走一遍完整生命周期（发起→办理→归档），亲眼看数据从 `ACT_RU_*` 搬进 `ACT_HI_*`。走通即关闭 P3。

---

## 步骤 0 · 准备干净现场

最好从"库里没有历史"开始，冒烟结论最干净。确认有流程定义可发起（Day 13 步骤 9 已恢复过 `leave.bpmn20.xml`）：

```sql
-- 有没有可发起的定义？预期至少 1 行 leaveProcess
SELECT ID_, KEY_, VERSION_, SUSPENSION_STATE_ FROM ACT_RE_PROCDEF WHERE KEY_ = 'leaveProcess';
-- 历史现状（记下当前行数，冒烟后好对照增量）
SELECT COUNT(*) FROM ACT_HI_PROCINST;
SELECT COUNT(*) FROM ACT_HI_TASKINST;
```

启动后端，确认「流程历史」分组出现在文档页，两个端点齐全。

## 步骤 1 · employee 发起（戳第一下，Day 12 接口）

1. `/auth/login` 用 **employee / 123456** 登录，token 粘进 Authorize；
2. 发起一条：

```json
POST /process-instance/start
{ "processDefinitionKey": "leaveProcess", "businessKey": "20001",
  "variables": { "days": 2, "reason": "冒烟测试" } }
```

**记下响应里的 `id`（记作 `{instanceId}`）。** 此刻 `ACT_RU_*` 有活数据、`ACT_HI_*` 也已经开始记（HI 边跑边写）：

```sql
-- 运行时：实例活着，任务挂着
SELECT COUNT(*) FROM ACT_RU_EXECUTION WHERE PROC_INST_ID_ = '{instanceId}';   -- 预期 2（A+B）
SELECT ASSIGNEE_, TASK_DEF_KEY_ FROM ACT_RU_TASK WHERE PROC_INST_ID_ = '{instanceId}';  -- 1 行, ASSIGNEE_ 空
-- 历史：实例行已在，但 END_TIME_ 还是 null（还没结束）
SELECT END_TIME_, DELETE_REASON_ FROM ACT_HI_PROCINST WHERE ID_ = '{instanceId}';       -- END_TIME_ 为 NULL
```

**这一步就印证了 01 文档②："HI 不是完结后才写的，发起瞬间就有行。"**

## 步骤 2 · 先查一次"运行中实例"的轨迹（关键认知点）

**别急着办**。用 **employee**（或任意）token 调轨迹接口，看活着的实例长什么样：

```
GET /history/instance/{instanceId}/activities
```

**预期**：返回 2 个节点——

| activityId | activityType | endTime |
|---|---|---|
| `startEvent` | startEvent | 有值（已经过） |
| `managerApprove` | userTask | **null**（← 正停在这儿） |

`managerApprove` 的 `endTime` 为 null，就是"当前停留节点"的标志（01 文档⑤）。前端画高亮流程图时，这个 null 就是"红点画哪儿"的依据。

## 步骤 3 · manager 办理（戳第二下，Day 13 接口）

1. `/auth/login` 换 **manager / 123456**，token 粘进 Authorize；
2. `GET /task/todo` 拿到那条待办的 `taskId`；
3. 办理：

```json
POST /task/complete
{ "taskId": "{taskId}", "variables": { "approved": true, "comment": "冒烟通过" } }
```

**预期** 200，日志 `任务已办理：…, assignee=2`。此刻实例撞 endEvent 完结，运行时表清空、数据全搬进历史：

```sql
SELECT COUNT(*) FROM ACT_RU_EXECUTION WHERE PROC_INST_ID_ = '{instanceId}';  -- 预期 0
SELECT END_TIME_, DELETE_REASON_ FROM ACT_HI_PROCINST WHERE ID_ = '{instanceId}';  -- END_TIME_ 有值, DELETE_REASON_ NULL
```

## 步骤 4 · 我的已审批（本块主接口）

**仍用 manager 的 token**：

```
GET /history/approved
```

**预期**：`total≥1`，records 里有刚办的那条——

| 字段 | 预期值 |
|---|---|
| `id` | 任务 id |
| `name` | 经理审批 |
| `taskDefinitionKey` | `managerApprove` |
| `assignee` | **`2`**（← Day 13 自动认领的兑现，这一条是本块能跑的命根子） |
| `processInstanceId` | `{instanceId}` |
| `startTime` / `endTime` | 都格式化成 `yyyy-MM-dd HH:mm:ss` |
| `durationInMillis` | 一个毫秒数（发起到办理的间隔） |
| `deleteReason` | `null`（正常办结） |

**若 `assignee` 是 null 或这里查不到**：说明 Day 13 的自动认领没生效，回头查 `complete` 里的 `claim`（01 文档④反复强调的那个前提）。

## 步骤 5 · 换 token 验隔离（关键对照）

同 Day 13 的套路——只看 manager 查得到不够，得看别人查不到：

| token | `GET /history/approved` 预期 |
|---|---|
| **manager** | ≥1 条 ✅（他办的） |
| **employee** | **0 条**（他只发起没审批，`ASSIGNEE_` 里没有他） |
| **admin** | **0 条** |

三行都对上，才证明 `taskAssignee(me)` 的过滤是真的按人分的，排除"库里就一条谁查都是它"的假阳性。

## 步骤 6 · 办结实例的完整轨迹

任意 token，`GET /history/instance/{instanceId}/activities`。

**预期**：3 个节点，`endTime` 全部有值——

```
startEvent（员工发起）    → managerApprove（经理审批，assignee=2） → endEvent（结束）
```

和步骤 2 对照：那时 `managerApprove` 的 `endTime` 是 null（正停着），现在有值了（办完了），还多出 `endEvent`。**同一个接口，实例活着和办完各查一次，就把"边跑边记"看透了。**

对照 SQL：

```sql
SELECT ACT_ID_, ACT_NAME_, ACT_TYPE_, ASSIGNEE_, START_TIME_, END_TIME_
FROM ACT_HI_ACTINST WHERE PROC_INST_ID_ = '{instanceId}' ORDER BY START_TIME_;
```

## 步骤 7 · 终止的实例长什么样（回收 Day 13⑨）

1. 用 **employee** 再发一条，记 `{instanceId2}`；
2. `DELETE /process-instance/{instanceId2}?reason=历史冒烟-测试终止`（Day 12 的 terminate）；
3. 对照两条实例的收尾状态：

```sql
SELECT ID_, END_TIME_, DELETE_REASON_ FROM ACT_HI_PROCINST
WHERE ID_ IN ('{instanceId}', '{instanceId2}');
```

**预期**：

| 实例 | `END_TIME_` | `DELETE_REASON_` |
|---|---|---|
| 办完的 `{instanceId}` | 有值 | **NULL** ← 已完成 |
| 终止的 `{instanceId2}` | 有值 | **历史冒烟-测试终止** ← 已终止 |

这一列就是历史列表将来显示"已完成/已终止"标签的判据（01 文档⑥）。再查 `{instanceId2}` 的轨迹，会看到它停在 `managerApprove`、没有 `endEvent`（没走到结束就被终止）。

## 步骤 8 · 冒烟总账（P3 关闭前的整体确认）

一句话复盘这趟走过的路，确认四个门面串成了一条线：

```
employee 发起 (RuntimeService)  →  ACT_RU_* 出现，ACT_HI_* 开始记
manager  办理 (TaskService)     →  ACT_RU_* 清空，数据搬进 ACT_HI_*
manager  查已审批 (HistoryService) →  ACT_HI_TASKINST 按 ASSIGNEE_ 查到
任意     查轨迹  (HistoryService) →  ACT_HI_ACTINST 按 START_TIME_ 排出流转
```

对照步骤 0 记的历史行数，`ACT_HI_PROCINST` 应比开始时 +2（一条办完、一条终止），`ACT_HI_TASKINST` 至少 +1（manager 办的那条）。
