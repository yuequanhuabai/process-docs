## 一、为什么要改（问题是什么）

`GET /history/approved` 现在返回的每一行长这样：

```json
{ "id": "...", "name": "经理审批", "startTime": "...", "endTime": "2026-08-14 15:22:07", "durationInMillis": 116000 }
```

**「经理审批」是哪个申请的经理审批？** 看不出来。翻到第二页时，十行全叫「经理审批」，除了时间没有任何区分度——而"分得清我批过哪些单子"正是这个页面存在的唯一理由。

轨迹接口同理：`assignee` 回的是 `"2"` 这样的 userId 数字，界面上直接摆出来没有意义。

所以补两处：

| 接口 | 补什么 |
|---|---|
| `GET /history/approved` | `processDefinitionName`（流程名）、`businessKey`（业务标识）、`startUserName`（发起人姓名） |
| `GET /history/instance/{id}/activities` | `assigneeName`（办理人姓名；**原 `assignee` 保留**，见第三节） |

## 二、★ 关键认知：这次的数据在 HI，不在 RU

**这是本次与 Day 17 唯一但致命的差异，照抄 Day 17 的 `enrich()` 必然翻车。**

Day 17 待办任务补字段时，路径是：

```
Task ──PROC_INST_ID_──▶ RuntimeService 查 ACT_RU_EXECUTION ──START_USER_ID_──▶ sys_user
```

`RuntimeService` 查得到，是因为**待办任务必属在途实例**——任务行还在 `ACT_RU_TASK`，它的实例就必然还在 `ACT_RU_EXECUTION`。

**已审批任务反过来**：我批完的任务，其所属实例**大概率已经办结**（后续节点也走完了），那一行**早已从 `ACT_RU_EXECUTION` 删掉**，只剩 `ACT_HI_PROCINST` 里的历史行。

```
HistoricTaskInstance ──PROC_INST_ID_──▶ HistoryService 查 ACT_HI_PROCINST ──START_USER_ID_──▶ sys_user
                                        （流程名 / businessKey / 发起人 id）
```

| | Day 17 `FlowableTaskServiceImpl.enrich()` | 本次 `FlowableHistoryServiceImpl.enrich()` |
|---|---|---|
| 起点 | `TaskVO`（RU 任务） | `ApprovedTaskVO`（HI 任务） |
| 查实例用什么 | `runtimeService.createProcessInstanceQuery()` | **`historyService.createHistoricProcessInstanceQuery()`** |
| 结果类型 | `ProcessInstance` | **`HistoricProcessInstance`** |
| 照抄的后果 | —— | **整页三字段恒 null**（实例已结束，RU 里查不到；`instanceMap.get()` 返回 null 走 `continue`）——编译全绿、不报错、不告警 |

> 📌 **这会是本项目第三次"编译全绿、字段恒 null"的静默失效**（前两次：08-11 的 `.muted` 样式选不中、08-12 的 `detail()` 返回未 enrich 的新对象 + `toPage()` 漏挂）。前两次都是靠**可数的自查断言**抓出来的，这次的断言写在 `09` 的 Step 5。
>
> 🔎 **API 已查证**（《讲解规则》第五节）：`HistoricProcessInstanceQuery.processInstanceIds(Set<String>)` 存在，`javap` 打 `flowable-engine-7.1.0.jar` 确认过签名（参数是 **`Set`** 不是 `List`）。`HistoricProcessInstance` 上的 `getProcessDefinitionName()` / `getBusinessKey()` / `getStartUserId()` 三个 getter，Day 16 的 `ProcessInstanceVO.of(HistoricProcessInstance)`（`ProcessInstanceVO.java:77-90`）已经在用，不是猜的。

## 三、改动清单（3 个文件，接口签名零变化）

### 1. `dto/response/ApprovedTaskVO.java`：补 3 个字段

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `processDefinitionName` | `String` | `HistoricProcessInstance.getProcessDefinitionName()` | 「报销流程」这种中文名 |

### 2. `dto/response/ActivityTraceVO.java`：补 1 个字段

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `assigneeName` | `String` | `assignee`（userId）→ 查 `sys_user` | 仅 userTask 行有值；事件/网关行恒 null |

> **为什么新增字段而不是就地把 `assignee` 的值换成姓名**（需求评审已定方案 A）：
> ① `assignee` 这个名字在 Flowable 语境里就是"办理人 id"，装姓名属于**名不副实**，半年后会误导；
> ② userId 留着有用——前端将来想做"高亮我办过的节点"，比的是 id 不是姓名（姓名会重名）；
> ③ 多一个字段的成本约等于零。

### 3. `service/impl/FlowableHistoryServiceImpl.java`

- 注入 `SystemUserMapper`（批量换姓名）
- 新增 `enrich(List<ApprovedTaskVO>)`：已审批列表的三字段
- 新增 `enrichAssigneeName(List<ActivityTraceVO>)`：轨迹的办理人姓名
- 两个方法共用一个私有 `nameMap(Set<Long>)`（第四节）
- `approved()` 末尾挂 `enrich(page.getRecords())`；`activities()` return 前挂 `enrichAssigneeName(vos)`

## 四、批量回填：两个 enrich，各自不超过 2 次查询

天真写法是遍历行逐条 `singleResult()` 查实例、`selectById()` 查用户——一页 10 条就是 20 次查询。姿势与 Day 16/17 相同：**先收集 → 一次批量 → 转 Map → 再回填**。

**`enrich(List<ApprovedTaskVO>)`：固定 2 次**

```
① 收集这页所有 processInstanceId → Set<String>
   historyService.createHistoricProcessInstanceQuery().processInstanceIds(ids).list()   ← 1 次
   转 Map<instanceId, HistoricProcessInstance>
② 从①的实例里收集 startUserId → Set<Long>
   nameMap(userIds)                                                                     ← 1 次
③ 遍历 vos 回填三字段（取不到实例就 continue）
```

**`enrichAssigneeName(List<ActivityTraceVO>)`：固定 1 次**（轨迹本来就同属一个实例，不需要查实例）

```
① 收集所有非空 assignee → Set<Long>
   nameMap(userIds)                                                                     ← 1 次
② 遍历回填 assigneeName
```

**共用的 `nameMap(Set<Long>) → Map<String, String>`** 就是 Day 16/17 那段，三个坑一个不少：

| 坑 | 处理 |
|---|---|
| `START_USER_ID_` / `ASSIGNEE_` 存的是 Long 的**字符串**形态 | 查库前 `Long.valueOf` 转过去，转 Map 时 `String.valueOf` 转回来，**两头都要转** |
| MP 的 `in()` 遇空集合拼出非法 SQL（`IN ()`） | `userIds.isEmpty() → Map.of()` 短路 |
| `Collectors.toMap` 的 value 为 null 直接 **NPE**（不是存个 null），而 `real_name` 列可空 | `u -> u.getRealName() == null ? u.getUsername() : u.getRealName()` |

### ⚠️ 轨迹这里多一个 Day 16/17 没有的坑：`assignee` 未必是数字

Day 16 的注释写得很清楚：`Long.valueOf` 不设防**是有前提的**——`START_USER_ID_` 的唯一写入口是 `start()` 里的 `Authentication.setAuthenticatedUserId(UserContext.userId())`，恒为数字。

**轨迹的 `ASSIGNEE_` 没有这个前提**。它有两个写入口：

1. `complete()` 里的 `taskService.claim(task.getId(), userId)` —— 数字，安全；
2. **BPMN 里静态写死的 `flowable:assignee="..."`** —— 我们四个模板的注释里就白纸黑字写着「若想固定指派某个人，可改为 `flowable:assignee="具体用户名"`」（`leave.bpmn20.xml:7` 等四处）。**照这句话改一次模板，`ASSIGNEE_` 里就会出现 `"manager"` 这种非数字值，`Long.valueOf` 当场 `NumberFormatException`，整个轨迹接口 500。**

**处理**：收集时加一道纯数字过滤，非数字的 userId 直接不参与查库 → `assigneeName` 为 null → 前端回退显示原 `assignee`。成本一行，换掉一个将来必踩的雷。

## 五、第三处重复到了：抽不抽公共方法？

Day 17 的 `07` 文档第四节留过一句话：

> 「②段的 userId → nameMap 与 Day 16 基本逐行重复……**触发点是「第三处要用、且重复看着难受了」**。Day 18 已审批页如果还要第三份，届时再收编成一个公共的姓名批量服务。」

**现在正是第三处**（第四处也在本篇里：轨迹）。按约定该评估了。

**本篇结论：本次只在 `FlowableHistoryServiceImpl` 内部抽一个私有 `nameMap()` 给两个方法共用（本类内不重复），跨类的收编推到 P4 收尾 / P8 评估。**

理由：

| # | 理由 |
|---|---|
| 1 | Day 16、17 的代码**刚验收关闭**（08-11、08-14），动它们要连带重测两条已关闭的验收链路。P4 只剩这一天，不在收官日翻修已验收的代码 |
| 2 | 跨类收编要先定**放哪层**（`util` 静态方法？`@Component` 服务？Mapper 上加个默认方法？）——这是个设计问题，值得单独想，不该塞进一个"补字段"的任务里 |
| 3 | 触发点的判据原文是「第三处要用**且重复看着难受了**」，两个条件。第一个满足了，第二个由你说了算——如果现在看着已经难受，见下面的改动清单，随时可以做 |

**将来收编的改动清单（4 处）**：新建 `UserNameResolver`（暂定 `service/support/` 下，`@Component`，注入 `SystemUserMapper`，暴露 `Map<String,String> namesOf(Collection<Long> ids)`）→ 替换 `ProcessInstanceServiceImpl.enrich()`、`FlowableTaskServiceImpl.enrich()`、`FlowableHistoryServiceImpl.nameMap()` 三处调用。**这条已登记进断点文档小尾巴清单（P4 收尾时评估）。**
