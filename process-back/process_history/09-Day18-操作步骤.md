## Step 1 · `ApprovedTaskVO.java`：补 3 个字段（只加声明，不动 `of()`）

**做什么**：加 `processDefinitionName` / `businessKey` / `startUserName` 三个 `String`，各配 `@Schema`（description 写清来源——knife4j 上这行字就是给前端看的接口文档）。

**建议**：三个新字段单独一段，上面加一行注释「`ACT_HI_TASKINST` 上没有，由 `enrich()` 从 `ACT_HI_PROCINST` 批量回填」——半年后回来看的人（还是你）才知道为什么工厂方法不填它们。

**自测**：编译通过；重启后 knife4j 的 `ApprovedTaskVO` schema 里能看到三个新字段（值还是 null，正常）。

## Step 4 · 新增两个 enrich + 一个共用的 `nameMap()`

这步是本次的主体，**分三小步写，每写完一小步编译一次**。

### 4a · 先写共用的 `private Map<String, String> nameMap(Set<Long> userIds)`

整段照 Day 16 `ProcessInstanceServiceImpl.enrich()` 的①段 / Day 17 `FlowableTaskServiceImpl.enrich()` 的②段抄，三个坑一个不少（08 第四节的表）：

1. `userIds.isEmpty()` → `return Map.of()` 短路（MP 的 `in()` 遇空集合拼非法 SQL）；
2. `new LambdaQueryWrapper<SysUser>().in(SysUser::getId, userIds)` 一次查出；
3. `Collectors.toMap(u -> String.valueOf(u.getId()), u -> u.getRealName() == null ? u.getUsername() : u.getRealName())` —— **value 不能直接写 `SysUser::getRealName`**，`toMap` 内部走 `HashMap.merge`，value 为 null 是**直接抛 NPE**（不是存个 null 进去），而 `real_name` 列可空。

> 为什么这次抽成方法：本类里**两个** enrich 都要用（Day 16/17 各只用一次，所以没抽）。跨类的收编推到 P4 收尾，理由见 `08` 第五节。

### 4b · `private void enrich(List<ApprovedTaskVO> vos)`

1. **开头判空**：`vos.isEmpty()` 直接 return。这不只是省事——下一行的 `processInstanceIds()` **吃不得空集合**（引擎会抛"Set of process instance ids is empty"）。
2. **① 段：任务 → 所属实例**：
   - 收集所有 `getProcessInstanceId()` → `Set<String>`（HI 任务的 instanceId 非空，不用 filter）
   - ⚠️ **这里是本次最容易翻车的一行**：用 **`historyService.createHistoricProcessInstanceQuery().processInstanceIds(ids).list()`**，**不是** `runtimeService`。照抄 Day 17 的写法编译一样能过，但已办结的实例在 RU 里查不到 ⇒ 整页三字段恒 null。
   - 参数类型是 **`Set<String>`**（`javap` 查证过），别传 `List`
   - 转 `Map<String, HistoricProcessInstance>`，key `HistoricProcessInstance::getId`，value `i -> i`
3. **② 段：发起人姓名**：从①的 `Map.values()` 收集 `getStartUserId()` → `filter(Objects::nonNull)` → `Long::valueOf` → `nameMap(...)`
4. **回填循环**：遍历 `vos`，从①的 Map 取实例——**取不到就 `continue`**（理论上不会发生，但防御一手，免得哪天引擎行为变了整页 NPE）；取到就 set 三个字段，`startUserName` 从②的 Map 里 `get(hi.getStartUserId())`。

### 4c · `private void enrichAssigneeName(List<ActivityTraceVO> vos)`

比 4b 简单：轨迹本来就同属一个实例，**不需要查实例，只查用户，固定 1 次**。

1. 判空 return；
2. 收集所有 `getAssignee()` → `filter(Objects::nonNull)` → **⚠️ 再加一道纯数字过滤** → `Long::valueOf` → `nameMap(...)`；
3. 遍历回填 `assigneeName`（`nameMap.get(vo.getAssignee())`，取不到就是 null，正常）。

> ⚠️ **那道纯数字过滤是本次唯一一个 Day 16/17 没有的新防御**，别省。`ASSIGNEE_` 不像 `START_USER_ID_` 只有一个数字写入口——四个 BPMN 模板的注释里就写着「若想固定指派某个人，可改为 `flowable:assignee="具体用户名"`」（`leave.bpmn20.xml:7` 等）。照那句话改一次模板，`ASSIGNEE_` 里就会出现 `"manager"`，`Long.valueOf` 当场 `NumberFormatException`，**整个轨迹接口 500**。加了这道过滤，最坏结果只是 `assigneeName` 为 null、前端回退显示原值。

**自测**：编译过。此时三个方法都还没人调用，IDE 会给"方法未使用"的灰色提示——**正常，下一步才挂**。

## Step 5 · 挂上去：`approved()` 与 `activities()` 两处

**做什么**：

1. `approved()` 的 `page.setRecords(...)` 之后、`return page;` 之前，加 `enrich(page.getRecords());`
2. `activities()` 现在是**一条 return 链**（`list.stream().sorted(...).map(...).toList()`）。要拆成三行：先把结果收进 `List<ActivityTraceVO> vos`，再 `enrichAssigneeName(vos)`，最后 `return vos;`

**坑（Day 17 在这一步栽过两次，原样适用）**：

- **别在 return 表达式里改**。Day 17 的 `detail()` 就是写成 `enrich(List.of(vo)); return TaskFormVO.of(...);` —— 又造了个新对象，把填好的那个丢了。**填谁就返回谁。**
- `.toList()` 返回的是**不可变列表**，但我们只改元素内部字段、不增删元素，所以没问题；真要 `add/remove` 得先 `new ArrayList<>(...)`。
- `approved()` 里 `count()` / `listPage()` / 排序**一个字不动**；`activities()` 里那段 `TRANSACTION_ORDER_` 二次排序（`Comparator.thenComparing(..., nullsLast(...))`）**原样保留**，别顺手"简化"掉——它是修过一次的兜底。

**✅ 自测断言（这次的可数清单，照做别跳）**：

| 断言 | 期望 |
|---|---|
| 全项目搜 `enrich(` | **2 行** = 1 处定义 + 1 处调用（`approved()`） |
| 全项目搜 `enrichAssigneeName(` | **2 行** = 1 处定义 + 1 处调用（`activities()`） |
| 全项目搜 `nameMap(` | **3 行** = 1 处定义 + 2 处调用（两个 enrich 各一） |
| 全项目搜 `runtimeService` in `FlowableHistoryServiceImpl` | **0 行**（出现了就是照抄 Day 17 了） |

> 数不对就别往下走。Day 17 那两处静默失效（`detail()` 返回新对象、`toPage()` 漏挂）就是靠这种"可数断言"抓出来的，而当时的文档里本来也写了这条清单，跳过没做才踩的。
