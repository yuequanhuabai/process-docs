# 00 · 领域概念与术语表（Glossary）

> 用途：在动手写流程引擎相关代码前，先建立**词汇地基**。对应《重写分析维度参考》的维度 **A1 / 序号 00**——"词汇不牢，看架构只是背名词"。
> 读法：从第 0 层的核心类比出发，逐层往下，每个术语都往那条主线上挂。
> 配套：架构 `01`、模块职责 `03`、数据模型 `04`；落地排期见 `05`。

---

## 第 0 层 · 一个贯穿全局的类比（最重要，先记这个）

> **流程定义（Process Definition）= 类（class）；流程实例（Process Instance）= 对象（object）**

- 画一张"请假审批流程图"并部署 → 得到一个**流程定义**，像写好 `class LeaveProcess`。它是**模板/蓝图**，静态的，画一次存起来。
- 张三点"发起请假" → 引擎按那张图 `new` 出一个**流程实例**，像 `new LeaveProcess()`。李四发起 → 又一个实例。**同一个定义能跑出无数个实例**，各自独立往前走。

这条主线撑起后面所有术语。下面每个词都往它上面挂。

---

## 第 1 层 · BPMN——那张"图"是什么

**BPMN**（Business Process Model and Notation，业务流程建模标注）是一套**国际标准的画流程图规范**，规定了圆圈/方块/菱形各代表什么。好处：图长得统一、能被引擎读懂。

部署的 `.bpmn20.xml` 本质就是**一张 BPMN 图的 XML 描述**——前端 bpmn-js 把它画成图给人看，后端 Flowable 把它读成可执行的流程。

图里的**四类基本元素**：

| 元素 | 图形 | 是什么 | 请假流程里的例子 |
|---|---|---|---|
| **事件 Event** | 圆圈 | 流程的**起点/终点**或中途触发点 | 开始事件（发起）、结束事件（审批完） |
| **任务 Task / 活动 Activity** | 圆角方块 | 一个**要做的事** | "填写请假单""经理审批" |
| **网关 Gateway** | 菱形 | **分支/汇合**的路口，决定往哪走 | "天数>3？是→总监审批，否→直接通过" |
| **顺序流 Sequence Flow** | 带箭头的线 | 连接上面元素，规定**先后顺序** | 从"填单"指向"经理审批"的箭头 |

**任务**里最关键的一种是 **UserTask（用户任务）**——需要**人来办理**的任务（审批、填单）。相对的是 ServiceTask（系统自动执行，如调接口发邮件）。本 Demo 主要跟 UserTask 打交道。

## 第 2 层 · 运行时——实例"动起来"后的概念

流程实例 `new` 出来后开始往前流，这层是它流动过程中的词：

- **任务 / 待办（Task）**：实例走到一个 UserTask 时，引擎**生成一条待办任务**挂给某人，就是前端"待办列表"里的一行。
  - ⚠️ 区分：BPMN 图里的 UserTask 是**定义**（蓝图上的节点），运行时生成的 Task 是**实例**（此刻某人要办的这一件）——又是"类 vs 对象"。
- **办理人 / 受理人（Assignee）**：这条待办**分给了谁**。张三的请假单，assignee 是他经理。
- **认领（Claim）**：任务先分给一**组人**（候选人 candidate），谁先点"认领"就归谁办，避免多人重复处理。Demo 若简单可直接指定 assignee，跳过认领。
- **办理 / 完成任务（Complete）**：办理人点"同意/驳回"提交 → `complete` 这条任务 → 引擎**销毁当前任务**，按顺序流和网关走到下一节点，可能又生成新任务。流程就是这样一格一格往前跳。
- **流程变量（Variables）**：实例身上携带的**数据口袋**（键值对）。发起时塞进"请假天数=5、事由=…"，网关靠读 `天数>3` 决定分支，审批人也能看/追加。变量是"流程"与"业务数据"之间的桥。
- **流转 / 流转历史**：实例从哪个节点走到哪个节点的轨迹。

## 第 3 层 · 从"画完"到"能跑"——部署相关

- **部署（Deployment）**：把 `.bpmn20.xml` **交给引擎、存进库、变成可用的流程定义**这个动作。`check-process-definitions: true` 就是启动时自动部署 `resources/processes/` 下的文件；前端设计器画完点"保存部署"走的也是这条路。
- **流程定义 Key vs 版本（Version）**：同一流程改图重新部署，引擎不覆盖而是**版本号 +1**（v1、v2 并存），`key` 不变。老实例继续跑老版本，新发起的用新版本——防止改流程把在途的搞乱。

---

## 第 4 层 · Flowable 怎么把这些暴露给你——Service API

Flowable 把能力切成几个 **Service**（Spring 注入即用），名字直接对应上面的概念：

| Service | 管什么 | 对应概念 |
|---|---|---|
| `RepositoryService` | **部署、流程定义**的增删查 | 第 3 层 |
| `RuntimeService` | **发起流程实例**、管运行中的实例、读写变量 | 第 0/2 层 |
| `TaskService` | **待办任务**：查、认领、办理（complete） | 第 2 层 |
| `HistoryService` | **历史**：已结束的实例/任务、流转轨迹 | 归档查询 |

后面 P4/P5/P6 写的 `ProcessInstanceService`、`TaskController` 等，内部基本就是包一层这四个 Service。

## 第 5 层 · 数据落哪——`ACT_*` 表家族（衔接维度 A2 / 文档 04）

Flowable 自动建的 30 多张表，**前缀分组**一看就懂它是"状态机 + 持久化"：

| 前缀 | 含义 | 存什么 | 对应概念 |
|---|---|---|---|
| `ACT_RE_*` | **RE**pository 仓库 | 流程**定义**、部署的 BPMN | 蓝图（类） |
| `ACT_RU_*` | **RU**ntime 运行时 | **在途**的实例、待办任务、变量 | 正在跑的对象 |
| `ACT_HI_*` | **HI**story 历史 | **已完成**的实例/任务/轨迹 | 归档 |
| `ACT_GE_*` | **GE**neral 通用 | 通用数据、附件、属性 | 杂项 |

主线：**部署** → 进 `ACT_RE_*`；**发起并运行** → 进 `ACT_RU_*`；**流程结束** → 从 `RU` 移到 `HI_*` 归档。`05` 排期里 Day 10 验收的"`ACT_RE_*` 有记录"，就是验证部署这一步落库成功。

---

## 小结 · 一条串起所有词的主线

> 用 **BPMN** 画图 → **部署**成**流程定义**（存 `ACT_RE`）→ 某人发起 `new` 出**流程实例**（存 `ACT_RU`）→ 走到 **UserTask** 生成**待办任务**分给**办理人**，携带**流程变量** → 办理人 **complete** → 按**顺序流/网关**流转到下一节点 → 全部走完实例结束，数据归档到 `ACT_HI`。全程通过 **RepositoryService / RuntimeService / TaskService / HistoryService** 操作。

## 术语速查表

| 术语 | 英文 | 一句话 |
|---|---|---|
| 流程定义 | Process Definition | 流程的模板/蓝图（≈ 类） |
| 流程实例 | Process Instance | 按定义跑起来的一次执行（≈ 对象） |
| BPMN | — | 画流程图的国际标准规范 |
| 事件 | Event | 起点/终点/中途触发（圆圈） |
| 用户任务 | UserTask | 需要人办理的节点 |
| 服务任务 | ServiceTask | 系统自动执行的节点 |
| 网关 | Gateway | 分支/汇合的路口（菱形） |
| 顺序流 | Sequence Flow | 规定先后的箭头 |
| 待办任务 | Task | 运行时分给某人的一条待办 |
| 办理人 | Assignee | 待办分给了谁 |
| 认领 | Claim | 从候选人里领走任务归自己办 |
| 完成任务 | Complete | 办理提交、推动流程往下走 |
| 流程变量 | Variables | 实例携带的键值数据，驱动分支 |

| 版本 | Version | 同 key 重新部署则版本 +1，并存 |
| RepositoryService | — | 管部署与流程定义 |
| RuntimeService | — | 管发起实例与运行时变量 |
| TaskService | — | 管待办任务 |
| HistoryService | — | 管历史与轨迹 |
