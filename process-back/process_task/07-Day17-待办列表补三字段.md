## 一、为什么要改（问题是什么）

Day 13 写的 `TaskVO` 的 8 个字段全部来自 `Task` 对象（`ACT_RU_TASK` 一张表），能示人的只有两个：

| 页面想要的列 | TaskVO 有吗 |
|---|---|
| 任务名称（「经理审批」） | ✅ `name` |
| 创建时间 | ✅ `createTime` |
| **流程名称**（「报销流程」） | ❌ 只有 `processDefinitionId`（形如 `reimburseProcess:1:xxx`） |
| **业务标识** | ❌ |
| **发起人姓名** | ❌ |

**后果**：manager 打开待办页，每行只有「经理审批 + 时间」——三条待办分不清是谁发起的哪个流程的申请，必须逐条点开详情靠 `variables.initiator` 辨认，列表的辨识价值归零。Day 13 时这无所谓（knife4j 里调接口的人就是你自己），界面化之后就不行了。

办理弹窗还要显示「流程 / 节点」和「业务标识」两行（原型第 ③ 节），所以**详情接口同样要补**——别只补列表。

## 二、关键认知：任务表不装业务上下文

`ACT_RU_TASK` 上只有一个 `PROC_INST_ID_` 外键，**流程名称、businessKey、发起人 id 都在所属实例上**（`ACT_RU_EXECUTION` 的实例行），姓名则再隔一跳在 `sys_user`。所以补这三个字段的路径是：

```
Task ──PROC_INST_ID_──▶ ProcessInstance ──START_USER_ID_──▶ sys_user.real_name
                          （流程名 / businessKey / 发起人 id）
```

和 Day 16 的 `enrich()` 对照着看，**方向正好相反**：

| | Day 16 `ProcessInstanceServiceImpl.enrich()` | 本次 `FlowableTaskServiceImpl.enrich()` |
|---|---|---|
| 起点 | 实例 VO | 任务 VO |
| 补什么 | 当前节点名（实例 → 任务）+ 发起人姓名 | 流程名 / businessKey / 发起人姓名（任务 → 实例 → 用户） |
| 查 RU 还是 HI | 实例来自 RU 或 HI 两种源 | **只查 RU 就够**——待办任务必属在途实例（任务行还在 `ACT_RU_TASK`，其实例必在 `ACT_RU_EXECUTION`），不用碰 HI |

## 三、改动清单（2 个文件，接口签名零变化）

### 1. `dto/response/TaskVO.java`：补 3 个字段

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `processDefinitionName` | `String` | `ProcessInstance.getProcessDefinitionName()` | 「报销流程」这种中文名 |
| `businessKey` | `String` | `ProcessInstance.getBusinessKey()` | 发起时选填，没填就是 null，前端拿 `—` 占位 |
| `startUserName` | `String` | 实例的 `startUserId` → 查 `sys_user` 换姓名 | 无姓名回退 `username`（同 Day 16 的兜底） |

> ⚠️ **`of()` / `fill()` 不碰**：`Task` 对象上没有这三样数据，工厂方法里拿不到。要是在 `fill()` 里逐条去查实例，就是 N+1 的第一步——这三个字段统一由 Service 层的 `enrich()` **批量**回填。
>
> `TaskFormVO extends TaskVO`，三个字段**自动继承**，详情接口不需要另改 VO。

### 2. `service/impl/FlowableTaskServiceImpl.java`

- 注入两个新依赖：`RuntimeService`（批量查所属实例）、`SystemUserMapper`（批量换姓名）
- 新增私有方法 `enrich(List<TaskVO>)`（第四节）
- `toPage()` 末尾挂 `enrich(page.getRecords())` —— 列表走这里
- `detail()` 在 return 前挂 `enrich(List.of(vo))` —— **别漏**，漏了会出现"列表有流程名、弹窗反而没有"的怪相

> 与 Day 16 的一个重要不同：**`FlowableTaskService` 接口和 `TaskController` 一个字都不用改**（没加参数、没改签名）。这省事，但也意味着**编译器不会帮你导航**——Day 16 改接口签名后红叉就是待办清单，这次没有红叉，`detail()` 忘挂 enrich 不会有任何编译提示，全靠清单自查。

## 四、⚠️ 批量回填：整页固定 2 次查询

天真写法是遍历任务逐条 `singleResult()` 查实例、`selectById()` 查用户——一页 10 条就是 20 次查询。正确姿势与 Day 16 相同，「先收集、一次批量、转 Map、再回填」：

**① 任务 → 所属实例**（1 次）
```
收集这页所有 processInstanceId → Set
runtimeService.createProcessInstanceQuery().processInstanceIds(ids) 一次查出
转 Map<instanceId, ProcessInstance>
```

**② 发起人姓名**（1 次）
```
从上一步的实例里收集 startUserId → Long 集合
一次 LambdaQueryWrapper .in(SysUser::getId, ids) 查出
转 Map<userId 字符串, realName>（Day 16 的三个坑原样适用：两头转型 / 空集合短路 / realName 可空兜底）
```

> ⚠️ **方法名别照抄 Day 16**：Day 16 在 `TaskQuery` 上用的是 `processInstanceIdIn(List)`；这次在 `ProcessInstanceQuery` 上，方法叫 **`processInstanceIds(Set)`**——名字和参数类型都不同，写的时候 IDE 补全确认。

### 已知重复，暂不抽取

②段的「userId 集合 → nameMap」与 `ProcessInstanceServiceImpl.enrich()` 里那段**基本逐行重复**。刻意不抽公共方法——与 `toPage`/`toHiPage` 那对重复同一个哲学：**触发点是「第三处要用、且重复看着难受了」**，不是「写第二遍了」。Day 18 已审批页如果还要第三份，届时再收编成一个公共的姓名批量服务，改动点那时登记。

## 五、验收（knife4j，先后端后前端）

**这一步必须先做完再动前端**，否则前端三列全空，你会以为自己前端写错了。

1. 起后端（改了代码要**重启**：`./mvnw spring-boot:run`，`http://localhost:9090/workflow/doc.html`）
2. **manager 账号** Authorize（knife4j 换账号 = 重新 Authorize，忘了切会出现"待办查不到"的假故障）
3. 调 `GET /task/todo`——重点看每行：
   - [ ] `processDefinitionName` 是「请假流程」这种中文名，不是 `leaveProcess:1:xxx`
   - [ ] `startUserName` 是「李員工」不是 `"3"`，也不是 null
   - [ ] `businessKey`：发起时填过的行有值，没填的行是 null（null 是对的，别当 bug 修）
4. 取一条的 `id` 调 `GET /task/{taskId}`——同样看到三字段 + `variables`（弹窗只读区两样都靠它）
5. **`POST /task/complete` 零改动，不必测**。⚠️ 也**别在 knife4j 里顺手办任务**——库里停在 `managerApprove` 的样本是留给前端页面验收用的（Day 17 的验收动作就是在界面上办它），现在办光了到时候还得重新造。

全绿后：回填 `plan/P4` Day 17 的后端小改那条，开工前端（`../../process-front/process_task/01-页面定位与修改点.md`）。
