# 01 · 待办任务办理原理

> 对应排期 Day 13「待办任务接口」。读完本文再进 `02-前置任务与完整代码`。
> Day 12 你学会了**戳第一下**（发起：从 StartEvent 推到第一个等待态）；这一块学**戳第二下**（办理：从当前等待态推到下一个）。两次戳之间，流程状态就躺在 `ACT_RU_*` 里——这一块把它推完。

---

## ① 换门面：TaskService

| Day | 门面 | 管辖 | 干的事 |
|---|---|---|---|
| 11 | `RepositoryService` | `ACT_RE_*` | 图纸：部署/版本/挂起 |
| 12 | `RuntimeService` | `ACT_RU_EXECUTION` / `VARIABLE` | 生产：发起/查实例/终止 |
| **13** | **`TaskService`** | **`ACT_RU_TASK` / `IDENTITYLINK`** | **工位：查待办/认领/办理** |
| 14 | `HistoryService` | `ACT_HI_*` | 档案：已办/轨迹 |

依旧一域一门面。注意 `ACT_RU_TASK` 在 Day 12 的表里也出现过（发起时它被创建），但**查询和办理它归 `TaskService`**——`RuntimeService` 只负责把令牌推到那儿，不负责这个工位上的活。

## ② 命名坑：为什么叫 `FlowableTaskService`

排期里写的是 `FlowableTaskService` 而不是 `TaskService`，这不是随手起的名字：

```java
import org.flowable.engine.TaskService;      // 引擎的门面

public class FlowableTaskServiceImpl implements FlowableTaskService {
    @Resource
    private TaskService taskService;          // 注入的是引擎那个
}
```

**你自己的接口如果也叫 `TaskService`，同一个文件里两个同名类，必有一个要写全限定名。** Day 14 的 `FlowableHistoryService` 同理（要躲 `org.flowable.engine.HistoryService`）。Day 12 没这问题，是因为你的 `ProcessInstanceService` 和引擎的 `RuntimeService` 天然不撞名。

## ③ 任务是怎么冒出来的（回顾 Day 12 第 5 步）

发起时引擎推到 `managerApprove` 这个 UserTask 停下，插了一行任务：

```
ACT_RU_TASK
  ID_            = 7ccc5cf1…      任务自己的 id
  EXECUTION_ID_  = B              挂在子执行（令牌）上，令牌在哪任务在哪
  PROC_INST_ID_  = A              属于实例 A
  TASK_DEF_KEY_  = managerApprove BPMN 里 userTask 的 id
  NAME_          = 经理审批        userTask 的 name
  ASSIGNEE_      = (空)  ← 关键
```

`ASSIGNEE_` 为空**不是遗漏**，是 BPMN 写法决定的，见 ④。

## ④ 两种派活模式：assignee vs candidateGroups

| BPMN 写法 | 语义 | `ACT_RU_TASK.ASSIGNEE_` | 谁能办 |
|---|---|---|---|
| `flowable:assignee="zhangsan"` | **钉死**给某人 | 创建时就写 `zhangsan` | 只有张三 |
| `flowable:candidateGroups="manager"` | 扔进**候选池** | **创建时为空** | manager 组任何人，**先认领后办** |

你的 `leave.bpmn20.xml` 用的是后者，所以任务此刻躺在"池子"里等 manager 来捞。候选组这层关系不在 `ACT_RU_TASK` 里，单独存：

```
ACT_RU_IDENTITYLINK
  TASK_ID_  = 7ccc5cf1…
  TYPE_     = candidate
  GROUP_ID_ = manager
```

**为什么拆表？** 一个任务可以有多个候选组 + 多个候选人，一对多装不进任务主表一行。这跟 execution 拆成树是同一个思路：**能一对多的，就拆独立记录**。

## ⑤ 第二次"接线"：role → candidateGroup

引擎凭什么知道当前登录的 manager 属于 `manager` 组？

Flowable 自带一套用户/组表（`ACT_ID_USER` / `ACT_ID_GROUP` / `ACT_ID_MEMBERSHIP`），但**本项目没用它**——用户在你自己的 `sys_user` 表里，"组"的概念对应 `role` 字段（`employee` / `manager` / `admin`）。

所以又要翻译一次，把你的世界翻给引擎听：

```
sys_user.role = "manager"
   → UserContext.get().getRole()
      → taskService.createTaskQuery().taskCandidateGroup("manager")
         → 引擎 join ACT_RU_IDENTITYLINK 里 TYPE_='candidate' AND GROUP_ID_='manager' 的行
```

这是**本项目第二处"两个世界接缝"**：

| Day | 接缝 | 方向 |
|---|---|---|
| 12 | `UserContext.userId()` → `Authentication.setAuthenticatedUserId()` | 我的用户 → 引擎的当前用户 |
| **13** | `UserContext.get().getRole()` → `taskCandidateGroup(role)` | **我的角色 → 引擎的候选组** |

两者性质不同，值得分清：Day 12 是**写**（塞进引擎 ThreadLocal，用完要清）；Day 13 是**读**（当查询条件传进去，不留状态、无需清理）。所以本块**不需要** `Authentication` 的那套 `try/finally`——见 ⑦。

> 代价（已接受）：角色即组，一个用户只能属于一个组。真实系统里"用户-组"是多对多（一个人既是 manager 又是 finance），那时要么启用 `ACT_ID_*`，要么自己建 `user_group` 表，把 `taskCandidateGroup(单个)` 换成 `taskCandidateGroupIn(多个)`。Demo 阶段一对一足够。

## ⑥ 认领（claim）为什么不能省

`taskService.claim(taskId, userId)` 干的事很简单：把 `ACT_RU_TASK.ASSIGNEE_` 写成 userId（并加一条 `assignee` 类型的 identitylink），语义是"**这活我接了，别人别抢**"。

引擎其实**允许不认领直接 `complete`**。但那样 `ASSIGNEE_` 全程是 null，办完进历史表 `ACT_HI_TASKINST.ASSIGNEE_` 也是 null——**Day 14 的「我的已审批」靠 `taskAssignee(userId)` 查，届时会一条都查不到**。

所以本块的决策：**`complete` 里未认领就先自动认领**（见 02 设计决策）。一次调用完成"认领+办理"，既保证历史有人名，又不用给前端多加一个按钮。

## ⑦ complete 干了什么：又一次"戳一下"

`taskService.complete(taskId, variables)` 是一个命令事务：

1. **落变量**：`variables`（如 `approved=true`）写进 `ACT_RU_VARIABLE`；
2. **删任务**：`ACT_RU_TASK` 该行删除，同步归档进 `ACT_HI_TASKINST`（`END_TIME_` 有值）；
3. **推令牌**：子执行 B 从 `managerApprove` 沿 `flow2` 往下走；
4. **走到底**：撞上 `endEvent` → **整条实例结束** → `ACT_RU_EXECUTION`（A + B）、`ACT_RU_VARIABLE`、`ACT_RU_IDENTITYLINK` 全部删除，数据搬进 `ACT_HI_*`；
5. 若下游还有 UserTask，则在那儿停下、建新任务——但你的 leave 流程审批完就是终点，所以本块办完即完结。

**这就是"戳一下动一下"的第二次兑现**：引擎没有常驻线程，`complete` 这次 HTTP 调用的线程，就是推动流程走完剩下全程的线程。

**不需要接 `Authentication`**：`claim` 已经把办理人显式写进 `ASSIGNEE_` 了，历史归档取的是这个字段，不走引擎 ThreadLocal。（例外：将来若用 `taskService.addComment()` 记审批意见，comment 的 `USER_ID_` 取自 `Authentication`，那时才要补接线。别提前 cargo-cult。）

## ⑧ 越权：本块最重要的安全点

Day 11/12 的接口，"谁调用"基本不影响正确性（`my-started` 顶多查不到）。**本块不一样**：`complete` 是替别人做决定。

如果不校验，employee 拿自己的 token 调 `POST /task/complete` 传一个 taskId，就能**把本该 manager 审批的假批掉**。待办列表按角色过滤只是"看不见"，但接口是裸的——**看不见 ≠ 调不动**，taskId 从别处泄漏出来就能越权。

所以 `complete` / `detail` 前必须校验（02 里的 `assertCanOperate`）：

- 任务**已被认领** → 只有 `ASSIGNEE_` 本人能操作；
- 任务**未认领** → 当前用户的 role 必须在该任务的候选组里。

## ⑨ 正常办结 vs 终止：靠 DELETE_REASON_ 区分

两条路都让实例"结束"、都让 `ACT_RU_*` 清空、都在 `ACT_HI_PROCINST` 留档，区别只在一列：

| | `END_TIME_` | `DELETE_REASON_` |
|---|---|---|
| **正常办完**（本块 complete 走到 endEvent） | 有值 | **NULL** |
| **中途终止**（Day 12 的 terminate） | 有值 | `'测试终止'`（你传的 reason） |

Day 14 的历史列表要显示"已完成 / 已终止"，判据就是这一列。本块办完一条、Day 12 终止过一条，两条对照着看最直观。
