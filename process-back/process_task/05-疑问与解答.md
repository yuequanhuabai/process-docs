# 05 · 疑问与解答

> 测试/看代码过程中的疑问随手记在这里，一问一节。格式：**Q**（问题）→ **A**（结论）→ 必要时附验证方法。

---

## Q1 · 办完任务后，连流程实例都不见了，是不是把数据办丢了？

**A**：不是，是**办完就结束了**。`leave.bpmn20.xml` 只有一个审批节点：`startEvent → managerApprove → endEvent`。`complete` 时令牌从 `managerApprove` 沿 `flow2` 走，立刻撞上 `endEvent` → 整条实例完结 → `ACT_RU_*`（execution/task/variable/identitylink）全套删除，数据搬进 `ACT_HI_*`。

**验证**：`SELECT * FROM ACT_HI_PROCINST WHERE ID_='{instanceId}'` 行还在，`END_TIME_` 有值。

如果流程里 `managerApprove` 后面还有节点（比如再加一级"总监审批"），complete 后令牌会停在那儿、建一条新任务，实例继续活着——那时 `ACT_RU_*` 就不会清空。所以"实例消失"是**这条流程太短**的结果，不是接口行为。

## Q2 · 为什么不做一个单独的「认领」按钮？

**A**：排期 Day 13 只要三件事（待办列表 / 办理 / 任务表单），且**必须保证 `ACT_HI_TASKINST.ASSIGNEE_` 有值**——否则 Day 14 的「我的已审批」（`taskAssignee(userId)` 查历史）会一条都查不到。所以决策是把认领收进 `complete` 里自动做：未认领就先 `claim` 再 `complete`，一次调用两步走。

**代价（已接受）**：没有"认领池"语义——即"我先把这活占住，稍后再办"。若 Day 17 的待办页确实需要这个交互，再补 `claim` / `unclaim` 一对端点。届时注意 02 坑 3：`taskCandidateGroup()` 默认排除已认领任务，认领后任务会从候选查询里消失，待办查询要加 `.includeAssignedTasks()`。

## Q3 · `role` 直接当候选组，够用吗？

**A**：这个 Demo 够用，因为 `sys_user.role` 是单值（`employee` / `manager` / `admin`），BPMN 里也只写了 `candidateGroups="manager"`，一对一正好。

**已知局限**：真实系统里"用户-组"是多对多（一个人既是 manager 又是 finance）。那时两条路——① 启用 Flowable 自带的 `ACT_ID_USER`/`ACT_ID_GROUP`/`ACT_ID_MEMBERSHIP`；② 自己建 `user_group` 表。无论哪条，Service 里 `taskCandidateGroup(单个)` 都要换成 `taskCandidateGroupIn(多个)`，改动很小——接缝已经隔离在那一行了。

## Q4 · `sys_user` 有 `manager_id`（直属主管），为什么审批不派给他？

**A**：这是**表设计意图和 BPMN 实现的一处分歧**，值得知道但当前不改。

`sys_user.sql` 的注释写着"发起请假时审批任务派给发起人的直属主管"，即按 `manager_id` 精确派人。但 `leave.bpmn20.xml` 实际用的是 `candidateGroups="manager"`——**按角色派给一个组**，任何 manager 都能办。李员工的 `manager_id=2`（王主管），当前恰好只有一个 manager 账号，所以两种方案跑起来效果一样，看不出区别。

**要改成"派给直属主管"怎么做**：发起时把主管 id 查出来塞进变量，BPMN 里用表达式取：

```java
// start() 里：variables.put("approverId", 查出来的 managerId);
```
```xml
<userTask id="managerApprove" flowable:assignee="${approverId}"/>
```

这是 `flowable:initiator` 那套"变量在 BPMN 表达式里被引用"的同一个机制。**不在 Day 13 做**：会同时改动 BPMN 模板和 Day 12 的发起接口，超出本块范围；且候选组模式更能演示 `ACT_RU_IDENTITYLINK` 的作用。留作 Day 30（HR 用户对接）或 P5 设计器做完后的增强项。
