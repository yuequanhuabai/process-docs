# 03 · 操作步骤

> 前提：02 的代码已进项目且 `mvnw compile` 通过。全程在 knife4j（`http://localhost:9090/workflow/doc.html`）操作，配合 SQL 客户端看表。
> 账号：`admin`(id=1) / `manager`(id=2) / `employee`(id=3)，密码均 `123456`。本块要**频繁换 token**，Authorize 按钮会用到很多次。

---

## 步骤 0 · 准备现场

需要**至少一条在途实例**，且它的 `managerApprove` 任务还挂着。

```sql
-- 有没有活的待办？预期至少 1 行，ASSIGNEE_ 为空
SELECT ID_, NAME_, TASK_DEF_KEY_, ASSIGNEE_, PROC_INST_ID_ FROM ACT_RU_TASK;
```

没有就用 employee 的 token 补发一条（Day 12 的接口）：

```json
POST /process-instance/start
{ "processDefinitionKey": "leaveProcess", "businessKey": "10001",
  "variables": { "days": 3, "reason": "年假" } }
```

启动后端，确认「待办任务」分组出现在文档页。

## 步骤 1 · manager 看待办（主路径）

1. `/auth/login` 用 **manager / 123456** 登录，token 粘进 Authorize；
2. `GET /task/todo`。

**预期**：`total=1`，records 里一条：

| 字段 | 预期值 |
|---|---|
| `id` | 任务 id（记下，后面要用，记作 `{taskId}`） |
| `name` | 经理审批 |
| `taskDefinitionKey` | `managerApprove` |
| `assignee` | **null**（候选组任务，还没人认领） |
| `processInstanceId` | 实例 id |
| `createTime` | 格式化成 `yyyy-MM-dd HH:mm:ss`，不是时间戳 |

这条能查出来，说明 `role='manager'` → `taskCandidateGroup("manager")` → `ACT_RU_IDENTITYLINK` 的接线通了。

## 步骤 2 · 换 token 验隔离（关键对照）

同 Day 12 的 `my-started` 套路——**只看 manager 查得到不够，得看别人查不到**：

| token | `GET /task/todo` 预期 |
|---|---|
| **manager** | 1 条 ✅ |
| **employee** | **0 条**（employee 组不在候选里） |
| **admin** | **0 条**（admin 组也不在候选里） |

三行都对上，才排除"库里就一条所以谁查都是 1"的假阳性。

## 步骤 3 · 越权校验（本块的安全点）

**仍用 employee 的 token**（他看不见这条待办，但我们手上有 `{taskId}`，模拟 id 泄漏）：

1. `GET /task/{taskId}` → 预期「**你不在该任务的候选办理人范围内，无权操作**」；
2. `POST /task/complete`，body `{"taskId": "{taskId}"}` → 同样被拒。

**这一步是本块最重要的验证**：证明"待办列表看不见"和"接口调不动"是两回事，`assertCanOperate` 真的挡住了 employee 替 manager 批假。

## 步骤 4 · 任务详情

换回 **manager** 的 token，`GET /task/{taskId}`。

**预期** `TaskFormVO`：继承来的任务字段（同步骤 1）+ 多出两个：

- `variables`：`{"days": 3, "reason": "年假", "initiator": "3"}` ← 发起时写的三个变量都在
- `formKey`：`null`（P6 表单设计器才用得上）

留意 `initiator` 是字符串 `"3"`（employee 的 userId），`days` 是数字 `3`——类型差异见 Day 12 的变量表 `TYPE_` 列。

## 步骤 5 · 办理（戳第二下）

仍用 manager 的 token：

```json
POST /task/complete
{
  "taskId": "{taskId}",
  "variables": { "approved": true, "comment": "同意" }
}
```

**预期**：`R.code=200`，后端日志出现 `任务已办理：taskId=…, assignee=2`。

**随即看表——这条 leave 流程只有一个审批节点，办完即完结，所以运行时表应该全空：**

```sql
-- 预期：0 行（任务办掉了）
SELECT COUNT(*) FROM ACT_RU_TASK        WHERE PROC_INST_ID_ = '{instanceId}';
-- 预期：0 行（令牌撞 endEvent，实例结束，A/B 两行都清）
SELECT COUNT(*) FROM ACT_RU_EXECUTION   WHERE PROC_INST_ID_ = '{instanceId}';
-- 预期：0 行
SELECT COUNT(*) FROM ACT_RU_VARIABLE    WHERE PROC_INST_ID_ = '{instanceId}';
SELECT COUNT(*) FROM ACT_RU_IDENTITYLINK WHERE PROC_INST_ID_ = '{instanceId}';
```

**别被"数据全没了"吓到**——搬进历史表了（01 文档⑦），下一步就去看。

## 步骤 6 · 历史留痕（Day 14 的预习）

```sql
-- 任务历史：预期 1 行，ASSIGNEE_ = '2'（manager），END_TIME_ 有值
SELECT ID_, NAME_, TASK_DEF_KEY_, ASSIGNEE_, START_TIME_, END_TIME_, DURATION_
FROM ACT_HI_TASKINST WHERE PROC_INST_ID_ = '{instanceId}';

-- 实例历史：预期 1 行，END_TIME_ 有值，DELETE_REASON_ 为 NULL
SELECT ID_, BUSINESS_KEY_, START_USER_ID_, END_TIME_, DELETE_REASON_
FROM ACT_HI_PROCINST WHERE ID_ = '{instanceId}';

-- 变量历史：预期 5 行 —— days/reason/initiator + approved/comment（办理时新增的两个）
SELECT NAME_, VAR_TYPE_, TEXT_, LONG_ FROM ACT_HI_VARINST WHERE PROC_INST_ID_ = '{instanceId}';

-- 活动轨迹：预期 startEvent → managerApprove → endEvent 三行，END_TIME_ 都有值
SELECT ACT_ID_, ACT_NAME_, ACT_TYPE_, ASSIGNEE_, START_TIME_, END_TIME_
FROM ACT_HI_ACTINST WHERE PROC_INST_ID_ = '{instanceId}' ORDER BY START_TIME_;
```

**重点确认 `ACT_HI_TASKINST.ASSIGNEE_ = '2'`** —— 这就是自动认领决策的兑现，Day 14 的「我的已审批」靠它。若这里是 NULL，说明 `complete` 里的 claim 没生效，Day 14 会白做。

`ACT_HI_ACTINST` 那条 `startEvent → managerApprove → endEvent` 的轨迹，就是 Day 14「实例历史轨迹」接口的数据源，也是将来前端画高亮流程图的依据。

## 步骤 7 · 异常路径

1. **重复办理**：拿刚办完的 `{taskId}` 再调一次 `complete` → 预期「待办任务不存在或已办理」（RU 表里没了，`getTaskOrThrow` 挡住）。**这是正确语义，不是 bug**；
2. **taskId 不存在**：随便编一个 id → 同样报「不存在或已办理」；
3. **taskId 缺失**：body 去掉 `taskId` → 400 参数校验错误（`@NotBlank` + `@Valid` 生效）。

## 步骤 8 · 正常办结 vs 终止的对照（01 文档⑨）

这一步能把 Day 12 和 Day 13 串起来看：

1. 用 employee 再发起一条新实例，记下 `{instanceId2}`；
2. `DELETE /process-instance/{instanceId2}?reason=测试终止`（Day 12 那个**已写未测**的接口，正好这次一起还账）；
3. 对比两条实例的历史：

```sql
SELECT ID_, END_TIME_, DELETE_REASON_ FROM ACT_HI_PROCINST
WHERE ID_ IN ('{instanceId}', '{instanceId2}');
```

**预期**：

| 实例 | `END_TIME_` | `DELETE_REASON_` |
|---|---|---|
| 办完的那条 | 有值 | **NULL** ← 正常完成 |
| 终止的那条 | 有值 | **测试终止** ← 中途终止 |

两条都"结束"了，靠 `DELETE_REASON_` 区分。Day 14 的历史列表要显示状态，判据就是这一列。

顺手把 Day 12 的另一笔尾巴也验了：终止完再 `DELETE` 同一个 id → 「运行中的流程实例不存在」（02 文档坑 5 的正确语义）。

## 步骤 9 · 清 Day 11 的最后一笔欠账（cascade=true）

> `cascade=false` 的冲突分支已于 2026-07-14 验过 ✅，只剩 `true`。

1. 确保库里还有**至少一条在途实例**（没有就再发一条）；
2. 取 deploymentId：`GET /process-definition/page` 响应里的 `deploymentId` 字段（**别拿 `processDefinitionId` 的第三段**，那是定义 id 不是部署 id）；
3. `DELETE /process-definition/deployment/{deploymentId}?cascade=true` → 预期成功；
4. 复查三处，确认"连历史一起删"不是虚言：

```sql
SELECT COUNT(*) FROM ACT_RE_PROCDEF  WHERE DEPLOYMENT_ID_ = '{deploymentId}';  -- 预期 0
SELECT COUNT(*) FROM ACT_RU_EXECUTION;                                          -- 预期 0（在途实例被级联清）
SELECT COUNT(*) FROM ACT_HI_PROCINST;                                           -- 预期 0（历史也没了！）
```

**`ACT_HI_PROCINST` 归零是重点**——这就是界面上必须二次确认的原因，Day 15 做流程管理页时删除按钮要加警告。

5. **恢复现场**：把 `leave.bpmn20.xml` 重新 `POST /process-definition/deploy` 传一次，别给 Day 14 留坑（Day 14 要冒烟，得有定义可发起）。
