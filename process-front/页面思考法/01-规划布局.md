## 一、动作 1 · 划边界：这张图里哪部分**不归我管**？

打开原型图，看到的是**整个后台界面**：侧栏、顶栏、面包屑、用户头像、白卡片。

**但你要写的文件，只负责白卡片里面的东西。**

```
┌─────────────────────────────────────────────┐
│ 侧栏  │  顶栏（面包屑 / 用户 / 退出）        │  ← layout/index.vue（P0 就写好了）
│  首页 │ ─────────────────────────────────── │
│  用户 │  ┌───────────────────────────────┐  │
│  流程 │  │                               │  │
│ ▶实例 │  │      ★ 你要写的全部内容 ★     │  │  ← views/instance/index.vue
│  发起 │  │                               │  │
│  关于 │  └───────────────────────────────┘  │
└─────────────────────────────────────────────┘
         ↑ 路由把你的组件塞进这个坑里
```

原型文档自己也写了这句（`原型-…html:355`）：

> 这一节给**完整外框**（侧栏+顶栏），下面几节只给白卡片——**白卡片里的内容才是你要写的 `views/instance/index.vue`**，外框是 P0 就做好的 layout。

### 边界是谁划的？——机制要说得出来

⚠️ **这里有个似是而非的理解**，必须掰开：

> ❌ 「侧栏已经写好了，所以不用再写第二遍。」

这话**结论对、机制错**，而且会推出一个错误推论：*「侧栏写好了，就会自动出现在每个页面上」*。**不会。**

真正的机制是**父子路由 + 一个出口**：

```
router/index.ts                          layout/index.vue
─────────────────                        ─────────────────
{ path: '/',                             <el-aside>  侧栏  </el-aside>
  component: layout,        ┌──────→     <el-main>
  children: [               │              <router-view/>   ← :60 这一行是「坑」
    { path: 'instance',  ───┘            </el-main>
      component: 你的页面 }
  ]}
```

- `/instance` 在路由表里是 layout 的 **children**（父子关系）
- `layout/index.vue:60` 的 `<router-view/>` 是**留给子路由的出口**
- 地址栏变成 `/instance` 时，Vue Router 把你的组件**塞进那个出口**

**准确的说法**：你的页面和侧栏是**父子两个组件，天生就在不同文件里**；父组件挖了个坑，你的文件负责填那个坑。

> 把 `layout/index.vue:60` 那行删掉，`/instance` 会变成「侧栏顶栏都在、主区一片空白」——**一个实验就能证明侧栏不是自动出现的**。
>
> 📌 `<router-view/>` 和 slot 是不是同一套机制？两者都是「父组件留位置、子组件填内容」，区别在**填充者是谁**（slot 由父模板书写者决定，编译期就定了；`router-view` 由路由表 + 当前 URL 决定，运行期才定）。**这个问题已登记为待深入主题，本人要求整个项目完工后再展开**——见 [`../../process-back/deep_dive/待深入主题清单.md`](../../process-back/deep_dive/待深入主题清单.md) 第 7 条。

### 可迁移的收获

> **拿到任何原型图，第一个动作不是数控件，是问「这张图里哪部分不归我管」。**

划错边界的代价是立刻可见的：多写了外框 → 页面上出现两个侧栏。

## 二、动作 2 · 拆条带：眯着眼看形状

挡住所有细节，只看轮廓。运行中实例页剩下三条：

```
┌───────────────────────────────────────────────┐
│ ①  运行中实例                    [全部流程 ▾] │  ← 工具条
├───────────────────────────────────────────────┤
│ ②  ┌──────┬──────┬──────┬─────┬────────┐      │
│    │流程名│业务标│当前节│发起 │  操作  │      │  ← 数据区
│    ├──────┼──────┼──────┼─────┼────────┤      │
│    │报销  │RB-01 │经理审│  3  │  终止  │      │
│    │采购  │CG-02 │总监审│  3  │  终止  │      │
│    └──────┴──────┴──────┴─────┴────────┘      │
├───────────────────────────────────────────────┤
│ ③                    共 4 条  ‹ [1] ›         │  ← 分页条
└───────────────────────────────────────────────┘
```

**上下堆叠，没有左右分栏、没有嵌套。** 整个结构就这么简单。

### 这个三段式不是这页独有的

对照 `views/process/index.vue`（流程管理页，仓库里现成的一份参考样本）：

| 条带 | 流程管理页 | 运行中实例页 |
|---|---|---|
| ① 工具条 | `:3-10` | 有，同位置 |
| ② 数据区 | `:13-37` | 有，同位置 |
| ③ 分页条 | `:39-46` | 有，同位置 |

**完全一样的骨架。** P4 后面的待办页、已审批页、历史页，还会再用四次。

> `plan/P4` 开头那句「四个页面全部同构于 `views/user`」——**同构指的就是这个三段式**。

### 可迁移的收获

> **列表页的通用骨架 = 工具条 / 数据区 / 分页条 三条横带。**
> 看到一张后台列表原型，先假设它是这三条，再去找哪里不一样。

## 三、动作 3 · 定职责：谁是输入、谁是输出

知道「有三块」还不够。要问一个问题：

> **这三块里，谁会导致「去后端重新拿一次数据」？**

| 条带 | 角色 | 动它会重查吗 |
|---|---|---|
| ① 工具条 | **输入**：决定「查哪个流程」 | ✅ 会 |
| ② 数据区 | **输出**：把已经拿到的数据摆出来 | ❌ 不会（它只是显示器） |
| ③ 分页条 | **输入**：决定「查第几页」 | ✅ 会 |

### 反直觉的结论

①和③在视觉上被②隔在两头、长得完全不像，但**它们是同一类东西——都是查询条件的输入口**。它们最终都指向同一个动作：*带着新条件，再查一次*。

```
   ① 选了别的流程 ──┐
                    ├──→ 【带着新条件去后端查】──→ ② 换一批数据显示
   ③ 点了第 2 页 ──┘
```

**数据只往一个方向流**：两头的输入 → 一次请求 → 中间的显示。**中间那块永远不会反向影响两头。**

### 这个判断在代码里的回报

`views/process/index.vue` 里 `handlePageChange`（`:128`）和 `handleLatestChange`（`:134`）是两个不同的函数，但**最后一行都是 `loadList()`**——因为它俩本质上是同一件事的两个入口。

**布局阶段就想清楚因果方向，写代码时才不会「咦这两个函数怎么这么像」。**

## 四、还有一类东西**不参与布局**

点「终止」要弹一个框让用户填终止原因。**但模板里一个弹窗组件都不用写。**

因为它是**命令式调用**的：在 JS 里写一行，组件库临时往 `<body>` 上挂一个框，用完销毁，**不占模板里的任何位置**。

| 类型 | 特点 | 例子 |
|---|---|---|
| **声明式组件** | 写在模板里，占 DOM 位置，跟着布局走 | 表格、下拉、分页器 |
| **命令式组件** | 在 JS 里调用，浮在页面之上，**不参与布局** | 确认框、提示消息、全局 loading |

**所以第 ① 步画的框线图里，弹窗和提示压根不该出现**——上面那张三条带图里确实一个都没有，就是这个原因。

（具体用哪个弹窗、为什么，是第 ② 步的事，见 `02` 第六章。）

## 五、布局的取舍靠什么判据

拆完条带会遇到「这块该放哪」的争论。判据只有两条，**按顺序用**：

### 判据 1 · 视觉第一性（视线路径）

中文阅读的视线从左上到右下。**进页面时可能要动的东西放在视线起点，看完一屏才需要的放在终点。**

- 筛选 → 起点（左上/右上）
- 分页 → 终点（右下）

### 判据 2 · 使用频率（可以打破判据 1）

**反例**：Gmail 的分页在**右上角**，和筛选并排。因为邮件列表是无限长的流，「翻页」的频率远高于「筛选」，于是把高频操作挪到了视线起点。

### 所以

> **布局的依据是「哪个动作更频繁」，不是「规范这么写」。**

「筛选在上、分页在下」是后台管理界面二十多年的约定（早期 JSP/Struts 后台 → 各家 admin 模板 → Ant Design / Element 固化成默认形态），但它**只是判据推出来的常见解，不是判据本身**。

**思想实验**：把筛选下拉搬到页面底部、和分页器并排——**功能一点不坏**。坏的只是视线路径。这恰好证明：布局管的是**认知成本**，不是功能。

## 六、检查点

> 答不出来别往下走，回到对应章节。

1. 为什么你的文件里不用写侧栏？**是谁把侧栏和你的页面拼在一起的？**
2. 三条带里哪些会触发重新查数据？为什么另一条不会？
3. 如果把筛选下拉搬到页面底部、和分页器并排——功能会坏吗？如果不坏，那「筛选放上面」的价值在哪？
4. 为什么第 ① 步的框线图里不该画弹窗？

<summary>参考答案</summary>

1. **不是**「侧栏已经写过了」。是 `/instance` 在路由表里是 layout 的 **children**，layout 里的 `<router-view/>`（`:60`）是留给子路由的出口，路由把你的组件塞进那个坑。删掉那行，侧栏还在但主区空白。
2. ①③ 会——它俩都是**查询条件的输入口**，只是被②隔在两头。②只是显示器，数据单向流入，不反向影响两头。
