## 一、背景与目标

P4 四个表格页已完成三个（流程管理、实例+我的发起、待办）。本页是**最后一个**：把「登录 → 发起 → 审批 → **历史**」这条链的最后一环界面化。

两件事：

1. **我的已审批** —— 审批人回头看"我办过哪些"，这是审批类系统的标配对账入口；
2. **流转轨迹** —— 任何一条实例走过哪些节点、每个节点谁办的、花了多久。这是**发起人**最关心的东西（"我的申请卡在谁那了"）。

**本页做完 P4 关闭**，下一站 P5 BPMN 设计器。

**交付物**：`api/history.ts` + `views/approved/index.vue` + 轨迹展示（形态见决策①）+ 路由与菜单 + **回头补 myStart 操作列的「轨迹」按钮并删掉占位破折号**（Day 16 排期切分留下的欠账，2026-08-10 登记）。

## 三、角色与场景

| 角色 | 「我的已审批」 | 「轨迹」 |
|---|---|---|
| manager（id=2） | 有数据：Day 17 验收时办掉的那一级 | 从已审批行进入，看整条链 |
| admin（id=1） | 有数据：Day 17 验收时办掉的二级 | 同上 |
| employee（id=3） | **空态**（从不审批）——要正常显示"暂无数据"，不是报错 | 从「我的发起」每行进入，看自己的申请卡在哪 |

**轨迹要覆盖三种实例状态**（库里三态样本齐全，见断点文档第二节）：

| 实例状态 | 轨迹长什么样 |
|---|---|
| 进行中 | 最后一个节点 `endTime` 为 **null**（当前停留处）、`durationInMillis` 也为 null ⇒ 页面要能渲染"进行中"而不是显示空白或 NaN |
| 已办结 | 完整链路：startEvent → …userTask… → endEvent，全部有 endTime |
| 已终止 | 链路**没有 endEvent**，最后停在被终止时所在的节点（`terminate` 清 RU 保 HI） |

## 四、接口契约与字段缺口

后端两条接口 **Day 14 已 knife4j 验收关闭**，本页开工不阻塞于后端。但列表字段有缺口（4.2）、有一个数据层面的硬缺口（4.4）。

### 4.1 接口清单

| 接口 | 入参 | 出参 | 备注 |
|---|---|---|---|
| `GET /history/approved` | `current`、`size`（均有默认值） | `IPage<ApprovedTaskVO>` | 内部固定 `taskAssignee(当前用户) + finished()`，按结束时间倒序 |
| `GET /history/instance/{instanceId}/activities` | 路径参数 `instanceId` | **`List<ActivityTraceVO>`（数组，不分页）** | ⚠️ 与前三页不同：**没有 `PageResult` 包装**，`api` 里写 `request.get<never, ActivityTrace[]>` |

### 4.2 `ApprovedTaskVO` 现有 10 个字段 vs 页面想要的列

| 页面想要的列 | VO 有吗 | 说明 |
|---|---|---|
| 任务名称（「经理审批」） | ✅ `name` | |
| 审批时间 | ✅ `endTime` | 我办完的时刻，列表主排序字段 |
| 耗时 | ✅ `durationInMillis` | **毫秒数**，页面要自己格式化成"3 分钟"/"2 天 4 小时"，直接显示 `86400000` 没有可读性 |
| 开始时间 | ✅ `startTime` | 任务到我手上的时刻。与 endTime 二选一显示即可，两个都放列太挤 |
| **流程名称**（「报销流程」） | ❌ 只有 `processDefinitionId`（`reimburseProcess:1:xxx`，不能直接示人） | **缺** |
| **发起人姓名** | ❌ 完全没有 | **缺** |
| **业务标识 businessKey** | ❌ 完全没有 | **缺** |
| 办理人 `assignee` | ✅ 有，但**恒等于当前登录人**（查询条件就是 `taskAssignee(我)`）——**这一列没有信息量，不显示** | |
| `deleteReason` | ✅ 有。正常办结为 null；非 null ⇒ 这条不是我办完的，是**流程被终止**时把我认领过的任务一起带走的（边界情况，见下） | |
| `id` / `taskDefinitionKey` / `processInstanceId` / `processDefinitionId` | ✅ | 前三个是内部标识，不显示；`processInstanceId` 是**打开轨迹的钥匙**，必须留在行数据里 |

**缺三字段的后果与 Day 17 一模一样**：不补的话，已审批列表每行只有「经理审批 + 时间」，翻到第三页时**完全分不清哪条对应哪个申请**——而"分得清"正是这个页面存在的唯一理由。

→ 补不补见 **七、决策②**。⚠️ 补的话**不能照抄 Day 17 的 `enrich()`**，原因写在决策②里（一句话：已审批对应的实例**可能已经结束**，`RuntimeService` 查不到，必须走 `HistoryService`）。

### 4.3 `ActivityTraceVO` 的 7 个字段与三个坑

| 字段 | 用途 / 坑 |
|---|---|
| `activityId` | 节点 id（`startEvent1` / `managerApprove` / `flow2`…） |
| `activityName` | 节点名。⚠️ **可能为空**：BPMN 里 `startEvent`/`endEvent`/连线通常不写 `name`。页面要回退（显示中文类型名或 activityId），不能渲染出一行空白 |
| `activityType` | ⚠️ **必须前端过滤连线**：`filter(a => a.activityType !== 'sequenceFlow')`，后端故意不滤（P3 Day 14 决策 2）。不滤的话四个节点会变成七八行，一半是箭头 |
| `assignee` | ⚠️ 是 **userId 字符串**（`"2"`），不是姓名；且只有 userTask 有值，事件/网关恒 null。要显示姓名 ⇒ 又是一个 enrich 缺口（见决策②，建议与已审批的三字段一并处理或一并放弃） |
| `startTime` / `endTime` | `endTime` 为 null = **当前停留节点**，这是"卡在谁那"的判据 |
| `durationInMillis` | 同样是毫秒，同样要格式化；停留中的节点为 null |

> 📌 排序已经被后端修过一次，前端**不要再自己排**：`START_TIME_` 是毫秒级，同事务内 <1ms 走完的多个节点时间戳相同，仅按时间排序顺序不保证；后端已用 `TRANSACTION_ORDER_` 做了二次排序兜底（`FlowableHistoryServiceImpl.java:49-56`，注释里写了 `HistoricActivityInstanceQuery` 没有对应 orderBy、是查 jar 确认过的）。**照返回顺序渲染即可。**

### 4.4 ⚠️ 硬缺口：**审批意见（comment）在轨迹里取不到**

画原型前必须知道这条，否则会画出一个做不出来的时间线。

Day 17 办理时，意见是这样存的：`POST /task/complete` → `taskService.complete(taskId, variables)`，`variables = { approved, comment }`。两个事实叠加导致意见丢失：

1. **`complete(taskId, variables)` 写的是「实例级」变量**（不是 task-local）。所以 manager 填的 `comment` 和 admin 填的 `comment` 是**同一个键**，后者直接**覆盖**前者；
2. **`history-level: audit`**（`application.yml:53`）—— 这一级只把变量的**当前值**写进 `ACT_HI_VARINST`，变量的**变更明细表 `ACT_HI_DETAIL` 不写**（那要 `full` 级别）。

⇒ 结果：**一条两级审批的实例，最终只剩下最后一个人填的那句意见**，且它挂在实例上、不挂在节点上——**没有任何办法把"哪句意见是哪个节点填的"还原出来**。

三条出路（都**超出 Day 18 范围**，本 Day 只登记不做）：

| 出路 | 做法 | 代价 |
|---|---|---|
| A | 办理时改用 **task-local 变量**（`setVariableLocal` / `complete(taskId, vars, true)`），意见就跟着任务走不再互相覆盖 | 改后端 + 已产生的历史数据仍是坏的 |
| B | `history-level` 调到 **`full`**，`ACT_HI_DETAIL` 记下每次变量变更 | 全局配置改动，历史表写入量上升，影响面大 |
| C | 改用 Flowable 的 **`taskService.addComment()`**（`ACT_HI_COMMENT` 表，本就是为审批意见设计的） | 最"正统"，但要动 Day 17 刚验收完的办理链路 |

**本篇建议**：登记为挂起项（登记三处：P4 Day 18 条目 + 总控第四节总表 + P8 第三节展开），**留到 P8 Day 31 与其他挂起项一并评估**。Day 18 的轨迹**只展示"节点 + 办理人 + 时间 + 耗时"，不展示意见**。

> 🔬 **开工前用 1 条 SQL 落实这个结论**（本节是从代码推的，按《讲解规则》第五节该实测一次）：
> `SELECT * FROM ACT_HI_VARINST WHERE PROC_INST_ID_ = '<Day 17 验收时那条走完两级的实例 id>';`
> 预期：`comment` **只有一行**（值 = admin 那次填的），且 `ACT_HI_DETAIL` 里没有它的变更记录。若实测与预期不符，本节结论作废、决策重来。

## 七、决策项（2026-08-14 已定稿）

> **定稿结果：① A · 弹窗　② B · 补后端　③ A · `el-timeline`　④ 是 · 已审批页也放轨迹入口。** 四项均采纳推荐方案，理由见各条。以下保留备选方案与代价，供将来回看"为什么这么选"。

### ① 轨迹用什么形态承载？　→ **A · 弹窗（已定）**

| 方案 | 内容 | 优点 | 缺点 |
|---|---|---|---|
| **A · 弹窗（`el-dialog`，推荐）** | 点行内「轨迹」→ 弹窗里显示该实例的流转 | 与 Day 17 办理弹窗同构，**体例已熟**；两个入口（myStart / 已审批）共用同一个弹窗；不占菜单位 | 弹窗里放长列表略挤（轨迹一般 4–8 行，够用） |
| B · 独立路由页 `/history/:instanceId` | 点「轨迹」跳页 | 可分享/刷新 URL；空间大 | 多一条路由 + 返回态管理；**菜单里放什么？**没有"全站历史列表"接口（见二、不做），这个菜单点进去是空的 |
| C · 抽屉 `el-drawer` | 右侧滑出 | 视觉上适合"详情"；空间比弹窗大 | 本项目没用过 drawer，多学一个组件 |

> 📌 决策影响 P4 清单的字面表述：清单里写的是 `views/approved` + `views/history` **两个页面**。选 A/C 的话 `views/history` 不作为页面存在，只是一个轨迹组件（放 `components/` 或直接内联在两个页面里）——需求确认后我会同步改 P4 的措辞。

### ② 已审批列表缺的三字段（流程名称 / 发起人姓名 / businessKey）补不补后端？　→ **B · 补（已定，本 Day 变双端）**

| 方案 | 内容 | 代价 | 效果 |
|---|---|---|---|
| A · 不补 | 列表只显示「任务名 + 时间 + 耗时」 | 零 | 翻到第二页就分不清哪条是哪个申请，页面价值大打折扣 |
| **B · 补（推荐）** | `ApprovedTaskVO` 加三字段 + `FlowableHistoryServiceImpl.approved()` 末尾挂 `enrich()`（整页固定 2 次查询，别写成 N+1） | Day 18 从纯前端变双端，约 +0.3 块 | 与前三页一致，列表一眼可辨 |

⚠️ **选 B 的话有个坑，别照抄 Day 17 的 `enrich()`**：Day 17 查的是 `RuntimeService`（待办任务的实例必然在途），而**已审批对应的实例大概率已经办结，`ACT_RU_EXECUTION` 里根本没有那行** —— 照抄会得到整页 null（又一次"编译全绿、字段恒 null"的静默失效）。正确写法是 `historyService.createHistoricProcessInstanceQuery().processInstanceIds(ids).list()`，姓名照旧查 `sys_user`。

> 附带项：轨迹里的 `assignee` 也是 userId（4.3）。若选 B，建议**顺手把轨迹的办理人也换成姓名**（同一批 `sys_user` 查询）；若选 A，则轨迹里的办理人就显示 userId 数字，或干脆不显示这一列。**两处保持一致，别一个显示姓名一个显示数字。**

### ③ 轨迹用什么控件渲染？　→ **A · `el-timeline`（已定）**

| 方案 | 内容 | 说明 |
|---|---|---|
| **A · `el-timeline`（推荐）** | 竖向时间线，每个节点一个 `el-timeline-item`，节点名做标题，办理人/时间/耗时做副文本，当前停留节点用不同颜色的圆点 | 语义最贴切（"流转顺序"天然是时间线），视觉上一眼看出走到哪；**本项目第一次用这个组件**，要多学一个 API |
| B · `el-table` | 五列：序号 / 节点 / 办理人 / 时间 / 耗时 | 完全复用已有手感，零学习成本；但"顺序感"和"当前停在哪"要靠自己标 |

> 学习角度我更推 A：P4 前三页把表格练透了，时间线是新东西且成本很小（就是个 `v-for` + 两个 props），P5 之前正好扩一个组件。但你要是想把 Day 18 快速收掉进 P5，B 也完全够用。

### ④ 「我的已审批」要不要也放一个「轨迹」入口？　→ **要（已定）**

理由：审批人办完一级后，想知道"我批过的这单后来批了吗"，除了这里没有别的入口（「我的发起」只显示自己发起的，审批人自己没发起）。成本几乎为零——弹窗组件与 myStart 共用。
