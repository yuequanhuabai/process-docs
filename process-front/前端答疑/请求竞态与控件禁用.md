# 请求竞态与控件禁用（`:loading` / `:disabled` 到底在治什么）

> **触发点**（2026-08-10）：「为什么要加 loading 和 disabled，之前的我没有理解，忘记了；**不加有什么影响？**」
>
> 这个欠账在 `plan/P4` 里已经被记了**四次**（Day 15 顺延 → Day 16 三次复核），每次都写着"零额外代码"却一直没做。原因不是懒，是**没理解它治什么病** —— 一个说不出后果的待办，永远排不进优先级。所以本篇的重点不是"该怎么写"，是"**不写会怎样、而且你不会发现**"。
>
> 本篇从 [`原生控件的外衣与el-switch.md`](./原生控件的外衣与el-switch.md) 第八节第 1 条抽出并大幅扩写 —— 它原本藏在讲 el-switch 的篇子里，牵扯到三个控件两个页面，位置太偏。

---

## 零、一句话结论

不加，**不会报错、不会崩、控制台干干净净**。它只会让「表格里的数据」和「开关 / 页码显示的状态」**对不上**。

这就是《讲解规则》§7.3 ③ 那条贯穿警戒线：**静默失败**。评估这类问题的正确问法不是"会不会出错"，而是——

> **出错时我会不会知道？**

这里的答案是：**不会。**

---

## 一、先纠一个误解：这不是"防手抖"

很多人（包括各种教程）把 `:disabled="loading"` 说成"防止用户重复提交"，好像是个体验优化、可做可不做。

**不是。** 重复提交只是它顺带治的。它真正治的是一个**必然发生、且无法在事后补救**的问题：

> 一旦两个请求同时在飞，**JS 没有任何机制保证它们按发出顺序回来**；而后回来的那个会静悄悄地覆盖先回来的那个。

也就是说，`loading` 变量本身不是"UI 状态"，它是**并发闸门**。它挂在 `v-loading` 上时是"给用户看的"，挂在 `:disabled` 上时是"给程序用的" —— 同一个变量，两种职责，别只用了前一半。

## 二、机制拆解（纵向轴）：拿真代码走一遍时序

### 2.1 现场代码

`process-front/src/views/process/index.vue:134-137`：

```js
function handleLatestChange() {
  current.value = 1
  loadList()          // ← async 函数，发出去就返回了，没人等它
}
```

`loadList()`（`:74-86`）：

```js
async function loadList() {
  loading.value = true
  try {
    const page = await pageDefinitions(current.value, size.value, latestOnly.value)
    list.value = page.records        // ← ★ 争抢的就是这一行
    total.value = page.total
  } catch { /* 拦截器已弹错 */ }
  finally {
    loading.value = false            // ← ☆ 这一行也在被争抢
  }
}
```

关键在 `await` 那一行：函数走到这里就**交出控制权**（原理见 [`async-await与JS单线程.md`](./async-await与JS单线程.md)：挂起的是**函数**不是**线程**）。函数没走完，浏览器该干嘛干嘛 —— **包括继续响应你的鼠标点击**。

### 2.2 快速点两下开关，实际时序

| 时刻 | 发生什么 | `latestOnly` | 屏幕上的开关 |
|---|---|---|---|
| t=0 | 点开 → v-model 立刻写值 → `loadList()` 发请求 **A**（带 `latestOnly=true`） | `true` | 开 |
| t=0.1s | 点关 → v-model 立刻写值 → `loadList()` 发请求 **B**（带 `latestOnly=false`） | `false` | 关 |
| t=0.3s | **B 先回** → `list.value = B的records`（全部版本） | `false` | 关 |
| t=0.5s | **A 后回** → `list.value = A的records`（只看最新版本） | `false` | 关 |

**最终屏幕**：开关是「关」的，表格里躺的却是「只看最新版本」的数据。

**没有任何提示。** 你以为看到的是全部版本，实际不是。

分页器（`:39-46`）同理：连点 1→2→3，页码高亮停在 3，表格里可能是第 2 页的数据 —— 而分页那个更阴险，因为页码和数据的对应关系**你根本没法一眼验证**（开关至少还能靠"版本号列有没有重复的 key"看出来）。

### 2.3 附带损伤：`loading` 自己也被争抢

`loading` 这个 ref 被两次调用**共用**。B 的 `finally` 会把它置回 `false` —— 可 A 还在路上。

于是 `v-loading` 的遮罩**提前消失**，看上去"加载完了"，其实还有一个请求正准备覆盖你的数据。**遮罩消失反而成了错误信号。**

### 2.4 为什么响应会乱序？（剥到网络这一层）

这不是偶发 bug，是网络的常态。至少四个来源：

1. **服务端处理耗时不同** —— `latestOnly=true` 要多一次 `latestVersion()` 过滤，两个请求在 Flowable 里走的查询路径本来就不一样，耗时不可能相等；
2. **HTTP/2 多路复用** —— 同一条 TCP 连接上多个流并行，响应帧交错返回，**先发的流可能后完成**；
3. **HTTP/1.1 的连接池** —— 浏览器对同一域名开 6 条连接，两个请求走**不同的 TCP 连接**，各自独立重传、各自受各自的拥塞窗口影响；
4. **代理 / 网络抖动** —— 本机 `HTTP_PROXY=127.0.0.1:10808` 这种链路上更明显。

**剥到底就是**：HTTP 的请求-响应配对靠的是"在哪条连接/哪个流上"，**不是靠顺序**。顺序保证从来就不存在，只是延迟低的时候你撞不上。

### 2.5 后端视角类比（这里最好懂）

就是**两个线程写同一个成员变量，没加同步**：

```java
// 线程1:  this.list = queryA();   // 慢
// 线程2:  this.list = queryB();   // 快
// 谁后写完谁赢，和谁先发起无关 —— 典型的 lost update
```

| | Java 多线程 | 本篇的 JS 竞态 |
|---|---|---|
| **对得上** | lost update / 乱序覆盖 | 一模一样 |
| **对不上** | 还有**可见性**（缓存不刷）和**撕裂**（写到一半被打断） | **没有**。JS 单线程，`list.value = ...` 这一句是原子的 |
| **解法** | 加锁 / CAS / volatile | **不需要锁** —— 只要别让第二个请求发出去 |

**这就是为什么解法是"禁用入口"而不是"加锁"**：JS 里根本没有需要互斥的临界区，要拦的是"用户制造出第二个并发流"这件事本身。

## 三、诞生背景（横向轴）：这个 prop 为什么长这样

### 3.1 旧世界 · jQuery 时代

```js
$('#latestOnly').change(function () {
  $.get('/process-definition/page', { latestOnly: this.checked }, function (data) {
    $('#tbody').html(render(data))      // ← 一模一样的竞态，一个字都不差
  })
})
```

当年这个问题**同样存在**，而且更常见（那时候网速更慢）。通行解法就是**手动锁控件**：

```js
$('#latestOnly').prop('disabled', true)
$.get(url, params, function (data) {
  $('#tbody').html(render(data))
  $('#latestOnly').prop('disabled', false)    // 成功了要恢复
}).fail(function () {
  $('#latestOnly').prop('disabled', false)    // 失败了也要恢复
})
```

### 3.2 痛点：不是"不优雅"，是真的写不下去

**两个具体的坎**：

**① 恢复语句必须在每一个出口写一遍。** 成功一处、失败一处、超时一处、参数校验提前 `return` 一处 —— **漏掉任何一个分支，控件就永久卡死**，用户只能刷新页面。而"永久卡死"和"竞态"比起来是**更可见**的 bug，所以现实中大家宁可少写 disable，也不愿冒卡死的险 —— **结果就是这个防护经常干脆不做**。

**② 状态无处安放。** "这个控件现在是不是禁用的"，答案只存在于 **DOM 属性**里。代码里没有任何变量能回答它。想在别处（比如另一个按钮）跟着一起禁用，只能再 `$('#other').prop('disabled', $('#latestOnly').prop('disabled'))` —— 从 DOM 读状态再写回 DOM，**DOM 变成了唯一数据源**，这正是 jQuery 时代所有状态混乱的根。

### 3.3 新方案：把"禁用"从 DOM 属性变成状态变量的函数

Vue / React 这一代做的取舍是：

```html
:disabled="loading"
```

**为什么必须是这个形状？** 因为它把上面两个坎一次性拆了：

- 坎 ②：状态住在 `loading` 这个 ref 里，是**唯一数据源**。DOM 只是它的投影。想让第二个、第三个控件跟着禁用，各挂一个 `:disabled="loading"` 就行，**互相之间不认识**。
- 坎 ①：`loading` 的归位由 **`try/finally`** 保证 —— `finally` 就是"所有出口"这件事的语言级答案。你不再需要枚举分支，**语言帮你枚举**。

所以 `:disabled="loading"` 不是"一种写法"，它是**声明式 UI + `try/finally` 两件事咬合之后的必然结果**。少了任何一半都成立不了：只有声明式没有 finally，照样漏分支；只有 finally 没有声明式，还得手动同步 DOM。

> 📌 **回看你这页**：`loading` 在 `:75` 置 true、`:83-85` 的 `finally` 置 false —— **两件事你都已经有了**，只是没把结果接到控件上。这就是"零额外代码"的确切含义：不是"改动小"，是**基础设施早就建好了，只差最后一根线**。

### 3.4 代价 / 边界：它只是 80% 方案，别当银弹

`disabled` **只遮蔽入口，不取消已发出的请求**。它治不了：

| 治不了的场景 | 为什么 |
|---|---|
| 请求飞行中你切走路由 | 组件卸载了，A 回来照样往一个死掉的组件里写（Vue 3 里通常无害，但 `list.value = ...` 确实还会执行） |
| 从别的路径触发的第二次加载 | 比如定时轮询、别处 emit 的事件 —— 它们不经过被禁用的那个控件 |
| 请求本身很慢时的体验 | 用户被锁住 3 秒，只能干等；理想行为是**取消旧的、立刻发新的** |

**完备解法有两个**，都比 `disabled` 贵：

1. **`AbortController`** —— 发新请求前 `abort()` 掉旧的，浏览器真的会掐断连接。axios 支持 `signal` 配置。
2. **latest-wins（请求发号）** —— 每次请求发一个自增序号，回来时对不上最新号就**直接丢弃不写**：
   ```js
   let seq = 0
   async function loadList() {
     const my = ++seq
     const page = await pageDefinitions(...)
     if (my !== seq) return        // 我已经过时了，不写
     list.value = page.records
   }
   ```

**为什么本项目现在选 `disabled`**：三行表格页，用户没有"必须能中途改主意"的需求，锁 200ms 无感知；而上面两种都要改 `api/*.ts` 的签名或每个 `loadList` 的结构。**等 P6 表单设计器那种连续输入触发的搜索（每敲一个字发一次请求，根本不能禁用输入框），`disabled` 就会第一次不够用** —— 那时候上 latest-wins。

## 四、为什么 switch 挂 `:loading`、pagination 挂 `:disabled`（不是风格不统一）

**是两个组件给的能力不同，不是随手写的。**

### 4.1 `el-switch` 有 `loading` prop，且它**自动连带 disabled**

源码为证 —— `node_modules/element-plus/es/components/switch/src/switch.vue_vue_type_script_setup_true_lang.mjs:42-44`：

```js
const switchDisabled = useFormDisabled(computed(() => {
  if (props.loading) return true;      // ← loading 为真 ⇒ 直接算作 disabled
}));
```

这个 `switchDisabled` 一路传到底层真实的 `<input>` 上（同文件 `:140` 的 `disabled: unref(switchDisabled)`）—— 也就是说**浏览器层面的原生 disabled 生效了**，不是靠 CSS 假装（`el-switch` 的真身是个 `opacity:0` 藏起来的 `<input type="checkbox">`，见 [`原生控件的外衣与el-switch.md`](./原生控件的外衣与el-switch.md)）。

同时 `:173-175` 会多渲染一个转圈图标。

**所以 `:loading` 一个 prop 顶两个用**，而且语义更准：

| prop | 用户读到的意思 |
|---|---|
| `disabled` | 这个功能**不可用**（可能没权限、可能条件不满足） |
| `loading` | **正在处理**，稍等就好 |

请求飞行中显然是后者。

### 4.2 `el-pagination` **没有** `loading` prop，只有 `disabled`

`node_modules/element-plus/es/components/pagination/src/pagination.mjs:151` 只声明了 `disabled: Boolean`，然后 `:254`、`:259` 用它把翻页 handler 直接短路，`:288`–`:303` 把它透传给 prev / next / pager 三个子组件。

**没得选，只能 `:disabled="loading"`。**

> 结论：两处 prop 名不同，是**组件库能力的差异**，不是代码风格不一致。看到别人页面上两个写法混用，先查组件有没有 `loading` prop 再下判断。

## 五、动手实验

### 实验 1 · 纯 Promise 复现（浏览器 console 直接粘，10 秒）

不用起项目：

```js
let list = 'init'

const fakeRequest = (tag, ms) => new Promise(r => setTimeout(() => r(tag), ms))

async function loadList(tag, ms) {
  const data = await fakeRequest(tag, ms)
  list = data
  console.log('写入 →', data)
}

loadList('A · 只看最新版本', 300)   // 先发，慢
loadList('B · 全部版本',     100)   // 后发，快（模拟你第二次点击）

setTimeout(() => console.log('%c最终 list = ' + list, 'font-size:16px;color:red'), 600)
```

**输出**：

```
写入 → B · 全部版本
写入 → A · 只看最新版本
最终 list = A · 只看最新版本      ← 最后点的是 B，屏幕上留下的却是 A
```

**记忆点就落在这个"咦"**：你最后点的是 B，开关也停在 B 的位置，可数据是 A 的。

**对照组**：把第二行 `loadList` 注释掉（模拟 `:disabled` 生效、第二次点击根本发不出去），最终就是 `A`，和开关状态一致。

### 实验 2 · 在真页面上撞出来

1. `npm run dev` 开到流程管理页；
2. F12 → **Network** → 把节流（Throttling）调成 **Slow 3G**；
3. 快速点两下「只看最新版本」；
4. 盯着**开关状态**和**表格里有没有重复的流程 Key**（"只看最新版本"开着时同一个 key 不该出现两次）。

Slow 3G 下能稳定撞出来。加上 `:loading="loading"` 后再试一次，第二下点不动了 —— 这就是对照组。

### 实验 3 · 证明 `await` 治不了（最容易想歪的地方）

很多人第一反应是"那我把 `loadList()` 前面加个 `await` 不就行了"。**不行**，因为两次点击是**两个独立的事件回调**：

```js
// 模拟两次独立的点击，各自 await，互不相干
async function onClick(tag, ms) {
  await loadList(tag, ms)        // 加了 await
  console.log(tag, '这次点击处理完了')
}
onClick('A', 300)
onClick('B', 100)
// 输出顺序照样是 B 先 A 后 —— await 只能让「同一个函数内部」的语句排队
```

`await` 序列化的是**一个函数内部的语句**，不是**多次独立调用**。中间没有任何东西能让两个事件回调互相等待 —— 除非有一个**共享的状态**告诉第二次"现在别来"。那个共享状态就是 `loading`。

> 📌 顺带说清 `views/process/index.vue:98`、`:122` 那两处**没写 await 的 `loadList()`**：那是**有意的**（注释在 `:81-82`），因为 `loadList` 内部已 `try/catch` 兜住，不 await 也不会漏 rejection。**它和本篇的竞态是两码事**，别混。

## 六、常见误解速查表

| 误解 | 实情 |
|---|---|
| 「这是防手抖的体验优化，可做可不做」 | 它是**并发闸门**。不做的后果是数据与 UI 静默错位，不是"用户多点了一下" |
| 「表格上已经有 `v-loading` 了，够了」 | `v-loading` 只在**表格自己那块区域**盖遮罩。工具条的开关（`:5`）和下面的分页器（`:39`）都在遮罩外，鼠标照样点得到。它挡的是"别点表格里的按钮"，不是"别再发请求" |
| 「加个 `await` 就行了」 | `await` 只能序列化**同一个函数内部**的语句。两次点击是两个独立回调，见实验 3 |
| 「JS 是单线程，不会有并发问题」 | 单线程消除的是**撕裂**和**可见性**，消除不了**乱序覆盖**。异步 I/O 一进来，逻辑上的并发就存在了 |
| 「响应总是按请求顺序回来吧」 | 从来没有这个保证。HTTP 靠连接/流配对，不靠顺序。见 §2.4 四个来源 |
| 「`disabled` 会取消掉正在飞的请求」 | **不会**。它只挡新请求出生。要真取消得用 `AbortController`，见 §3.4 |
| 「switch 用 `loading`、分页用 `disabled`，是写乱了」 | 是组件能力不同：`el-switch` 有 `loading` prop 且自动连带 disabled，`el-pagination` 压根没有。见 §4 |
| 「加了 `:disabled` 就没有竞态了」 | 只挡住了**经由这个控件**的第二次触发。轮询、路由切换、别处 emit 都绕得过去。80% 方案 |

## 八、一句话总结

`loading` / `disabled` **不是为了好看，也不是防手抖 —— 它是唯一一处能阻止第二个请求出生的地方**。因为一旦两个请求同时在飞，JS 就没有任何机制保证它们按顺序回来，而**后回来的那个会静悄悄地赢**。

1. **`AbortController` 与 axios `signal`** —— 真正的取消。搜索框那种"每敲一个字发一次"的场景 `disabled` 完全失效，P6 表单设计器会撞上。
2. **latest-wins 模式怎么封装** —— §3.4 那段发号代码每个 `loadList` 都要抄一遍，能不能封成一个 `useLatest()` 组合式函数？这会是本项目第一个**自己写的 composable**。
3. **防抖 / 节流（debounce / throttle）** —— 和本篇是**互补**不是替代：防抖减少请求**数量**，`disabled`/latest-wins 保证结果**正确**。两个都做才完整。`@vueuse/core` 已在依赖里，有现成的 `useDebounceFn`。
4. **组件卸载后写 ref** —— §3.4 表里那条，Vue 3 里为什么通常无害？（`onUnmounted` 里 abort 是正经做法）
5. **`useFormDisabled`** —— §4.1 源码里那个函数：Element Plus 的 `el-form` 有个 `disabled` 属性能**一次性禁用整个表单**，靠的是 provide/inject 沿组件树往下传。这是 [`props向下events向上.md`](./props向下events向上.md) 之外的**第三种**父子通信方式，值得单开一篇。
