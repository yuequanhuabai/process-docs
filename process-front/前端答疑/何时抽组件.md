# 何时该把一段 UI 抽成子组件（答疑笔记）

> 由答疑 CLI 整理。通用前端原理，不限于某一页。
> 类比：跟后端"何时把代码抽成方法/类"是同一个问题——组件的"函数签名"就是 **props（入参）+ events（出参）**。
> 前置：`props 向下、events 向上` 的单向数据流（见本目录相关笔记 / 对话）。

## 一句话心法

> **抽组件不是免费的**——每抽一个，就要设计一套 props/events 接口。所以只在 **收益 > 这套接线成本** 时才抽。
> 别一看到"这是一块 UI"就抽；要看它值不值得为它**定义一个契约**。

## 该抽的 5 个信号（命中越多越该抽）

1. **复用**：同样的 UI 出现在 ≥2 个地方。一处改、多处受益。最硬的理由。
2. **篇幅/复杂度**：一个文件太长、一眼看不完。把内聚的一坨切出去，让主文件回到"一屏看懂骨架"。
3. **独立职责**：它是一件能自圆其说的事（"编辑一个用户""按 schema 渲染表单""画流程图"）。
4. **自有状态**：它管着一坨父组件根本不关心的内部状态（弹窗开关、表单校验信息、画布选中节点）。把状态连同 UI 封进去，父只通过 props/events 打交道。
5. **能起好名字**：对得上一个领域概念（`ProcessTable` / `UserEditDialog` / `TaskApproveDialog`）。只能叫 `Block2`/`RightPart` 的多半是硬切，不该抽。

## 不该抽 / 会踩坑的情况

- **陷阱① 过早抽象**：只用一次 + 简单 + 无独立逻辑，为它单开组件只增加跳文件负担和接线成本。简单东西留在原地更好读。
- **陷阱② "相同模式" ≠ "必须共用一个组件"**：结构相似但列/操作/接口不同的页面，强行抽"万能组件"会为兼容差异塞一堆 props/插槽，比重复写更糟。
  - **Rule of Three**：复制到**第三次**再考虑抽公共组件。头两次宁可复制——前两次看不清"哪些是真共性、哪些是各自特性"，过早抽出来的抽象往往是错的。
- **陷阱③ 切错边界**：把"本该一起变的东西"切开，改个小需求要同时动三个文件。内聚的留一起，独立变化的才分开（单一职责）。

## 落到本项目路线（P4/P5/P6）

| 阶段 | 该不该抽 | 为什么 |
|---|---|---|
| P4 现在（流程管理页） | **先不抽**，整页写在 `index.vue` | 第一次写，看不清共性；先跑通 |
| P4 写到第 2–3 个页面 | **考虑抽弹窗**（编辑/办理/审批 Dialog） | 职责独立、有自有状态、开始重复 |
| P4 四页写完回头看 | **再评估抽通用表格** | 到那时才知道四页真实共性在哪 |
| P5/P6 | **一开始就抽**（BpmnDesigner / FormRenderer / PropertiesPanel 等） | 职责独立、复杂、明确复用——五信号全中，排期本就规划成组件 |

> 呼应排期文档："P4 四个页面全部同构于 `views/user`" —— 但**同构 ≠ 立即抽公共组件**。先各写一遍，看清真共性再抽。

## 真要抽时，接口怎么设计

用"props 向下、events 向上"设计契约。以"编辑弹窗"为例：

- **props（父传进来）**：`visible`（是否显示）、`row`（要编辑的数据，新增时为空）。
- **events（往上报）**：`@submit`（用户保存，把表单数据喊上去让父调接口）、`@update:visible`（要关闭时通知父改状态）。
- 弹窗**内部**的表单值、校验状态自己管，不外泄。

好接口的标准：**父只通过这套 props/events 就能完全驾驭它，不用知道它内部怎么实现**——等同于后端设计类的 public 方法、隐藏内部字段。

## 一句话总结

> 抽组件时机 = **复用（Rule of Three）／篇幅过大／职责独立／自有状态／能命名** 命中；核心权衡是"收益是否值得那套 props/events 接口成本"。**别为相同的'模式'过早抽公共组件**——先复制，看清真共性再抽。
