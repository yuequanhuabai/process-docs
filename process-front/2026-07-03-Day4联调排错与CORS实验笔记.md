## 一、HTTP 的真面目（裸 TCP 实验回顾）

用 `net.createServer`（纯 TCP，不用任何 HTTP 库）打印浏览器发来的原始字节，结论：

1. **HTTP 请求/响应就是纯文本**：`方法 路径 版本` + 若干行 `键: 值` 头 + **空行** + 体。
   头和体之间用 `\r\n\r\n` 分隔，这是全部规矩。
2. **axios / fetch / request.ts 只是逐层薄包装**：
   - 第 1 层：HTTP 文本（电线上的真实形态）
   - 第 2 层：浏览器原生 `fetch`/`XMLHttpRequest`（method/headers/body 显式可见）
   - 第 3 层：axios（自动 JSON 序列化/解析 + 拦截器机制）
   - 第 4 层：`utils/request.ts`（注入 JWT + 拆 `R{code,msg,data}` 信封 + 401 跳登录）
3. **排查口诀**：不管包了几层，F12 Network 面板显示的永远是第 1 层的真相。

### 实验中撞到的错误 ①：HTTP 头不允许中文

```
TypeError: Failed to execute 'fetch': ... String contains non ISO-8859-1 code point.
```

- **根因**：`Authorization: 'Bearer 假token'` 里有中文。HTTP 头部规定只能用 ISO-8859-1（≈ASCII）；
  请求体可以 UTF-8（因为 `Content-Type` 声明了 charset），头部没有声明编码的机制。
- **推论**：这就是 JWT 长成 `eyJxxx.yyy.zzz` 的原因之一——Base64URL 编码产物全是 ASCII，才能安全放进头里。

### 顺带看到的三个冷知识

- 地址栏访问一次会产生 **3 个请求**：页面本身（`Sec-Fetch-Mode: navigate`）、
  `favicon.ico`（浏览器自动补发）、`/.well-known/appspecific/com.chrome.devtools.json`（开着 F12 时 Chrome DevTools 的探测，关 F12 就消失）。
- **Cookie 按域名隔离但不区分端口**：localhost 上任何程序设的 cookie 会被发给 localhost 所有端口（报文里看到 IDEA 和百度统计的 cookie 串门）。
- 浏览器会用 `Sec-Fetch-*` 头如实申报请求上下文（navigate / cors / no-cors、目标是 document/image/empty）。

## 二、后端报错：SQL Server 分页必须 ORDER BY

```
SQLServerException: Incorrect syntax near '@P0'
SQL: SELECT ... FROM sys_user OFFSET ? ROWS FETCH NEXT ? ROWS ONLY
```

- **根因**：T-SQL 中 `OFFSET/FETCH` 是 `ORDER BY` 子句的一部分，**没有 ORDER BY 就是语法错误**。
  `selectPage(page, new QueryWrapper<>())` 传了空条件、无排序。
- **修法**：分页查询显式加排序
  `new LambdaQueryWrapper<SysUser>().orderByDesc(SysUser::getCreateTime)`。
- **通用铁律**：**没有 ORDER BY 的分页在任何数据库都是不确定的**（结果集本无顺序，MySQL 只是"碰巧"稳定，
  翻页可能重复/丢行）。SQL Server 只是用语法强制你诚实。分页排序键最好含唯一列。
- **细节**：报错里的 `@P0` 是 mssql-jdbc 驱动把 Java 的 `?` 占位符翻译成的 SQL Server 命名参数——又一个"包装下面的真实形态"。
- **为什么 COUNT 成功、列表失败**：count 语句不拼分页子句，躲过了语法问题。
- ⚠️ 遗留疑点：当时日志 `COUNT` 返回 Total: 1，种子数据应为 3 条（admin/manager/employee）。
  若页面只显示 1 行，去库里 `SELECT * FROM sys_user` 核对种子 SQL 是否插全。

## 三、前端报错两连：TS 类型空间 与 async/await

### 错误 ②：把泛型写成了函数参数

```ts
// ✗ 错：never / PageResult 是类型，不是运行时的值
request.get(never, PageResult<SysUser>('/user/page', {...}))
// ✓ 对：类型参数放尖括号里、圆括号前
request.get<never, PageResult<SysUser>>('/user/page', { params: { current, size } })
```

- **核心概念：TS 的两个世界**。`<>` 里是**类型空间**（编译后全部擦除，运行时不存在）；
  `()` 里是**值空间**（编译后仍在，真正执行）。
- **重要推论（类型擦除）**：声明 `id: string` 不会在运行时校验后端真的返回 string。
  接口类型写错只会静默出 bug——类型是对运行时事实的**描述**，不是**保证**。
- 第二个泛型参数写 `PageResult<SysUser>` 而非 `R<PageResult>`，是因为拆包发生在拦截器里，
  业务代码拿到的已经是 `data` 本身——**运行时行为改了，类型声明要如实跟着改**。

### 错误 ③：await 缺 async（+ 重复 import）

```
Vue: await expressions are only allowed within async functions ...
```

- **根因**：`onMounted(() => { await ... })` 回调没标 `async`；另外 `ref` 被 import 了两次。
- **规则**：`async` 标记的是**离 `await` 最近的那层函数**——await 写在哪个函数体里，哪个函数就必须标 async，外层是不是都不算数。
- **本质**：`await` 是 `.then()` 的语法糖。函数体要被编译器切开重排塞进 then 回调，所以必须提前用 `async` 声明"此函数可暂停"。

```ts
// 等价的两种写法
pageUsers().then(page => { users.value = page.records })          // then 链
const page = await pageUsers(); users.value = page.records        // async/await
```

### 顺带学到：Vue 响应式的价值

`users.value = page.records` 一句赋值，表格自动重渲染，没写任何操作 DOM 的代码。
「数据变 → 视图自动变」是 Vue/React 存在的根本理由，其余都是周边。

## 四、CORS 完整拼图（本日核心收获）

### 4.1 规则总结

- **源(origin) = 协议 + 域名 + 端口**，任一不同即跨源（5173 → 9090 就是跨源）。
- **简单请求**（老 HTML 本来就发得出的）**直接发、不预检**：
  方法限 GET/HEAD/POST + 无自定义头 + Content-Type 限表单三件套（`text/plain` / `x-www-form-urlencoded` / `multipart/form-data`）。
- 踩了红线（如 `Content-Type: application/json`、`Authorization` 头）→ 浏览器先发 **OPTIONS 预检**"敲门"：
  预检不带请求体、不带真实 Authorization，只申报 `Access-Control-Request-Method/Headers`。
  服务器响应里必须有 `Access-Control-Allow-Origin/-Headers` "通行证"，真请求才会发出。
- **实测验证过**：带 JSON+Authorization 的 fetch → 两个请求（OPTIONS + POST）；
  `body:'hello'` 的裸 POST（text/plain）→ 只有一个请求，不预检。

### 4.2 CORS 是纯浏览器行为

- 执法者只有浏览器（保护用户浏览器不被恶意页面当枪使）。
- curl、Node、Vite proxy 这类**服务器对服务器**的请求不存在 CORS。

### 4.3 为什么走 proxy 没有预检

```
页面 http://localhost:5173
请求 http://localhost:5173/workflow/...   ← baseURL 是相对路径
→ 同源 → CORS 机制从头到尾未触发（连 Origin 头都不发）
→ Vite dev server 自己作为客户端把请求转发给 9090（服务器间通信，无 CORS）
```

**proxy 不是"绕过"预检，而是让浏览器眼里的请求变成同源，CORS 压根没启动。**
开发期 proxy 是把 CORS 问题推迟，不是消灭：生产环境前端静态资源与 API 不同源时它会回来
（对策：后端 CorsConfig 发通行证，或 Nginx 把页面和 API 反代到同一域名下永远同源）。

### 4.4 绝对地址直连实验（故意制造失败）

把 `request.ts` 的 baseURL 临时改为 `http://localhost:9090/workflow` 直连后端：

- **现象**：前端 axios 报 `Network Error`，页面弹"网络异常"，**后端一行日志都没有**。
- **解释 1（没日志 ≠ 没请求到）**：后端只配了 MyBatis SQL 日志，Spring Boot 默认不打印收到的 HTTP 请求。
  预检 OPTIONS 由 DispatcherServlet 在框架层直接应答（200 + `Allow` 头），**从未进入任何 Controller**，
  没有 SQL 就没有日志；且预检失败后真正的 GET 根本没发出。
  验证办法：Network 过滤器切到 **All** 找 OPTIONS 那条（预检不算 XHR）；
  或临时给后端加 `logging.level: org.springframework.web: DEBUG`。
- **解释 2（Network Error 为何干巴巴）**：**故意的安全设计**。CORS 拦截后浏览器给 JS 的错误被刻意抹平
  （不区分"服务器不存在/连接拒绝/CORS 拦截"），否则恶意页面可用 fetch 探测内网端口。
  详细死因只给"人"看：Console 红色报错（明说缺 `Access-Control-Allow-Origin`）+ Network 面板。
- **排查口诀**：**axios 说 Network Error 时，别问 axios，去问 Console 和 Network。**
- 实验已结束，baseURL 已改回 `'/workflow'`。

### 4.5 对 Day 6 的直接指导

1. 写 `CorsConfig` 就是给这套机制发通行证（等价于裸 TCP 实验里手写的那两行 `Access-Control-Allow-*` 文本）。
2. **经典坑提前预防**：`LoginInterceptor` 必须放行 OPTIONS——预检不带 Authorization 头（见 4.1），
   若拦截器对 OPTIONS 也要求 token，预检永远 401，所有跨源 POST 全挂。
