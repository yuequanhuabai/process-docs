## 一、为什么这次非要动后端

### Q1：前端查两次（一次 RU 一次 HI）再合并，不就不用改后端了？

**A**：会错，而且是**分页层面的错**。

两次查询各自有各自的 `total` 和分页切片。你把两页数据拼起来，页码就对不上了 —— 第 1 页可能出 15 条、第 2 页出 5 条，`total` 该填哪个也说不清。去重也麻烦（在途的实例 RU 和 HI 里**都有**）。

而且根本没必要：**HI 表本来就是全集**（见 Q2），一次查完事。

### Q2：`ACT_HI_*` 不是"历史归档表"吗，为什么在途的实例也在里面？

**A**：这是这次改造最反直觉的一点，但你 Day 12 亲手验过。

实例**一发起**，`ACT_HI_PROCINST` 里就有这一行了，只是 `END_TIME_` 为空；完结时引擎只是回来把 `END_TIME_` **UPDATE** 上去，不是那时候才插入。

| 表 | 装什么 |
|---|---|
| `ACT_RU_*` | **只装在途的**，结束就删行 |
| `ACT_HI_*` | **装全部**（含在途），在途的 `END_TIME_` 为空 |

所以它俩是「**在途子集 / 全集**」，不是「运行时 / 归档」。完整推演见 [`../../process-back/deep_dive/hi_tables/00-历史表族-宏观.md`](../../process-back/deep_dive/hi_tables/00-历史表族-宏观.md)。

### Q3：`status` 为什么让后端算？前端拿到 `endTime` 和 `deleteReason` 自己判断不行吗？

**A**：能跑，但会埋雷 —— **同一套业务规则写在两个地方，迟早不一致**。

判据是三行 if（`endTime` 空→进行中；有 `endTime` 且无 `deleteReason`→办结；两者都有→终止）。今天前端后端写得一样，明天后端加个"已挂起"状态，前端不知道，就显示错了。

而且 Day 18 历史页还要再用一次这套判定 —— 放后端只写一遍，放前端要抄两遍。

**延伸**：这是个通用原则 —— **业务判定归后端，前端只做展示映射**。前端该做的是 `RUNNING` → 「进行中」+ 蓝色 tag 这种纯 UI 的事。

## 二、参数传递（这次最容易栽的地方）

### Q4：`definitionKey: definitionKey || undefined` 这一行，为什么不能直接写 `definitionKey`？

**A**：**axios 会自动丢弃值为 `undefined` 的 params，但不会丢弃空字符串。**

下拉选「全部流程」时你的 `definitionKey.value` 是 `''`，直接传的话 axios 会拼出：

```
/process-instance/page?current=1&size=10&definitionKey=
```

后端 `@RequestParam(required=false) String definitionKey` 收到的是**空字符串**（不是 null），于是拿空串去过滤 → **0 条**。页面一片空白，你还以为是后端挂了。

转成 `undefined` 后 axios 直接不拼这个参数，后端才拿到 null，才走"不过滤"分支。

**延伸**：转换放在 **api 层**做（而不是页面层），这样以后每个调用点都不用操心。`status` 同理。

### Q5：`variables` 为什么要嵌一层？直接 `{ processDefinitionKey, businessKey, reason }` 不行吗？

**A**：因为 `reason` 不是接口的固定字段，它是**流程变量**。

请求体的三个字段里，`processDefinitionKey` 和 `businessKey` 是引擎的固定概念（用哪个流程、关联哪条业务记录），而 `variables` 是一个**开放的 Map** —— 你往里塞什么，引擎就存什么到 `ACT_RU_VARIABLE` / `ACT_HI_VARINST`。

平铺的话后端没法区分"这是接口字段"还是"这是业务变量"。

```json
{
  "processDefinitionKey": "reimburseProcess",
  "businessKey": "RB-2026-0001",
  "variables": { "reason": "出差住宿费", "amount": 1200 }
}
```

### Q6：变量名写错会怎样？

**A**：**什么都不会发生 —— 这才是可怕的地方。**

引擎不校验变量名拼写。你写 `resaon` 它照单全收，悄悄新建一个叫 `resaon` 的变量；审批人那边按 `reason` 取，取到 `null`，页面显示空白，**没有任何报错**。

这叫**弱契约**。三个地方要对齐：前端表单字段名 / `complete` 传参 / BPMN 里的表达式。详见 [`../../process-back/deep_dive/hi_tables/04-ACT_HI_VARINST.md`](../../process-back/deep_dive/hi_tables/04-ACT_HI_VARINST.md)，这也正是 P6 表单 schema 要管住的事。

### Q7：发起时传 `processDefinitionKey` 而不是 `processDefinitionId`，为什么？

**A**：`key` 跨版本不变（`reimburseProcess`），`id` 是**带版本的**（`reimburseProcess:1:xxx`）。

传 key，后端 `startProcessInstanceByKey()` 会自动取**最新版本**。这样你重新部署了 v2 之后，新发起的自动走 v2，前端一行代码都不用改。

传 id 就锁死在某个版本上了 —— 那是特殊场景（比如"重跑一条旧版本的流程"）才需要的。

## 三、筛选与分页

### Q8：状态筛选为什么必须传给后端？前端 `list.filter()` 不是更简单？

**A**：**前端 filter 只能过滤"当前这一页"**，分页立刻就错：

假设总共 25 条，其中办结 8 条。你在第 1 页（10 条里恰好 3 条办结）做 filter：

- 表格显示 3 条 ✅ 看着没问题
- 但分页器还写着「共 25 条」❌（应该是 8）
- 点第 2 页 → 又从后端拿 10 条再 filter → 可能 0 条 ❌ 空页
- 用户永远看不到第 3 页里的那些办结记录 ❌

**只要有分页，筛选就必须在后端做。** 这条对任何列表页都成立。

### Q9：切换筛选条件时，为什么要 `current.value = 1`？

**A**：因为筛选后总条数变少了，当前页码可能已经不存在。

比如你在第 3 页，切到「已终止」只剩 2 条（1 页），还停在 `current=3` 去查 → 后端返回空数组 → 页面空白但分页器显示「共 2 条」，很怪。

**规则：任何改变结果集的操作（筛选、搜索、切换条件）都要回第一页。**

### Q10：为什么「运行中实例」页终止后要 `current.value -= 1`，「我的发起」页撤回后却不用？

**A**：**因为两页查的表不一样** —— 这道题能检验你有没有真的理解这次改造。

| | 查哪 | 终止/撤回后 |
|---|---|---|
| 运行中实例 | **RU 表** | 那行**从结果里消失**（RU 只装在途的）→ 若是当前页最后一条，会停在空页，所以要回退页码 |
| 我的发起 | **HI 表** | 那行**还在**，只是 `status` 变成 `TERMINATED` → 总条数不变，页码不用动 |

## 四、表单与弹窗

### Q11：`formRef.value?.validate().then(() => true).catch(() => false)` 为什么写这么绕？

**A**：`validate()` 返回一个 Promise —— 校验通过 resolve，**不通过 reject**。

如果直接 `await formRef.value?.validate()`，校验不通过就会抛异常。要么你在外层包 try/catch，要么就用这种 `.then/.catch` 转成布尔值的写法（`views/user/index.vue` 用的就是这个）。

后者的好处是意图明确：`if (!valid) return`，读代码的人一眼知道这里在做什么。

### Q12：重置表单为什么用手动赋值 + `clearValidate()`，不用 `resetFields()`？

**A**：`resetFields()` 只能重置**写了 `prop` 的** `el-form-item`。没写 `prop` 的字段它不认识，重置不了。

代码库里 `views/user/index.vue` 就是手动重置的（那个表单有几个 item 没写 prop）。跟着现有做法走，不容易踩坑。

`clearValidate()` 是单独清掉红色报错提示的 —— 不清的话，上次校验失败的红字会留在那儿。

### Q13：既然 P6 要做表单设计器，现在这三个输入框是不是该先抽成通用组件？

**A**：**别抽。**

P6 做完之后，这块会整体换成"按表单 schema 动态渲染"—— 是**推倒重来**，不是在现有组件上改。现在抽的通用组件到时候一行都用不上，纯属白费功夫，还增加了当前的理解成本。

**原则：为"还没想清楚的未来需求"做抽象，通常是负收益。** 等真出现第二个、第三个相似场景，共性自然会浮出来，那时候再抽既准又快。（同样的道理见 [`../前端答疑/何时抽组件.md`](../前端答疑/何时抽组件.md)）

## 五、Element Plus 新用法

### Q14：`ElMessageBox.prompt` 返回的是什么？怎么拿到用户输入？

**A**：resolve 出来的是一个**对象** `{ value, action }`，输入的内容在 `.value` 里：

```ts
const { value } = await ElMessageBox.prompt('请输入终止原因', '终止流程', { ... })
```

和 `.confirm` 一样，用户点「取消」会 **reject**，所以要 try/catch。

**必填校验**用配置项 `inputValidator` —— 返回 `true` 表示通过，返回**字符串**表示不通过并把该字符串当错误提示：

```ts
inputValidator: (v: string) => (v && v.trim() ? true : '终止原因不能为空')
```

### Q15：`handleTerminate` 里为什么是**两个**独立的 `try/catch`？

**A**：因为要处理的是**两件性质完全不同的事**：

```ts
try { ...prompt... } catch { return }        // ① 用户取消 → 静默返回，什么都不做
try { ...terminate... } catch { /* 空 */ }   // ② 接口失败 → 拦截器已弹错，这里只是别让 rejection 逃走
```

写成一个 try 的话，"用户点了取消"和"接口 500 了"会走进同一个 catch —— 你就没法区分该不该提示、该不该刷新列表了。

### Q16：`el-select` 的 `label` 和 `value` 分别对应什么？

**A**：`label` 是**给人看的**，`value` 是**提交给后端的**。

```vue
<el-option v-for="d in defs" :key="d.key" :value="d.key" :label="d.name" />
```

用户看到「报销流程」，`v-model` 拿到的是 `reimburseProcess`。这也是为什么下拉的数据源要请求流程定义列表 —— 得同时拿到中文名和 key。

## 六、三级流程带来的新情况

### Q17：发起后 `currentActivityName` 为什么直接是「经理审批」，而不是「员工发起」？

**A**：因为 `startEvent`（开始事件）是**瞬时**的，没有停留。

引擎在一个事务里走完：创建实例 → 经过 startEvent → 沿 flow1 → 到达 `managerApprove`（userTask）→ **停下等人办理**。只有 userTask 会"卡住"，所以"当前节点"永远是某个 userTask。

`ACT_HI_ACTINST` 里能看到 startEvent 那一行的 `START_TIME_` 和 `END_TIME_` 是同一时刻（甚至同一毫秒，这就是 Day 14 要加二次排序的原因）。

### Q18：我用 manager 账号，为什么在待办里看不到「财务审批」那个节点？

**A**：**这是对的，不是 bug。**

新增的三个流程是三级：一级 `candidateGroups="manager"`、二级 `candidateGroups="admin"`。待办查询是拿你的 `role` 去匹配候选组：

| 账号 | role | 能看到 |
|---|---|---|
| manager | `manager` | 只有「经理审批」节点 |
| admin | `admin` | 只有「财务/总监审批」节点 |
| employee | `employee` | 都看不到（他是发起人不是审批人） |

**所以测一条三级流程走完，必须用两个账号**（manager 批一次 + admin 批一次）。这是 Day 16 联调和 Day 15 最大的操作差异。

### Q19：我发起的流程，我自己能审批吗？

**A**：不能。employee 的 role 是 `employee`，而审批节点的候选组是 `manager` / `admin`，匹配不上 —— 后端 `assertCanOperate` 会拦下来（Day 13 实测过越权四连）。

**延伸**：真实系统里"发起人不能审批自己的单子"通常还要额外防一手（万一某人既是员工又是经理）。当前 demo 里一人一个 role，天然不会出现，暂不处理。

## 七、调试

### Q20：页面出来了，但「状态」列全是空白 / 报错，怎么排？

**A**：**九成是后端还没改完**。按这个顺序查：

1. **DevTools → Network**，找 `my-started` 那条请求，看响应 JSON 的 `data.records[0]`：
   - **没有 `status` 字段** → 后端 VO 没加字段，回去做 [`07`](../../process-back/process_instance/07-Day16-查询改造为历史表.md) 第四节
   - **有 `status` 但是 `null`** → VO 加了字段但工厂方法里没赋值（判据那三行没写）
   - **有值但办结的实例根本没出现在列表里** → `myStarted()` 还在查 `RuntimeService`，没换成 `HistoricProcessInstanceQuery`
2. 字段都对但页面还空白 → 检查你的 `STATUS_MAP` 的 key 和后端返的字符串**大小写是否一致**（后端返 `COMPLETED`，你写成 `Completed` 就取不到）

**记住 Step 0 那条**：后端 knife4j 验通过再写前端，能省掉这一整轮排查。

### Q21：「发起人」列显示的是数字 `3` 不是姓名，怎么回事？

**A**：后端 `enrich()` 没生效 —— `startUserName` 是 null，你的模板兜底显示了 `startUserId`。

去 knife4j 调一下 `my-started`，看返回里 `startUserName` 是不是 null。是的话回后端检查那个批量查 `sys_user` 的逻辑（注意别写成 N+1）。

### Q22：筛选「已办结」和「已终止」加起来，和「全部」的条数对不上？

**A**：说明后端的过滤分支写漏或写重了。三个状态应该是**互斥且穷尽**的：

```
RUNNING + COMPLETED + TERMINATED = 全部
```

最常见的错是 `.finished()` 把终止的也算进"已办结"了 —— 终止的实例**也是 finished 的**（有 `END_TIME_`），要再叠一个 `DELETE_REASON_` 为空的条件才是真正的"正常办结"。

这条正是 [`07`](../../process-back/process_instance/07-Day16-查询改造为历史表.md) 验收清单第 5 步要验的。
