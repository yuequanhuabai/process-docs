## 一、这两个页面要干什么（需求）

### 页面 A：运行中实例　`/instance`

**把所有人正在跑的实例列出来，可按流程筛选，可终止。**

- 表格：流程名称 / 业务标识 / 当前节点 / 发起人 / 发起时间 / 实例 ID
- 顶部「流程」下拉筛选（对应后端 `definitionKey` 参数）
- 每行一个操作：**终止**（要填终止原因）
- 分页

### 页面 B：我的发起　`/my-start`

**看自己发起过的全部申请单（含已办结、已终止），并能发起新流程。**

- 表格：流程名称 / 业务标识 / **状态** / 当前节点 / 发起时间 / **结束时间**
- 顶部「状态」下拉筛选（全部 / 进行中 / 已办结 / 已终止）
- 顶部「＋ 发起流程」按钮 → **弹窗**（选流程 + 填业务标识 + 填事由）
- 每行操作：进行中的可**撤回**（= 终止自己的）

## 二、和 Day 15 的关系：结构同构，多两样新东西

两个页面的骨架和 `views/process` 完全同构 —— **工具条 + 表格 + 分页**。五个 ref（`list / total / current / size / loading`）、`loadList()`、`handlePageChange()`、`onMounted(loadList)` 这套套路照搬，换字段即可。

真正的新东西只有两样：

| 新东西 | 说明 |
|---|---|
| **第一次往后端提交数据** | 发起流程弹窗（`el-dialog` + `el-form`）。Day 15 全是查询和状态切换，没有表单提交 |
| **第一次是"要填参数"的危险操作** | 终止要带 `reason`，所以用 `ElMessageBox.prompt`，不是 Day 15 那个 `.confirm` |

选型理由逐条见 [`组件选型解析.md`](./组件选型解析.md)。骨架范式若记不清，回看 [`../process_manage/01-页面定位与修改点.md`](../process_manage/01-页面定位与修改点.md) 第二节。

## 四、后端契约速查（写 api 层时对着填）

base 路径：`/process-instance`（request 的 baseURL 已是 `/workflow`，写相对路径即可）

| 用途 | 方法 + 路径 | 参数 | 拆包后返回 |
|---|---|---|---|
| 运行中实例分页 | `GET /process-instance/page` | query: `current, size, definitionKey?` | `PageResult<ProcessInstance>` |
| 我的发起分页 | `GET /process-instance/my-started` | query: `current, size` | `PageResult<ProcessInstance>` |
| 发起流程 | `POST /process-instance/start` | **body**（JSON）| `ProcessInstance` |
| 终止 / 撤回 | `DELETE /process-instance/{instanceId}` | 路径 id；query: `reason?` | `void` |

`ProcessInstance` 前端类型（对齐**改造后**的 `ProcessInstanceVO`）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 实例 id（引擎 uuid）。**终止传它** |
| `processDefinitionKey` | string | 流程 key，如 `reimburseProcess` |
| `processDefinitionName` | string | 流程名称，如「报销流程」|
| `processDefinitionId` | string | 具体版本的定义 id |
| `businessKey` | string \| null | 业务标识，可能 null |
| `startUserId` | string | 发起人 userId（数字字符串）|
| `startUserName` | string \| null | 发起人姓名 ← **页面显示这个，别显示 userId** |
| `startTime` | string | 发起时间（后端已格式化成 `yyyy-MM-dd HH:mm:ss`）|
| `endTime` | string \| null | 结束时间，在途为 null |
| `status` | `'RUNNING' \| 'COMPLETED' \| 'TERMINATED'` | 结局，**后端已算好** |
| `deleteReason` | string \| null | 终止原因 |
| `currentActivityName` | string \| null | 当前节点名，已结束为 null |
| `suspended` | boolean | 实例是否挂起（本页不用）|

**发起请求体**（对齐后端 `StartProcessInstanceRequest`，写之前去 knife4j 对一眼字段名）：

```json
{
  "processDefinitionKey": "reimburseProcess",
  "businessKey": "RB-2026-0001",
  "variables": { "reason": "出差住宿费报销" }
}
```

> 传的是 **key 不是 id** —— 后端按 key 自动取最新版本。

## 五、⚠️ 四个坑

1. **`status` 是后端算好的字符串，前端只做映射**。别在前端写 `if (endTime && !deleteReason)` 这种判据 —— 同一套规则写两遍迟早不一致。三态映射写成常量对象（`STATUS_MAP`），Day 18 历史页还要再用一次，能直接搬。
2. **`my-started` 查历史表、`page` 查运行时表 —— 数据源不同是故意的**。「运行中实例」本来就只该看在途的。看到两个接口返回范围不一致时，别以为是 bug。
3. **终止要填原因，用 `ElMessageBox.prompt` 不是 `.confirm`**。原因不是可有可无 —— `deleteReason` 正是区分「已办结」和「已终止」的判据之一，不填的话这条单子在历史里就成了莫名其妙结束的。
4. **所有 id 都是字符串**。实例 id 是带 `-` 的 uuid，TS 里声明 `string`，别写 `number`。
