## 一、背景与目标

P4 四个表格页已完成两个（流程管理、实例+我的发起）。本页是第三个：**待办任务页**——审批人（manager / admin）登录后看到轮到自己办的任务，在界面上完成办理，推动流程流转到下一节点。

这是全链路「登录 → 发起 → **审批** → 历史」中此前只能靠 knife4j 手工调接口的一环，本页做完后审批动作首次界面化。

**交付物**：`api/task.ts` + `views/task/index.vue` + 路由 `/task` + 侧栏菜单项。

## 二、范围

### 做

| # | 功能 | 说明 |
|---|---|---|
| F1 | 待办列表（分页表格） | 调 `GET /task/todo`，展示当前登录人的待办（候选组 = 我的角色，或已指派给我），按创建时间倒序 |
| F2 | 办理弹窗 | 点行内「办理」→ 调 `GET /task/{taskId}` 拉详情 → 弹窗内**上半只读区**展示申请内容（流程变量），**下半输入区**填审批意见 → 提交调 `POST /task/complete` |
| F3 | 办理后列表刷新 | 提交成功后关弹窗、刷新列表（该行应消失——任务已流转走） |
| F4 | 路由与菜单 | `/task` 挂 layout 子路由 + 侧栏菜单「待办任务」 |

### 不做（明确排除，防蔓延）

| 项 | 理由 / 去处 |
|---|---|
| 转办、委派、退回 | 后端无接口，P3 范围就没做；需要时另立需求 |
| 已办列表 | 是 Day 18「已审批」页的活（`ApprovedTaskVO` + HistoryController） |
| 按流程/发起人筛选待办 | 后端 `todo()` 只有 `current/size` 两个入参，无过滤参数；待办本来就该"全都要处理"，不筛 |
| 动态表单渲染 | `formKey` 当前恒 null，P6 表单设计器的活；只读区先按变量 key-value 渲染 |
| 认领/释放（claim/unclaim）界面化 | 后端 `complete()` 内部已自动认领（`FlowableTaskServiceImpl.java:57-60`），界面无需单独的认领按钮 |

## 三、角色与场景

| 角色 | 场景 | 数据来源 |
|---|---|---|
| manager（id=2） | 一级审批：看到停在 `managerApprove` 的任务并办理 | `taskCandidateGroup("manager")` |
| admin（id=1） | 二级审批：manager 办完一级后，三级流程（报销/采购/出差）流转到 `adminApprove`，admin 看到并办理 | `taskCandidateGroup("admin")` |
| employee（id=3） | 发起人，无审批节点 → 待办列表**空** | 空态要有正常展示，不是报错 |

⚠️ 越权兜底在后端（`assertCanOperate`，`FlowableTaskServiceImpl.java:83-98`）：已被他人认领的任务、不在候选组的任务，提交会被 `BizException` 拦下。前端只需正常展示错误信息，不必自己做权限判断。

## 四、接口契约与字段缺口

后端三条接口 P3 已就绪（`TaskController.java`），**本页开工不阻塞于后端**。但列表字段有缺口，见 4.2。

### 4.1 接口清单

| 接口 | 入参 | 出参 | 备注 |
|---|---|---|---|
| `GET /task/todo` | `current`、`size` | `IPage<TaskVO>` | 无其他过滤参数 |
| `GET /task/{taskId}` | 路径参数 | `TaskFormVO`（= TaskVO + `variables` + `formKey`） | 办理前拉详情用 |
| `POST /task/complete` | body：`CompleteTaskRequest { taskId, variables? }` | `R<Void>` | ⚠️ 是 body 传 taskId，**不是** `/task/{taskId}/complete`（旧文档写错过，以代码为准） |

### 4.2 列表字段：TaskVO 现有 8 个字段 vs 页面想要的列

| 页面想要的列 | TaskVO 有吗 | 说明 |
|---|---|---|
| 任务名称（如「经理审批」） | ✅ `name` | |
| 创建时间 | ✅ `createTime` | 已格式化 `yyyy-MM-dd HH:mm:ss` |
| **流程名称**（如「报销流程」） | ❌ 只有 `processDefinitionId`（形如 `reimburseProcess:1:xxx`，不能直接示人） | **缺** |
| **发起人姓名** | ❌ 完全没有 | **缺** |
| **业务标识 businessKey** | ❌ 完全没有 | **缺** |
| 办理人 | ✅ `assignee`（未认领为 null） | 本页多数行是 null，价值低，倾向不显示 |
| 是否挂起 | ✅ `suspended` | 本页 TaskVO 走 RU 查询、字段真实可用（断点文档的哑雷是 `ProcessInstanceVO` 的 HI 路径，与本页无关）；但暂无使用场景，不显示 |

**缺口的后果**：不补的话，列表每行只能看到「经理审批 + 时间」，manager 面对多条待办**分不清哪条是谁发起的哪个流程的申请**，必须逐条点开详情靠 `variables` 里的 `initiator` 辨认——列表的筛选价值基本归零。

→ 补不补、怎么补，见 **七、待决策项 ①**。

### 4.3 详情与办理的字段

- `TaskFormVO.variables`：发起时提交的流程变量（`days` / `reason` / `initiator` 等，`taskService.getVariables()` 沿执行树取到实例级）。**只读区按 key-value 渲染**，不写死字段名（不同流程变量不同）。
- `CompleteTaskRequest.variables`：办理时写入的变量。按后端示例约定为 `{ approved: boolean, comment: string }`，选填。

## 六、验收标准（= P4 Day 17 验收行 + 断点文档 A.3 展开）

1. manager 登录 → 待办列表出现停在 `managerApprove` 的现成样本（数据库已有）；
2. manager 在**界面**办掉一条**三级流程**（报销/采购/出差）的一级；
3. 切 admin 登录 → `adminApprove` 的待办出现 ⇒ **界面办理 + 两级流转**都通；
4. admin 再办掉它 → employee 的「我的发起」里该条变「已办结」；
5. employee 登录 → 待办列表为空态，不报错；
6. `npm run build`（含 `vue-tsc -b`）转绿。

## 七、待决策项（需求层面，画原型前必须定）

### ① 列表三个缺字段（流程名称 / 发起人姓名 / businessKey）补不补后端？

| 方案 | 内容 | 代价 | 效果 |
|---|---|---|---|
| A · 不补 | 列表只显示 `name` + `createTime`，靠点开详情辨认 | 零 | 列表辨识度差，manager 多条待办时体验明显掉档 |
| **B · 补（推荐）** | `TaskVO` 加 `processDefinitionName` / `startUserName` / `businessKey` 三字段，`todo()` 末尾照 Day 16 `enrich()` 套路批量填充（**整页固定 2~3 次查询，不写成 N+1**） | Day 17 从纯前端变**双端**，约 +0.5 块 | 列表一眼可辨；且 Day 16 决策时已预判"Day 17/18 还会用到发起人姓名"，套路现成 |

推荐 B 的理由与 Day 16 方案①同构：改的是同一个 VO + 同一个 Service，现在不补，Day 18 已审批页大概率还要再来一遍。

### ② 办理弹窗的按钮形态：单按钮还是「同意/拒绝」双按钮？

⚠️ 关键事实：当前四个 BPMN 模板**都是直线流程，没有排他网关**——`complete` 一执行流程就往下走，`approved: false` 只是被记录进变量，**并不会改变流向或终止流程**。

| 方案 | 内容 | 问题 |
|---|---|---|
| **A · 单按钮「提交办理」+ 意见输入（推荐）** | `approved` 固定 true（或干脆不传），comment 选填 | 与引擎实际语义一致，不撒谎 |
| B · 「同意/拒绝」双按钮 | 拒绝时传 `approved: false` | **语义错位**：用户点了"拒绝"，流程却照样流转甚至办结——界面在撒谎 |
| C · 改 BPMN 加排他网关走真拒绝分支 | 需改四个模板 + 重部署 | 超出 Day 17 范围；建议登记为挂起项，留给 P5 设计器做完后顺手落 |

推荐 A 落地 + C 登记挂起项（登记三处：P4 Day 17 条目、总控第四节、P8 第三节——维护约定要求）。

### ③ 审批意见（comment）必填吗？

推荐**选填**：后端 `variables` 本就可选，且方案②-A 下没有"拒绝必须给理由"的场景。空值照 myStart 体例 `.trim() || undefined` 处理，不往 variables 里塞空串。
