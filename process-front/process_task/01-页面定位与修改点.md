## 一、这个页面要干什么（需求速览，全文见 `00`）

**待办任务　`/task`**

- 表格：流程名称 / 业务标识 / 任务名称 / 发起人 / 创建时间 + 操作列「办理」
- **没有筛选控件**——后端 `todo` 只有 `current/size` 两个入参，待办本来就该全处理，工具条只有标题
- 点「办理」→ 先拉详情 → 弹窗：**上半只读区**（流程/节点、业务标识、申请变量）+ **下半审批意见**（选填）→ 单按钮「提交办理」
- 办理成功 → 关弹窗 → 该行从列表消失（任务流转走了）
- 数据随登录人变：manager 看 `managerApprove`、admin 看 `adminApprove`/`财务审批`、employee 恒为空态——**页面零角色判断代码**，过滤在后端（`taskCandidateGroup(role)`）

## 二、和 Day 16 的关系：骨架第三次复用，多两样新东西

骨架仍是 **工具条 + 表格 + 分页** 那套（五个 ref + `loadList()` + `handlePageChange()` + `onMounted`），4 div 布局照实例页范本（`.task-page` > `.toolbar` / `.table-wrap` / `.pager-wrap`）。比 Day 16 还少一样——没有筛选下拉。

真正的新东西：

| 新东西 | 说明 |
|---|---|
| **第一次"先查详情再操作"** | 发起弹窗打开时是空表单；办理弹窗打开前要先调 `GET /task/{taskId}` 拿 variables，**拉不到就不开弹窗** |
| **第一次动态渲染 key-value** | 只读区按 `variables` 的键值对遍历渲染，**不写死字段名**（不同流程变量不同，P6 表单渲染器来之前先这样过渡） |

另有一样"新东西的消失"也值得注意：**办理弹窗不需要 `el-form` 那套校验**——零必填字段，`validate` / `rules` / `resetFields` 全用不上。为什么可以不用见 [`组件选型解析.md`](./组件选型解析.md)。

## 四、后端契约速查（写 api 层时对着填）

base 路径：`/task`（request 的 baseURL 已是 `/workflow`，写相对路径即可）

| 用途 | 方法 + 路径 | 参数 | 拆包后返回 |
|---|---|---|---|
| 待办分页 | `GET /task/todo` | query: `current, size`（**没有第三个**）| `PageResult<Task>` |
| 任务详情 | `GET /task/{taskId}` | 路径 id | `TaskForm` |
| 办理 | `POST /task/complete` | **body**（JSON）| `void` |

⚠️ **办理的 `taskId` 在 body 里，不是路径参数**——不是 `/task/{taskId}/complete`。旧断点文档在这里写错过一次，以 `TaskController.java:40-44` 为准。

`Task` 前端类型（对齐**补字段后**的 `TaskVO`，11 个字段）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 任务 id（引擎 uuid）。**办理传它** |
| `name` | string | 任务名称，如「经理审批」 |
| `taskDefinitionKey` | string | BPMN 节点 key，如 `managerApprove`（本页不显示）|
| `assignee` | string \| null | 办理人 userId，未认领为 null（本页不显示）|
| `processInstanceId` | string | 所属实例 id |
| `processDefinitionId` | string | 定义 id 含版本（不能示人，显示用下面的 name）|
| `createTime` | string | 后端已格式化 `yyyy-MM-dd HH:mm:ss` |
| `suspended` | boolean | 本页不用（此处走 RU 是真值，但没有使用场景）|
| `processDefinitionName` | string | ← Day 17 新增，「报销流程」 |
| `businessKey` | string \| null | ← Day 17 新增，可能 null |
| `startUserName` | string \| null | ← Day 17 新增，发起人姓名 |

`TaskForm`（详情出参，= `Task` 再加两个）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `variables` | `Record<string, unknown>` | 申请内容（days / reason / initiator…），**只读区据此动态渲染** |
| `formKey` | string \| null | P6 之前恒 null，先声明着不用 |

**办理请求体**（对齐后端 `CompleteTaskRequest`）：

```json
{
  "taskId": "7ccc5cf1-…",
  "variables": { "approved": true, "comment": "同意" }
}
```

> `approved` 前端固定传 `true`（决策②，四个模板无排他网关，"拒绝"是谎言）；`comment` 选填，空则不塞进 variables。

## 五、⚠️ 五个坑

1. **`todo` 没有筛选参数**。照抄 `api/instance.ts` 时别把 `definitionKey` / `status` 那第三个参数也抄过来——后端没有，传了也是被忽略，但类型里声明了就是撒谎。
2. **详情拉不到就别开弹窗**。`taskDetail` 可能被后端拦（"已被他人认领，无权操作"）——错误拦截器会弹，页面要做的只是 catch 后 `return`，别让一个空弹窗立在那里。
3. **办理失败不关弹窗**。提交被拦（同上，或任务刚被别人办掉）时用户填的意见还在，关了就丢了；只有成功才关。
4. **办空一页要回退页码**。办理成功后该行消失，若当前页只剩这一条且不在第一页，`current -= 1` 再 `loadList()`——照实例页 `handleTerminate` 里那三行。
5. **variables 的值类型是 `unknown`**。渲染时直接插值显示即可（`{{ v }}`），别去 `v.length` / `v.toFixed()`——引擎里存什么类型都有可能。`initiator` 显示出来是 userId 数字，**这是已知现状不是 bug**（值美化是 P6 表单渲染器的活）。
